# Контрибьюции в 1c-dev-rules

Спасибо, что хотите улучшить набор! Этот документ — короткий гайд: как добавить скил, поправить правило или синхронизироваться с upstream.

> Подробности устройства набора — в [`docs/ARCHITECTURE.md`](./docs/ARCHITECTURE.md). Здесь — практические шаги.

## Перед началом

- Откройте [Issue](https://github.com/Roman-repo/1c-dev-rules/issues) с описанием, что планируете (особенно для нового скила или изменения правила) — обсудим подход, чтобы работа не ушла впустую.
- Для бага/опечатки можно сразу PR.

## Как добавить новый скил

1. Создайте каталог `skills/1c-<имя>/` (префикс `1c-`, kebab-case).
2. Создайте `SKILL.md`:
   ```yaml
   ---
   name: 1c-<имя>            # совпадает с каталогом
   description: <суть>. Use when <сигналы> — главное в первых ~250 символах
   when_to_use: <доп. триггеры, ключевые слова>
   license: MIT
   ---
   ```
3. Тело `SKILL.md` ≤500 строк: краткая сводка правил + мини-чек-лист.
4. Если правила не помещаются — `references/<файл>.md`, сошлитесь из тела.
5. **Проверьте локально:**
   ```bash
   python3 scripts/validate_skills.py
   python3 -m unittest tests.test_validate_skills -v
   ```
   Обе команды должны дать PASS/OK.
6. Обновите таблицу скилов в [`README.md`](./README.md).
7. Добавьте запись в [`docs/CHANGELOG.md`](./docs/CHANGELOG.md).

## Главные правила оформления

- **Универсальность.** Скилы не содержат упоминаний конкретных конфигураций (`торо_`, `гкс_`, `Project/Toir`, названия продуктов). Примеры — абстрактные (`Документ.РеализацияТоваровУслуг`, `РегистрНакопления.ТоварыНаСкладах`) или в виде плейсхолдеров (`<Домен>Сервер`). Проектная специфика — в `AGENTS.md` проекта-потребителя, не здесь.
- **Буква `ё`** в именах метаданных в примерах — допустима только в пользовательских текстах (синонимах), не в коде/именах.
- **`description` ≤1024 символа** (хард-лимит ZCode), но **главное — в первых ~250** (это влияет на триггер).
- **Ссылки на стандарты** — на `https://github.com/zeegin/v8std/blob/main/docs/std/NNN.md`.
- **Cross-skill ссылки** — текстовым упоминанием «скил `1c-<имя>`» или «скил `1c-<имя>` → `<reference>`». Не ссылками `../<name>.md` (скилы — это каталоги, не `.md`-файлы).
- **Ссылки на `std/`** — относительно: из `skills/<name>/references/foo.md` → `../../../std/<file>.md` (3 уровня вверх до корня).

## Синхронизация с upstream

Источники контента (см. [`docs/SOURCES.md`](./docs/SOURCES.md)):

- **`zeegin/v8std`** — стандарты. Наши карточки — **адаптация**, не копия. При изменении upstream: прочитайте diff стандарта, внесите правки в `references/<card>.md`, сохраняя структуру мини-сводки. Запишите в `CHANGELOG.md` со ссылкой на коммит upstream. Расхождение оглавления `std/` с upstream отслеживается автоматически — workflow `upstream-sync` раз в квартал открывает Issue при дивергенции (локально: `python3 scripts/check_upstream_std.py`).
- **`comol/ai_rules_1c`** — practice (public domain). Аналогично.
- **`Nikolay-Shirokov/cc-1c-skills`** — спецификации форматов. Используем как есть, со ссылкой.

## Каталог checkbsl (генерируемый)

`skills/1c-code-review/references/checkbsl/{index,code,query,metadata}.md` —
генерируемый каталог правил checkbsl.org (SonarQube 1C (BSL) Plugin):
ключ, название, суть, ссылки на стандарты v8std и пометка аудита безопасности. Файлы помечены генератором и датой — **не правятся
руками**, только перегенерацией:

```bash
python3 scripts/harvest_checkbsl.py   # нужна сеть
```

Когда перегенерировать: при обновлении правил на docs.checkbsl.org или при
смене структуры каталога. После перегенерации — прогон
`python3 scripts/validate_skills.py`.

## Версионирование

- `plugin.json` → `version` (SemVer).
- **patch** — исправление опечатки/неточности в существующем правиле.
- **minor** — новый скил, новая карточка в references, расширение правила.
- **major** — обратно-несовместимое изменение (удаление скила, смена формата).
- **Версия видна пользователю:** в заголовке H1 README («`# <имя> — X.Y.Z»),
  бейдже в шапке и строке статуса («`**Текущий: ✅ vX.Y.Z**`» в разделе
  «Статус и roadmap»). `bump-version.sh` обновляет все три атомарно вместе с
  манифестами; README без версии в H1/бейдже/статусе — ошибка (рассинхрон).
  Руками версия в README не правится — только скриптом.
- Синхронность версий во всех местах проверяется в CI скриптом
  `scripts/check_version_sync.py` (запускается на каждый push/PR).
