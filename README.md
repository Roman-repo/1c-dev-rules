## Что это и зачем

При разработке 1С ИИ-ассистент часто пишет «правдоподобный, но не по стандартам» код: `СрезПоследних` без параметров, чтение внутри транзакции, новый объект без ролей, плейсхолдеры вместо UUID. Этот набор заставляет ИИ **применять стандарты на лету** — через скилы, которые триггерятся по типу задачи и показывают конкретные правила.

**Главное:** это не справочник «почитать» — это набор, который **автоматически активируется** в контексте задачи. Модель видит описание скила в system-reminder и открывает его, когда задача подходит.

## Чем это отличается от существующего

| Источник | Что это | Чем данный набор отличается |
|---|---|---|
| [zeegin/v8std](https://github.com/zeegin/v8std) | ~360 стандартов разработки 1С как текст | Данный набор — **скилы**, адаптированные для триггеров ИИ: мини-сводка + чек-листы + примеры неправильно/правильно |
| [comol/ai_rules_1c](https://github.com/comol/ai_rules_1c) | Practice-карточки (public domain) | Переработаны: очищены от проектной специфики, перекрыты ссылками на v8std, добавлены мини-чек-листы |
| [cc-1c-skills](https://github.com/Nikolay-Shirokov/cc-1c-skills) | Спецификации форматов 1С | Используются как первоисточник для скилов метаданных/ParentConfigurations |

**Кратко:** v8std говорит «что правильно», `ai_rules_1c` — «как писать», а этот набор — **«как ИИ-ассистенту применять это на лету»** через механизм скилов.

## Что внутри

**30 скилов** + 49 карточек-ссылок + 14 оглавлений и индекс стандартов v8std покрывают весь цикл доставки задачи 1С — от постановки до релиза:

### 🚚 Конвейер разработки

| Скил | Назначение |
|---|---|
| `1c-epic-planning` | ⛰️ **Уровень над конвейером — эпик**: инициатива дороже одной задачи. Декомпозиция на задачи по лимиту размера, вертикальные срезы (работающая функциональность как можно раньше), rolling wave (детально только ближайшие 1–2 задачи). Карточка эпика `00-epic-brief.md` |
| `1c-delivery-gate` | 🚪 **Маршрутизатор конвейера разработки** (жизненного цикла задачи): Планирование → Проектирование → **Согласование** → Разработка → Внутренняя приёмка → Внешняя приёмка → Релиз. | `1c-planning` | Этап «Планирование» (роль: РП): карточка задачи — проблема, цель, измеримые критерии успеха, рамки «что НЕ делаем», оценка S/M/L + лимит размера задачи для одного ИИ-прохода (~7 файлов; крупнее — эпик) |
| `1c-solution-design` | Этап «Проектирование» (архитектор + аналитик): Сценарий исполнения (роль-шаг-триггер-описание-результат + отклонения), Спецификация изменений (+arch-checklist, +ADR для развилок с долгими последствиями), Критерии приёмки с матрицей трассировки; выход — передача пакета на согласование (этап 3) |
| `1c-dispatch-gate` | Этап «Разработка» (роль: разработчик): 🚪 маршрутизатор правил разработки — гейт-чек-лист до кода (новый объект, форма, XML, проведение, запросы) + таблицы «тип работы → скилы» и «сигнал в коде → карточки»; сверка плана изменений с границами 03 (выход за список — стоп-вопрос); также точка входа для любой работы над кодом/ревью вне полного цикла задачи |
| `1c-internal-acceptance` | Этап «Внутренняя приёмка» (разработчик-тестировщик): прогон каждого шага сценария с evidence, отчёт приёмки |
| `1c-external-acceptance` | Этап «Внешняя приёмка» (приёмщик-инициатор): протокол по критериям, лист возврата с классами A/B/C/D; «возврат ≠ расширение рамок» |
| `1c-release` | Этап «Релиз» (РП/релиз-инженер): состав из принятых задач, свод миграций, примечания пользователям и админам |

>
> 🎚️ Этап «Согласование» (3): после подготовки пакета 02/03/04 Исполнитель в режиме **manual** (по умолчанию) останавливается и ждёт решения Оркестратора (лист замечаний 04a), в режиме **auto** решение фиксируется автоматически. Управление — команды плагина `/auto` и `/manual` (пишут `<каталог доставки>/_conveyor-mode.md`); нет файла — действует manual. ## Как это работает на практике

Пример сессии в ZCode после установки:

```
Вы: Создай в конфигурации новый регистр сведений «ИсторияСогласований»

[ZCode видит в system-reminder скил 1c-dispatch-gate, срабатывает
 триггер «создаётся новый объект метаданных» → открывает скил]
  ↓
1c-dispatch-gate → гейт-чек-лист: «новый объект → 1c-metadata + 1c-security»
  ↓
1c-metadata: проверяет UUID (случайные, включая producedTypes),
             структуру модуля, синоним ru/en
1c-security: напоминает про №532 — включить в роль, даёт grep-проверку
  ↓
ИИ создаёт .mdo по правилам, а не «наугад»
```

Аналогично при ревью: стоит `Попытка/Исключение` без лога → `1c-thin-triggers` подсвечивает, `1c-logging` даёт шаблон с `ЗаписьЖурналаРегистрации`.

## Как подключить

### Вариант 1 — плагин с GitHub (основной, ZCode)

1. В ZCode: **Settings → Plugin Management → Discover → `+`**
2. Вставьте URL: `https://github.com/Roman-repo/1c-dev-rules`
3. **Install** — плагин включён по умолчанию, все 30 скилов сразу появятся в system-reminder

### Вариант 2 — как marketplace (удобно для команды)

Тот же URL подключается как marketplace (в репозитории есть `marketplace.json`), после чего плагины из него ставятся одним кликом. Удобно, если планируете развивать несколько плагинов.

### Вариант 3 — локальная разработка/тестирование

```bash
git clone https://github.com/Roman-repo/1c-dev-rules ~/Projects/1c-dev-rules
```

В `~/.zcode/cli/config.json` добавьте путь в `plugins.dirs`:
```json
{
  "plugins": {
    "enabled": true,
    "dirs": ["~/Projects/1c-dev-rules"]
  }
}
```

### Вариант 4 — Kimi (Kimi Work)

В репозитории есть манифест `kimi.plugin.json` — плагин можно зарегистрировать в личном маркете Kimi:

1. Скопируйте корень репозитория в рабочую папку сессии Kimi (требование личного маркета: корень плагина должен лежать внутри workspace) — например `~/Documents/kimi/workspace/1c-dev-rules`
2. Попросите агента зарегистрировать плагин («зарегистрируй плагин из 1c-dev-rules») — регистрация проверит `kimi.plugin.json` и добавит плагин в личный маркет
3. Установите плагин со страницы плагинов — все 30 скилов `1c-*` появятся в индексе скилов

Обновление версии: скопируйте свежую версию в workspace и повторите регистрацию/установку (git-pull установленного плагина Kimi не делает — как и ZCode).

> ⚠️ Триггерные слова скилов продублированы в `description` — роутер Kimi отбирает скилы по `description`, поле `when_to_use` (ZCode) он не читает. Команды `/auto` и `/manual` в Kimi недоступны — режим согласования конвейера переключается правкой `docs/delivery/_conveyor-mode.md` (см. [«Режимы согласования конвейера»](#режимы-согласования-конвейера-auto-и-manual)).

## Режимы согласования конвейера (`/auto` и `/manual`)

Конвейер — работа трёх участников: **Постановщик** (инициатор задачи), **Оркестратор** (координирует исполнение; сегодня человек, с ростом возможностей ИИ — потенциально агент) и **Исполнитель** (ИИ-агент, проходит этапы конвейера). Ключевая точка живого контроля — **этап 3 «Согласование»**: подготовленный пакет документации (сценарий `02` + спецификация `03` + критерии приёмки `04`) проходит решение Оркестратора **до первой строки кода** — чтобы не оказалось «разработка по несмотренному чертежу». Режим определяет, как именно проходит этап.

| Режим | Поведение на гейте 2→3 |
|---|---|
| **`manual`** (по умолчанию) | После подготовки 02/03/04 Исполнитель **останавливается** и предъявляет Оркестратору сводку пакета: сценарий (основной путь + отклонения), границы спецификации, ключевые критерии приёмки, развилки ADR. «Согласовано» → «Разработка». «Доработать» → лист замечаний с адресом возврата: этап 2 (правка 02/03/04) или этап 1 (до-сбор требований), повторное согласование. 🔴 Код до решения не пишется |
| **`auto`** | Лист замечаний создаётся автоматически с решением «Согласовано», пометкой режима и датой — конвейер идёт без остановки. Ответственность за пропуск живого согласования — на Оркестраторе, включившем режим |

### Как переключить

**В ZCode** — команды плагина (появляются после установки; пишут файл `<каталог доставки>/_conveyor-mode.md`, по умолчанию `docs/delivery/`):

```
/auto      ← конвейер без остановок (автосогласование пакета)
/manual    ← остановка на согласовании пакета (дефолт)
```

**Без ZCode** (Kimi Work, Claude Code и др. — механизма команд нет) — создайте или отредактируйте файл вручную:

```markdown
<!-- Режим конвейера разработки (1c-dev-rules). Управляется /auto и /manual. -->
mode: auto        # или manual
updated: 2026-08-23
```

- Файла нет — действует **manual** (безопасный дефолт: новый пользователь получает остановку, а не тихий проезд в код).
- Режим относится ко **всему каталогу доставки** (всем его задачам) и персистентен между сессиями.

### Где видно состояние

Факт согласования — **лист замечаний `04a-design-review.md`** в каталоге задачи (решение, режим, кто, дата, замечания с адресом возврата, история раундов). Сверка скриптом:

```bash
python3 scripts/delivery_tools.py status <каталог задачи>   # строка «Согласование 04: …»
python3 scripts/delivery_tools.py check  <каталог задачи>   # гейт 3→4: нет 04a → WARN, «Доработать» при начатом коде → ERR
```

Задачи, начатые до 0.19.0 (этапа согласования ещё не было), получают **WARN без блокировки** — задним числом конвейер не останавливается; при желании Оркестратор создаёт 04a задним числом. Штамп 0.18.0 в секции 04 читается как legacy-источник.

## Другие ассистенты (Claude Code, Codex, Cursor)

Плагин оформлен в формате ZCode (`.zcode-plugin/plugin.json`). Для других ассистентов есть два пути:

**Быстрый (копирование скилов):** скопируйте каталоги из `skills/*/` в `.agents/skills/` вашего проекта — этот путь понимают Claude Code и Codex, а также ZCode (как workspace-scope). `SKILL.md` — это markdown с YAML frontmatter, формат совместимый.

**Адаптация манифеста:** ZCode принимает альтернативные имена каталога манифеста — `.claude-plugin/`, `.codex-plugin/`, `.cursor-plugin/`. Можно сделать символическую ссылку или скопировать `plugin.json` под нужным именем.

> ⚠️ На сегодня **протестировано в ZCode и Kimi** (для Kimi есть штатный манифест `kimi.plugin.json` — см. «Вариант 4»). Для Claude Code/Codex/Cursor формальная совместимость есть, но триггеры не проверялись в реальных клиентах.

## Архитектура и пример скила

```
1c-dev-rules/
├── .zcode-plugin/plugin.json   ← манифест плагина ZCode
├── kimi.plugin.json            ← манифест плагина Kimi (версия бампится тем же bump-version.sh)
├── skills/                     ← 30 скилов (каждый = каталог)
│   └── <name>/
│       ├── SKILL.md            ← frontmatter + мини-сводка (≤500 строк)
│       └── references/*.md     ← полные карточки и шаблоны артефактов, progressive disclosure
├── scripts/                    ← delivery_tools.py (конвейер), validate-new-object.sh (X1–X15), validate_skills.py, bump-version.sh
├── commands/                   ← команды плагина: /auto и /manual (режим согласования конвейера)
├── std/                        ← 14 оглавлений v8std + индекс (справочный слой)
└── docs/                       ← ARCHITECTURE, SOURCES, CHANGELOG
```

Принцип: **универсальные правила здесь, проектная специфика — в `AGENTS.md` проекта**. Скилы не содержат упоминаний конкретных конфигураций (`торо_`, `Project/Toir`) — только универсальные правила и примеры.

```markdown

  query/DCS/dynamic-list code: №733 (СрезПоследних с параметрами), №655 (нет ВТ
  в соединении). Мини-чек-лист в конце.

---

# 1c-queries — запросы, СКД

## Краткая сводка критичных правил
...мини-сводка стандартов...
```

Правила оформления скилов (поля frontmatter, длина description, очистка от проектной специфики) — в [docs/ARCHITECTURE.md](./docs/ARCHITECTURE.md).

## Если что-то не работает (FAQ)

### Поставил плагин, а скилы не появились в system-reminder

1. **Проверьте, что плагин включён:** Settings → Plugin Management — должен быть в списке со статусом enabled.
2. **Запустите диагностику ZCode:**
   - `/zcode-guide:diagnosing-plugins` — корректность установки плагина (манифест, путь, включён ли).
   - `/zcode-guide:diagnosing-skills` — корректность обнаружения скилов (frontmatter, `description` ≤1024 симв., `name` совпадает с каталогом).
3. **Перезапустите сессию** — список скилов строится в начале хода; после установки нового плагина нужен новый сеанс.
4. **Проверьте права:** плагин должен быть включён для текущего workspace или глобально (см. `~/.zcode/cli/config.json` → `plugins.enabledPlugins`).

### Скилы появляются, но не триггерятся автоматически

- `description` — главный триггер. Если скил under-triggers, проверьте, что описание начинается с «Use when…» и содержит конкретные сигналы. Лимит — первые ~250 символов; всё важное должно быть в начале.
- Можно вызвать скил явно: `/1c-queries` или через меню `/` → Skills.

### Скил загрузился, но контент не соответствует моему проекту

Это задумка: скилы **универсальны** (без привязки к конкретной конфигурации). Проектная специфика (префикс, карты объектов, каноничные чтения) должна лежать в `AGENTS.md` вашего проекта. Сгенерировать его: `/1c-project-bootstrap`.

### Хочу отключить часть скилов

В `~/.zcode/cli/config.json` → `plugins.enabledPlugins` укажите плагин как `false`, либо используйте UI: Settings → Plugin Management → отключить.
