## Что это и зачем

При разработке 1С ИИ-ассистент часто пишет «правдоподобный, но не по стандартам» код: `СрезПоследних` без параметров, чтение внутри транзакции, новый объект без ролей, плейсхолдеры вместо UUID. Этот набор заставляет ИИ **применять стандарты на лету** — через скилы, которые триггерятся по типу задачи и показывают конкретные правила.

Плагин закрывает три задачи команды разработки 1С:

1. **Качество кода по стандартам** — 30 тематических скилов (запросы, формы, метаданные, транзакции, права, интеграция, тесты…) автоматически активируются в контексте задачи: модель видит описание скила в system-reminder и открывает его, когда задача подходит. Каждый скил — мини-сводка критичных правил + чек-лист + карточки «неправильно/правильно» в `references/`.
2. **Управляемый процесс доставки задачи** — конвейер полного жизненного цикла: Планирование → Проектирование → Согласование → Разработка → Внутренняя приёмка → Код ревью → Внешняя приёмка → Релиз (плюс уровень эпиков). Каждый этап оставляет артефакт в `docs/delivery/<ID-задачи>/` (карточка, сценарий, спецификация, листы замечаний 04a/05a, протоколы), а живые гейты — согласование документации и код ревью — проходят в режиме `manual` (стоп до решения человека) или `auto` (команды `/manual` `/auto`).
3. **Детерминированная проверка кода инструментами, а не «глазами»** — этап «Код ревью» опирается на три автоматических слоя: regex-сканер `checkbsl_scan.py`, AST-анализатор `bsl_ls_analyze.py` (bsl-language-server; вместе — 135 из 322 правил каталога checkbsl, 41,9%, счётчик: `python3 scripts/bsl_ls_analyze.py --coverage-report`) и metadata-слой `metadata_scan.py` (XML метаданных `.mdo`/`.rights` из диффа: 16 каталогных metadata-ключей + 15 структурных, без Java, счётчик `--coverage-report`). Одинаковый вход → одинаковые замечания независимо от модели и настроения: отчёты «код + что не так + как правильно» пишутся в каталог задачи, а петля «правка → повторный прогон» идёт до чистого результата по 🔴. Плюс валидаторы: формовые цепочки и вызов metadata-слоя (`validate-new-object.sh`), структура скилов, механическая сверка артефактов конвейера (`delivery_tools.py`).

**Главное:** это не справочник «почитать» — это набор, который **автоматически активируется** в контексте задачи и **проверяет результат инструментально**. Универсальные правила живут в плагине, проектная специфика (префиксы, карты объектов) — в `AGENTS.md` вашего проекта (генерируется командой `/1c-project-bootstrap`).

## Чем это отличается от существующего

| Источник | Что это | Чем данный набор отличается |
|---|---|---|
| [zeegin/v8std](https://github.com/zeegin/v8std) | ~360 стандартов разработки 1С как текст | Данный набор — **скилы**, адаптированные для триггеров ИИ: мини-сводка + чек-листы + примеры неправильно/правильно |
| [comol/ai_rules_1c](https://github.com/comol/ai_rules_1c) | Practice-карточки (public domain) | Переработаны: очищены от проектной специфики, перекрыты ссылками на v8std, добавлены мини-чек-листы |
| [cc-1c-skills](https://github.com/Nikolay-Shirokov/cc-1c-skills) | Спецификации форматов 1С | Используются как первоисточник для скилов метаданных/ParentConfigurations |

**Кратко:** v8std говорит «что правильно», `ai_rules_1c` — «как писать», а этот набор — **«как ИИ-ассистенту применять это на лету»** через механизм скилов.

## Что внутри

**30 скилов** + 56 карточек-ссылок + 14 оглавлений и индекс стандартов v8std покрывают весь цикл доставки задачи 1С — от постановки до релиза (включая каталог правил код ревью checkbsl):

### 🚚 Конвейер разработки

| Скил | Назначение |
|---|---|
| `1c-epic-planning` | ⛰️ **Уровень над конвейером — эпик**: инициатива дороже одной задачи. Декомпозиция на задачи по лимиту размера, вертикальные срезы (работающая функциональность как можно раньше), rolling wave (детально только ближайшие 1–2 задачи). Карточка эпика `00-epic-brief.md` |
| `1c-delivery-gate` | 🚪 **Маршрутизатор конвейера разработки** (жизненного цикла задачи): Планирование → Проектирование → **Согласование** → Разработка → Внутренняя приёмка → **Код ревью** → Внешняя приёмка → Релиз. Роли участников (Постановщик / Оркестратор / Исполнитель / Ревьюер), обязательные артефакты этапов, DoD-гейты переходов (включая согласование документации с Оркестратором — лист замечаний 04a — и код ревью — лист 05a; режимы `manual`/`auto`), классификация возвратов (A/B/C/D) |
| `1c-planning` | Этап «Планирование» (роль: РП): карточка задачи — проблема («как сейчас / недостатки / желаемое»), цель с бизнес-ценностью «базовая → целевая метрика», измеримые критерии успеха, рамки «что НЕ делаем», оценка S/M/L + лимит размера (~7 файлов; крупнее — эпик); DoR-чек-лист готовности постановки (`references/dor-checklist.md`) |
| `1c-solution-design` | Этап «Проектирование» (архитектор + аналитик): Сценарий исполнения (роль-шаг-триггер-описание-результат + отклонения), Спецификация изменений (+arch-checklist, +ADR для развилок с долгими последствиями), Критерии приёмки с матрицей трассировки, НФТ-блок спецификации (совместимость/объёмы/регрессия/отказоустойчивость) и макеты новых форм; выход — передача пакета на согласование (этап 3) |
| `1c-dispatch-gate` | Этап «Разработка» (роль: разработчик): 🚪 маршрутизатор правил разработки — гейт-чек-лист до кода (новый объект, форма, XML, проведение, запросы) + таблицы «тип работы → скилы» и «сигнал в коде → карточки»; сверка плана изменений с границами 03 (выход за список — стоп-вопрос); также точка входа для любой работы над кодом/ревью вне полного цикла задачи |
| `1c-internal-acceptance` | Этап «Внутренняя приёмка» (разработчик-тестировщик): прогон каждого шага сценария с evidence, отчёт приёмки |
| `1c-code-review` | Этап «Код ревью» (Ревьюер): два детерминированных слоя (`checkbsl_scan.py` — regex, 22 ключа; `bsl_ls_analyze.py` — bsl-language-server CLI, 129 ключей + 17 локальных карточек немапленных 🔴-диагностик; вместе 135/322 — 41,9%, счётчик `--coverage-report`) + чек-лист по секциям + полный каталог правил checkbsl (код 256 / запросы 34 / метаданные 32, аудит-Б); петля самоочистки по отчётам (`code-review/` в каталоге задачи) до чистого по 🔴; решение в листе 05a «Одобрено»/«Доработать» |
| `1c-external-acceptance` | Этап «Внешняя приёмка» (приёмщик-инициатор): протокол по критериям, лист возврата с классами A/B/C/D; «возврат ≠ расширение рамок» |
| `1c-release` | Этап «Релиз» (РП/релиз-инженер): состав из принятых задач, свод миграций, примечания пользователям и админам |

> ⚙️ Механическая сверка конвейера: `scripts/delivery_tools.py` по артефактам задачи 01–06 — `status` (этап, статусы матрицы, согласование Оркестратора, код ревью, решение протокола, следующий шаг), `check` (прогон DoD-гейтов; ERR — блокирующее нарушение) и `roadmap <каталог доставки>` (сводка всех задач и эпиков: этап конвейера каждой задачи, связь с эпиками).
>
> 🎚️ Живые гейты конвейера — «Согласование» (3) и «Код ревью» (6): в режиме **manual** (по умолчанию) Исполнитель останавливается — после пакета 02/03/04 ждёт решения Оркестратора (лист замечаний 04a), после чистого 05 передаёт код Ревьюеру (лист 05a); в режиме **auto** решения фиксируются автоматически. Управление — команды плагина `/auto` и `/manual` (пишут `<каталог доставки>/_conveyor-mode.md`, один файл на оба гейта); нет файла — действует manual. Подробная инструкция — [«Режимы согласования конвейера»](#режимы-согласования-конвейера-auto-и-manual).

Пример сессии в ZCode после установки:

```

[ZCode видит в system-reminder скил 1c-dispatch-gate, срабатывает

  ↓

  ↓

```

Аналогично при ревью: стоит `Попытка/Исключение` без лога → `1c-thin-triggers` подсвечивает, `1c-logging` даёт шаблон с `ЗаписьЖурналаРегистрации`.

### Типовые сценарии использования

**Полный цикл задачи (конвейер).** Скажите: «возьми задачу <описание> по конвейеру». Агент пройдёт этапы и оставит артефакты в `docs/delivery/<ID>/`: карточку `01` (проблема → цель с метрикой), пакет проектирования `02/03/04` (остановится на согласовании — лист `04a`), код, отчёт внутренней приёмки `05`, на код-ревью — отчёты анализаторов `code-review/` и лист `05a`, протокол `06`. Контроль процесса:

```bash
python3 scripts/delivery_tools.py status   # этап задачи, статусы, следующий шаг
python3 scripts/delivery_tools.py check    # прогон DoD-гейтов (ERR — блокеры)
python3 scripts/delivery_tools.py roadmap docs/delivery  # все задачи и эпики
```

**Точечная разработка или ревью вне полного цикла.** Точка входа — скил `1c-dispatch-gate`: он сам открывает нужные скилы по типу работы («новый объект», «форма», «проведение», «запрос») и гоняет гейт-чек-лист до кода.

**Код-ревью с анализатором.** На этапе 6 (или по запросу «прогони ревью диффа») агент вызывает детерминированные слои на диффе задачи:

```bash
python3 scripts/checkbsl_scan.py --diff main        # regex-слой, ~22 правила
python3 scripts/bsl_ls_analyze.py --diff main --src-root <корень src EDT> \
  --report docs/delivery/<ЗАДАЧА>/code-review/bsl-ls-r1.md   # AST-слой, отчёт петли
```

🔴 в отчёте → возврат в разработку, правка по «как правильно», повторный прогон `r2` — пока не чисто. На больших конфигурациях добавьте `--slim-config --cache-dir .cache/bsl-ls` (см. [«Настройка анализатора кода (BSL LS)»](#настройка-анализатора-кода-bsl-ls--опционально)).

**Явные вызовы.** Любой скил можно открыть вручную: `/1c-queries`, `/1c-forms` и т.д. Команды плагина: `/auto` и `/manual` — режим живых гейтов конвейера; `/1c-project-bootstrap` — онбординг нового проекта (генерация `AGENTS.md`). Ручная правка XML метаданных без EDT — после неё `bash scripts/validate-new-object.sh` (кросс-файловые цепочки X1–X15: UUID, роли, подсистемы, обработчики).

## Настройка анализатора кода (BSL LS) — опционально

Этап 6 «Код ревью» работает в три детерминированных слоя: regex-сканер `checkbsl_scan.py` (22 правила, без зависимостей), AST-анализатор `bsl_ls_analyze.py` — обёртка **bsl-language-server** (129/322 правил checkbsl — 40%: запросы, транзакции, устаревшие методы, сложность, области) и metadata-слой `metadata_scan.py` (XML метаданных `.mdo`/`.rights` — синонимы №474, «ё», пароли №740, роли №532, обязательные роли, UUID-коллизии, обработчики РЗ/подписок, СКД; 16 каталогных ключей + 15 локальных структурных; Java не нужна):

```
python3 scripts/metadata_scan.py --diff main --src-root <корень src EDT>   # объекты из диффа
python3 scripts/metadata_scan.py --coverage-report                          # metadata: 16/32
```

Второму слою нужны Java и jar — настраивается один раз:

**Шаг 1. Установите Java 21+**

- macOS: `brew install openjdk` (пакет keg-only, в PATH не попадает — обёртка сама ищет его в `/opt/homebrew/opt/openjdk`)
- Windows/Linux: [Temurin 21](https://adoptium.net) или любой JDK 21+
- Проверка: `java -version`
- Java в нестандартном месте → укажите путь в переменной `BSL_LS_JAVA`

> ⚠️ Нужна именно 21+: exec.jar 1.0.7 на JDK 17 падает при запуске (Spring Boot launcher, Class.forName) — воспроизведено в CI.

**Шаг 2. Скачайте jar bsl-language-server**

1. Откройте [последний релиз](https://github.com/1c-syntax/bsl-language-server/releases/latest) и скачайте `bsl-language-server-<версия>-exec.jar` (~124 МБ; имя ассета версионировано, прямой ссылки «latest/download» нет)
2. Положите в `~/.local/share/1c-dev-rules/bsl-language-server.jar` (рекомендуемое место). Альтернативы: каталог `.tools/` в корне репозитория плагина или путь в переменной `BSL_LS_JAR`

**Шаг 3. Проверьте**

```bash
python3 scripts/bsl_ls_analyze.py --help     # справка по флагам
python3 scripts/bsl_ls_analyze.py <файл.bsl> # живой прогон на модуле
```

Если Java или jar не найдены — слой честно сообщает об этом (exit 3) и ревью идёт сканером + ручным проходом: плагин работоспособен и без этой настройки.

**Как это используется дальше.** Ничего вызывать вручную не нужно: на этапе 6 агент сам прогоняет анализатор на диффе задачи (`--diff main`) и пишет отчёт ревью в `docs/delivery/<ЗАДАЧА>/code-review/bsl-ls-r<N>.md` (петля «правка → повторный прогон», пока не чисто по 🔴). Нюансы для больших конфигураций:

- `--src-root <корень src EDT>` — корень исходников конфигурации (с `Configuration.mdo`): без него AST не разбирает запросы к метаданным; BSL LS анализирует всё дерево srcDir, а в отчёт попадают только изменённые строки диффа
- `--slim-config` — анализ только диагностик каталога checkbsl: быстрее, шум 🟡 без привязки к каталогу уходит
- `--cache-dir .cache/bsl-ls` — повторный прогон петли без правок мгновенный (кэш по хэшу входов)
- `--timeout` (дефолт 900 с), `--no-line-filter` — см. `--help`

### Потолок детерминированных слоёв

Текущее покрытие каталога checkbsl: **вместе 135/322 — 41,9%** (счётчик: `python3 scripts/bsl_ls_analyze.py --coverage-report`, без Java). Структурный потолок связки regex+AST — оценка **≈187 ключей (58%)**: overall ~136, metadata ~28, query ~23 (диагностика пользователя 2026-08-31). Остальные правила требуют данных вне текста модуля и его AST — XML метаданных (`.mdo`), права (`.rights`), межфайловые цепочки. Два следствия зафиксированы честно:

- **рост — не алиасы, а источники**: metadata-слой `scripts/metadata_scan.py` реализован (META-001, 0.32.0) — 16/32 каталогных metadata-ключей детерминированно по `.mdo`/`.rights` из диффа (было 4/32); вливание в общий счётчик обёртки и остальные 12 ключей (режимы конфигурации, полный обход ролей, существующие объекты) — задачи META-002..005 эпика [docs/delivery/EP-001-METADATA-LAYER/](docs/delivery/EP-001-METADATA-LAYER/00-epic-brief.md);
- **слепоты по блокирующим нет**: все немапленные 🔴-диагностики BSL LS (важность Блокирующий/Критичный) закрыты локальными карточками `LOCAL_CATALOG` в `bsl_ls_analyze.py` — находка получает № стандарта и «что не так / как правильно» из базы fixes, ссылка ведёт на документацию BSL LS; slim-конфиг их не отключает; целостность держит `check_bsl_ls_drift.py` (замок «карточка + fixes», отрабатывает и в CI, и в квартальной сверке).

## Режимы согласования конвейера (`/auto` и `/manual`)

Конвейер — работа четырёх участников: **Постановщик** (инициатор задачи), **Оркестратор** (координирует исполнение; сегодня человек, с ростом возможностей ИИ — потенциально агент), **Исполнитель** (ИИ-агент, проходит этапы конвейера) и **Ревьюер** (второй программист / техлид; проверяет код на стандарты). Две точки живого контроля: **этап 3 «Согласование»** — подготовленный пакет документации (сценарий `02` + спецификация `03` + критерии приёмки `04`) проходит решение Оркестратора **до первой строки кода** — чтобы не оказалось «разработка по несмотренному чертежу»; и **этап 6 «Код ревью»** — код после чистой внутренней приёмки проверяется Ревьюером **до демонстрации заказчику** (петля самоочистки на детерминированных слоях — `checkbsl_scan.py` + `bsl_ls_analyze.py` с отчётами-замечаниями в `code-review/` — затем чек-лист `1c-code-review` + каталог правил checkbsl, решение в листе `05a-code-review.md`). Режим определяет, как именно проходят оба гейта.

| Режим | Поведение на живых гейтах (3→4 и 6→7) |
|---|---|
| **`manual`** (по умолчанию) | После подготовки 02/03/04 Исполнитель **останавливается** и предъявляет Оркестратору сводку пакета: сценарий (основной путь + отклонения), границы спецификации, ключевые критерии приёмки, развилки ADR. «Согласовано» → «Разработка». «Доработать» → лист замечаний с адресом возврата: этап 2 (правка 02/03/04) или этап 1 (до-сбор требований), повторное согласование. 🔴 Код до решения не пишется. После чистого 05 — **петля самоочистки код ревью** (0.25.1): анализаторы на диффе задачи с отчётами в `code-review/`; 🔴 → возврат на этап 4, правка по листу замечаний, повторный прогон r<N+1> до чистого; затем Исполнитель **останавливается** и передаёт код Ревьюеру; «Одобрено» → внешняя приёмка, «Доработать» → возврат на этап 4, повтор затронутых проверок и ревью. 🔴 Внешняя приёмка до «Одобрено» не начинается |
| **`auto`** | Оба листа (04a, 05a) создаются автоматически с положительным решением, пометкой режима и датой — конвейер идёт без остановки. Ответственность за пропуск живого контроля — на Оркестраторе, включившем режим |

### Как переключить

**В ZCode** — команды плагина (появляются после установки; пишут файл `<каталог доставки>/_conveyor-mode.md`, по умолчанию `docs/delivery/`):

```
/auto      ← конвейер без остановок (автосогласование пакета и автокод-ревью)
/manual    ← остановки на согласовании пакета и код ревью (дефолт)
```

**Без ZCode** (Kimi Work, Claude Code и др. — механизма команд нет) — создайте или отредактируйте файл вручную:

```markdown
<!-- Режим конвейера разработки (1c-dev-rules). Управляется /auto и /manual. -->
mode: auto        # или manual
updated: 2026-08-23
```

- Файла нет — действует **manual** (безопасный дефолт: новый пользователь получает остановку, а не тихий проезд в код).
- Режим относится ко **всему каталогу доставки** (всем его задачам), действует на оба живых гейта и персистентен между сессиями.

### Где видно состояние

Факты живых гейтов — **лист замечаний `04a-design-review.md`** (согласование) и **лист код-ревью `05a-code-review.md`** в каталоге задачи (решение, режим, кто, дата, замечания, история раундов). Сверка скриптом:

```bash
python3 scripts/delivery_tools.py status <каталог задачи>   # строки «Согласование: …» и «Код ревью: …»
python3 scripts/delivery_tools.py check  <каталог задачи>   # гейт 3→4: нет 04a → WARN; гейт 6→7: нет 05a → WARN, «Доработать» при начатой внешней приёмке → ERR
```

Задачи, начатые до введения живого гейта (до 0.19.0 — согласование, до 0.23.0 — код ревью), получают **WARN без блокировки** — задним числом конвейер не останавливается; при желании Оркестратор/Ревьюер создаёт лист задним числом. Штамп согласования 0.18.0 в секции 04 читается как legacy-источник; строка «code-review ✅» в шапке 05 — самопрогон разработки (гейт 4→5), решением Ревьюера не считается.

## Другие ассистенты (Claude Code, Codex, Cursor)

Плагин оформлен в формате ZCode (`.zcode-plugin/plugin.json`). Для других ассистентов есть два пути:

**Быстрый (копирование скилов):** скопируйте каталоги из `skills/*/` в `.agents/skills/` вашего проекта — этот путь понимают Claude Code и Codex, а также ZCode (как workspace-scope). `SKILL.md` — это markdown с YAML frontmatter, формат совместимый.

**Адаптация манифеста:** ZCode принимает альтернативные имена каталога манифеста — `.claude-plugin/`, `.codex-plugin/`, `.cursor-plugin/`. Можно сделать символическую ссылку или скопировать `plugin.json` под нужным именем.

> ⚠️ На сегодня **протестировано в ZCode и Kimi** (для Kimi есть штатный манифест `kimi.plugin.json` — см. «Вариант 4»). Для Claude Code/Codex/Cursor формальная совместимость есть, но триггеры не проверялись в реальных клиентах.

├── scripts/                    ← инструменты: checkbsl_scan.py + bsl_ls_analyze.py (слои код-ревью),
│                                 delivery_tools.py (конвейер), validate-new-object.sh (X1–X15),

## Если что-то не работает (FAQ)

### Поставил плагин, а скилы не появились в system-reminder

1. **Проверьте, что плагин включён:** Settings → Plugin Management — должен быть в списке со статусом enabled.
2. **Запустите диагностику ZCode:**
   - `/zcode-guide:diagnosing-plugins` — корректность установки плагина (манифест, путь, включён ли).
   - `/zcode-guide:diagnosing-skills` — корректность обнаружения скилов (frontmatter, `description` ≤1024 симв., `name` совпадает с каталогом).
3. **Перезапустите сессию** — список скилов строится в начале хода; после установки нового плагина нужен новый сеанс.
4. **Проверьте права:** плагин должен быть включён для текущего workspace или глобально (см. `~/.zcode/cli/config.json` → `plugins.enabledPlugins`).

### Скилы появляются, но не триггерятся автоматически

- `description` — главный триггер. Если скил under-triggers, проверьте, что описание начинается с «Use when…» и содержит конкретные сигналы. Лимит — первые ~250 символов; всё важное должно быть в начале.
- Можно вызвать скил явно: `/1c-queries` или через меню `/` → Skills.

### Скил загрузился, но контент не соответствует моему проекту

Это задумка: скилы **универсальны** (без привязки к конкретной конфигурации). Проектная специфика (префикс, карты объектов, каноничные чтения) должна лежать в `AGENTS.md` вашего проекта. Сгенерировать его: `/1c-project-bootstrap`.

### Хочу отключить часть скилов

В `~/.zcode/cli/config.json` → `plugins.enabledPlugins` укажите плагин как `false`, либо используйте UI: Settings → Plugin Management → отключить.
