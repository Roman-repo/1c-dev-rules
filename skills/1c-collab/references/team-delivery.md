# Командная разработка и поставка 1С — полная карточка

> Скил `1c-collab` — выжимка. Здесь — детали по каждому режиму и процессу.

---

## 1. Хранилище конфигурации — детали

### Жизненный цикл правки

1. Захватить объект(ы) в хранилище (только нужные — не «захватить всю конфигурацию»).
2. Изменить, проверить (самопроверка: `1c-thin-triggers`).
3. **Получить из хранилища** свежие версии → конфликты → разрешить.
4. Обновить конфигурацию БД, прогнать ключевой сценарий.
5. Поместить с комментарием (номер задачи + суть).

### Типовые ситуации

| Ситуация | Решение |
|---|---|
| «Объект захвачен коллегой, а мне срочно» | Договориться; коллега помещает или отменяет захват сам. «Отменить захват» чужого — только с ним на связи |
| «Поместил, а у коллеги пропали изменения» | Помещение без актуализации. Восстановление — из версии хранилища (история версий) |
| «Нужно посмотреть, кто и когда менял объект» | История хранилища по объекту + версии |
| Долгий захват (неделя+) | Разбить задачу: помещать промежуточные рабочие состояния чаще |

## 2. EDT + git — детали

### Структура

- Исходники конфигурации — файловый формат EDT (`src/`), под git.
- Ветки `feat/...` от `main`, PR с ревью (см. `1c-code-review`), squash-мерж.
- Бинарные артефакты (`.cf`, `.epf`, `.cfe`) — релизный артефакт, не исходник.

### Конфликты мержа

- `.mdo` — XML целиком описывает объект. Конфликт внутри `.mdo` разрешать **по смыслу обеих правок**; «взять нашу версию» = потерять чужую доработку объекта.
- `Configuration.mdo` конфликтует почти всегда (там регистрация всех новых объектов): оба изменения — добавления строк, взять **обе**.
- После разрешения — загрузка в чистую ИБ обязательна: синтаксически «слившийся» XML может быть логически битым.

### Git-гигиена для 1С

- `.gitignore`: служебные каталоги EDT/конфигуратора, временные выгрузки.
- Коммит = логически завершённая правка + рабочая загрузка.

## 3. Обновление типовой / БСП — по шагам

1. **Фиксация текущего состояния**: копия продуктива, список доработок (расширения, объекты с префиксом, правки типовых — должны быть задокументированы, иначе это «минное поле»).
2. Чтение changelog поставщика: новые/изменённые/удалённые объекты, **обработчики обновления** (отложенные обновления данных могут идти часами — планировать окно).
3. Обновление на копии через «Сравнение и объединение»: для типовых объектов с правками — вручную переносить доработки в новую версию.
4. Проверка расширений: платформа проверяет применимость, но **не** проверяет, что заимствованный метод не изменил сигнатуру/логику — перехватчики `&ИзменениеИКонтроль` могут молча перестать работать (см. `1c-extensions`).
5. Регламентные тесты + ручной прогон ключевых сценариев.
6. Обновление продуктива в окно: бэкап → монопольный режим → обновление → обработчики обновления → контроль ЖР.

🔴 **Отложенные обработчики обновления**: релиз не «завершён», пока они не отработали. Пользователи могут видеть старые данные/ошибки — предупредить, мониторить очередь.

## 4. Поставка и релизы — детали

### Артефакты

| Артефакт | Что | Когда |
|---|---|---|
| `.cf` | Конфигурация целиком | Полная поставка |
| `.cfu` | Обновление конфигурации | Поставка обновления на поддерживаемую конфигурацию |
| `.cfe` | Расширение конфигурации | Поставка доработок без изменения типовой |

### Версионирование

- Версия — в свойствах конфигурации; правило команды фиксируется (например `major.minor.patch.build`).
- Совместимость: `compatibilityMode` платформы + версия конфигурации-приёмника для `.cfe` + версия БСП (для расширений, использующих БСП).

### Мониторинг после релиза

- Первые часы: ЖР на ошибки (`EXCP` в ТЖ — см. `references/diagnostics.md` скила `1c-performance`), очередь отложенных обработчиков, обратная связь пользователей.
- План отката проверен **до** наката: из чего восстанавливать и за какое время.

- [ ] Конфликты `.mdo` разрешены по смыслу; чистая загрузка проверена
- [ ] Доработки типовой инвентаризированы (расширения/префикс/документированные правки)
- [ ] Расширения проверены после каждого обновления основной конфигурации
- [ ] Релиз: версия ↑, changelog, чистая ИБ, тест, бэкап, откат, окно
- [ ] После релиза: мониторинг ЖР/обработчиков, готовность к откату
