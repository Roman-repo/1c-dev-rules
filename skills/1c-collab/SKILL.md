# 1c-collab — командная разработка и поставка

> Код пишется в одиночку, а конфигурация живёт в команде. Большинство потерь кода в 1С — не баги, а процессные ошибки: перезатёрли доработку при обновлении, поместили в хранилище без актуализации, выкатили релиз без отката.

## 🔴 Два режима командной разработки — не смешивать

| Режим | Когда | Ключевой артефакт |
|---|---|---|
| **Хранилище конфигурации** | Классическая схема, конфигуратор, команда до ~10 разработчиков | Хранилище + захват объектов |
| **EDT + git** | Современная схема, ветки, code review, CI | Исходники EDT в git-репозитории |

Правила ниже разделены по режимам. Смешанная схема (часть команды в хранилище, часть в git без процесса синхронизации) — источник потери кода.

## Хранилище конфигурации — правила

- 🔴 **Захват перед правкой.** Изменять объект без захвата запрещено — иначе при помещении затрёте чужие правки.
- 🔴 **Актуализация перед помещением.** Сначала «Получить из хранилища» (обновить конфигурацию БД), разрешить конфликты, потом помещать.
- 🟡 **Комментарий к версии обязателен** — что и зачем изменено (номер задачи).
- 🟡 Не держать объекты захваченными неделями — чем дольше захват, тем дороже мерж.
- 🔴 Не «отменять захват» чужого объекта без автора — его несохранённые правки умрут.

## EDT + git — правила

- 🔴 Ветки: `feat/...` → PR → squash в `main` (как в этом плагине). Правка прямо в main запрещена.
- 🔴 Конфликты в `.mdo` XML разрешать **внимательно по смыслу**, не «взять наше/ихнее» целиком: XML объекта целостен, половинчатый мерж = битый объект при загрузке.
- 🟡 Бинарники (`.cf`, `.epf`) в git не коммитить без необходимости — исходники важнее.
- 🟡 После мержа — проверка загрузки в чистую ИБ до выкладки (см. релизный чек-лист).

## 🔴 Обновление типовой конфигурации / БСП

Порядок, который не теряет доработки:

1. **Копия продуктива** — вся работа только на копии.
2. Обновление через «Сравнение и объединение» — доработки видны в дереве различий.
3. Доработки — **в расширениях** (см. `1c-extensions`) или объектах с префиксом проекта (см. `1c-platform-support` — «два слоя кода»). Правки типовых объектов — последнее средство, с документированием.
4. После обновления: **проверить расширения** — заимствованные методы могли измениться (`&ИзменениеИКонтроль` перестанет вызываться при смене сигнатуры).
5. Тест ключевых сценариев на копии → продуктив в регламентное окно.

🔴 Признак беды после обновления: «доработка пропала» = её не было ни в расширении, ни в объекте с префиксом, и режим объединения её затёр.

## 🔴 Выпуск релиза / поставка — чек-лист

> Это **технический** чек-лист сборки. Артефактный слой релиза (состав из
> принятых задач, свод миграций, примечания пользователям/админам) — скил
> `1c-release` конвейера разработки.

- [ ] Версия конфигурации увеличена (свойство «Версия» в свойствах конфигурации)
- [ ] Changelog/описание изменений сформировано
- [ ] Конфигурация загружается в **чистую** ИБ без ошибок (не только «обновляется на нашей базе»)
- [ ] Расширения (.cfe) проверены на совместимость с версией конфигурации и платформы (`compatibilityMode`)
- [ ] Тест ключевых сценариев на копии продуктива пройден
- [ ] **Бэкап продуктива** перед накатом
- [ ] **План отката** написан до начала: что делать, если обновление конфигурации БД упало на половине
- [ ] Окно обновления согласовано (монопольный режим для обновления ИБ)

## Типовые грабли

| ❌ Грабля | Последствие |
|---|---|
| Помещение в хранилище без актуализации | Чужие правки затёрты, узнают через неделю |
| «Отменил захват» чужого объекта | Потерянная работа коллеги |
| Половинчатый мерж `.mdo` | Объект не загружается в ИБ |
| Обновление типовой с доработками «вживую» | Доработки затёрты режимом объединения |
| Расширение не проверено после обновления | Перехватчики молча не вызываются |
| Релиз без бэкапа и плана отката | Обновление ИБ упало на половине — база в подвешенном состоянии |

## Мини-чек-лист

- [ ] Ветка feat/ + PR, правки в main только через мерж
- [ ] Доработки типовой — в расширениях / объектах с префиксом
