# 1c-code-review — этап «Код ревью» + чек-лист

> Этап **«Код ревью»** конвейера: после «Внутренней приёмки» (чистый 05), до
> «Внешней приёмки». Проверка кода задачи на стандарты разработки — два
> детерминированных слоя (regex-сканер `scripts/checkbsl_scan.py` +
> bsl-language-server CLI через `scripts/bsl_ls_analyze.py`) + чек-лист по
> секциям ниже + полный каталог правил checkbsl (`references/checkbsl/`).
> Вне конвейера чек-лист применим к любому MR/PR 1С.

## Место в конвейере

- **Вход:** внутренняя приёмка завершена — 05 без красных строк, вердикт
  отмечен (`1c-internal-acceptance`); Исполнитель предъявляет дифф кода задачи.
- **Участники:** **Ревьюер** (второй программист / техлид / Оркестратор —
  проверяет код, решение в 05a) и **Исполнитель** (предъявляет код).
- **Режим:** manual (дефолт) — Исполнитель останавливается после 05 и передаёт
  код Ревьюеру; 🔴 внешняя приёмка не начинается до «Одобрено» в 05a. auto —
  самопрогон с пометкой режима, ответственность на Оркестраторе. Режим общий
  для согласования и ревью — файл `_conveyor-mode.md`.
- **Выход:** артефакт `05a-code-review.md` (шаблон
  `references/code-review-report-template.md`). «Одобрено» → внешняя приёмка;
  «Доработать» → возврат на этап «Разработка», правка, повтор затронутых
  проверок 05 и повторное ревью этим же файлом.
- **Проверка:** `delivery_tools.py check` — гейт 6→7 (решение в 05a; задачи,
  начатые до 0.23.0 без 05a, — WARN без блокировки).

## Как пользоваться

Порядок «пакет-первым»: сначала детерминированные слои (сканер → BSL LS),
затем каталог группами, затем чек-лист секций по типу изменения.

1. Прогоните **детерминированные слои** на диффе задачи (см. «Детерминированные
   слои» ниже): `scripts/checkbsl_scan.py`, затем `scripts/bsl_ls_analyze.py`
   с `--report` — отчёт пишется в каталог задачи (петля исправлений — там же).
   Срабатывания — кандидаты в findings: ложные отсеиваются (например,
   `MagicNumber` на осмысленном индексе), остальное переносится в 05a.
2. Определите **тип изменения** (какие объекты затронуты — см. таблицы ниже).
3. Сверьте сомнительные места с **каталогом checkbsl**
   (`references/checkbsl/index.md`): полная сеть правил проверки кода
   (код / запросы / метаданные) со ссылкой на стандарт — для паттернов, не
   покрытых чек-листом секции и сканером. Приоритет нарушения — по чек-листу
   и стандарту.
4. Откройте релевантные секции чек-листа и пройдитесь по пунктам. Каждый пункт
   ссылается на стандарт — если сомневаетесь, открывайте первоисточник.
5. 🔴-пункты — блокирующие (код не проходит ревью без исправления). 🟡 — важные. 🟢 — рекомендации.
6. Замечания оформляйте форматом из «Шаблон комментария к MR» ниже и
   переносите в `05a-code-review.md`; ссылайтесь на ключ правила каталога
   или № стандарта.
7. Решение Ревьюера — в 05a («Одобрено» / «Доработать»); ретроспективу спора
   решает ссылка на номер правила/стандарта.

### Детерминированные слои: сканер + BSL LS

Два детерминированных слоя перед ручным проходом (одинаковый вход →
одинаковые findings, без ИИ-погрешности):

1. **Сканер** `scripts/checkbsl_scan.py` — regex-слой (~22 ключа каталога):
   `UseQueryInALoop` №436, `VirtualTablesWithoutInnerFilter` №733,
   `SynchronousMethods` №703, `DeprecatedMethodMessage`, `MagicNumber`,
   `HardcodedGUID`… Быстрый, без зависимостей, работает на любой машине.

       python3 scripts/checkbsl_scan.py <изменённые файлы/каталог>   # md-таблица findings
       python3 scripts/checkbsl_scan.py --diff main --format json   # только дифф задачи
       # exit: 0 — 🔴 нет, 1 — есть 🔴, 2 — ошибка; 🟡/🟢 допустимы (как WARN)

2. **BSL LS** `scripts/bsl_ls_analyze.py` — ядро полноты пакета:
   bsl-language-server CLI в режиме analyze (AST: запросы, транзакции,
   устаревшие методы, области, сложность, метаданные — ~85–95% правил
   детерминированно). Ключи диагностик маппятся на каталог checkbsl (таблица
   алиасов в скрипте — системы имён разные), № стандарта — из каталога;
   `--diff` фильтрует по изменённым файлам и строкам. Требует Java 11+ и jar
   (установка — в докстринге скрипта); нет Java → слой пропускается с честным
   сообщением (exit 3), остаются сканер и ручной проход.

       python3 scripts/bsl_ls_analyze.py --diff main                          # дифф: файлы и строки
       python3 scripts/bsl_ls_analyze.py <файлы> --src-root <корень src EDT>  # контекст конфигурации
       # + --report docs/delivery/<ЗАДАЧА>/code-review/bsl-ls-r1.md — отчёт ревью (петля ниже)
       # exit: 0 — 🔴 нет, 1 — есть 🔴, 2 — ошибка, 3 — Java/jar недоступны

   BSL LS разбирает **всё дерево srcDir** на каждой итерации петли (требование
   AST: контекст метаданных и межмодульных вызовов), поэтому на больших
   конфигурациях ускоряйте прогоны петли:
   - `--slim-config` — анализ только диагностик каталога∪алиасов: быстрее,
     шум 🟡 без привязки к каталогу уходит (не действует, если у проекта есть
     свой `.bsl-language-server.json`);
   - `--cache-dir .cache/bsl-ls` — повторный прогон без правок входов
     мгновенный (кэш по хэшу дерева src_root + jar + конфиг);
   - тюнинг `--timeout` (дефолт 900 с) и `--no-line-filter` (фильтр по файлам
     диффа, без фильтра по строкам) — см. `--help`.

Слои — предфильтр, а не вердикт: решение всегда за Ревьюером (05a). Права,
несуществующие элементы форм и другой контекст конфигурации, недоступный
слоям, — за ручным проходом (пункты 3–4).

**Пополнение слоя 1 (обязательное правило).** Если ручной проход нашёл
нарушение, которое слои 1–2 пропустили, и оно проверяется текстом (regex по
строке/циклу, без AST и контекста конфигурации) — это кандидат на
детерминированное покрытие. Сообщите явно: «⚠️ Обнаружен новый паттерн, не
покрытый детерминированными слоями: <ключ/суть>», — и **спросите, добавить ли
его в `checkbsl_scan.py`** (правило + тест). Не добавляйте молча и не
теряйте находку: каждый такой кандидат либо становится правилом слоя 1, либо
фиксируется отказом в 05a. Пример: «СрезПоследних с отбором, но без периода»
(0.28.0, из живого теста на ТОИР).

### Отчёт ревью и петля исправлений

Каждый прогон слоя оставляет **файл-отчёт в каталоге задачи** —
`docs/delivery/<ЗАДАЧА>/code-review/`: BSL LS — `bsl-ls-r<N>.md` (флаг
`--report`; содержит код с замечаниями, «что не так», пример «как правильно»
и вердикт), сканер — `checkbsl-r<N>.md` (перенаправлением вывода `>`).

**Петля самоочистки (порядок Исполнителя до передачи кода Ревьюеру):**

1. Прогон обоих слоёв на диффе задачи → отчёты r1.
2. Есть 🔴 → **возврат на этап «Разработка»**: правка кода по отчёту («как
   правильно» — отправная точка) → повторный прогон теми же командами →
   отчёты r2. Петля повторяется, пока отчёт не станет чистым по 🔴.
3. 🟡 в изменённом коде — правятся в той же петле либо обосновываются в 05a;
   🟢 — на усмотрение автора (переносить в findings не обязательно).
4. Чистый по 🔴 отчёт — код идёт Ревьюеру (чек-лист ниже); отчёты раундов
   хранятся как история самоочистки и приложение к 05a.

Петля не отменяет решение Ревьюера: «Доработать» в 05a — тот же возврат на
этап «Разработка», только с замечаниями ревью; после правки — повторный прогон
слоёв (новый r<N>) и повторное ревью тем же файлом 05a.

### Два отчёта — разделять (проект системы vs проект плагина)

Результат ревью и наблюдения о работе самого плагина — разные документы,
кладутся в разные проекты и не смешиваются:

1. **Отчёт ревью** — артефакт 05a (заполненный шаблон) + детальные замечания
   вида «фрагмент кода → почему косяк → как исправить» + отчёты слоёв
   `r<N>`. Место: **проект системы под ревью** — для задачи конвейера
   `docs/delivery/<ЗАДАЧА>/code-review/`, для ревью вне задачи
   `docs/code-review/<ГГГГ-ММ-ДД>-<объект>.md`. Адресат — автор кода.
2. **Отчёт об отклонениях плагина** — что слой не поймал / поймал ложно
   (формат: `[Скил/Скрипт] — что не поймал / Пример / Предложение / Класс`).
   Место: **проект плагина** `docs/field-reports/<ГГГГ-ММ-ДД>-<суть>.md`.
   Адресат — мейнтейнер плагина; полнотекст отчёта ревью не дублируется —
   только ссылка на файл из п.1.

> Подробные карточки с примерами «неправильно/правильно» — в тематических скилах (`1c-queries`, `1c-forms`, `1c-metadata`…).

## 8. High-risk patterns (проверять ВСЕГДА, независимо от типа объекта)

> Рубрикатор из 9 категорий, которые чаще всего приводят к инцидентам на проде.
> В отличие от секций 1–7 (привязаны к типу объекта), этот список проходится
> **полностью** при любом MR — даже маленьком. Большинство категорий уже раскрыты
> выше; здесь они собраны в единый «провальный» чек-лист.
>
> Идея рубрикатора заимствована у плагина [Unica](https://github.com/IngvarConsulting/unica)
> (Ingvar Consulting, LGPL-3.0), адаптирована под структуру v8std.

| # | Категория | Что искать | Подробнее |
|---|---|---|---|
| 1 | **Границы транзакций** | Чтение внутри `НачатьТранзакцию...Зафиксировать`; длинные транзакции; транзакция без `Попытка/ОтменитьТранзакцию` | секция 4, [№783](https://github.com/zeegin/v8std/blob/main/docs/std/783.md) |
| 2 | **Запрос в цикле** | `Запрос.Выполнить()` / `.Выгрузить()` внутри `Для`/`Для Каждого` | секция 2, [№436](https://github.com/zeegin/v8std/blob/main/docs/std/436.md) |
| 3 | **Серверный/клиентский контекст** | `&НаСервере` где достаточно `&НаСервереБезКонтекста`; передача формы на сервер; клиентский код, дёргающий БД | секция 1, [№636](https://github.com/zeegin/v8std/blob/main/docs/std/636.md) |
| 4 | **Привилегированный режим** | `УстановитьПривилегированныйРежим(Истина)` без обоснования; привилегированные общие модули вне служебных целей | секция 6, [№521](https://github.com/zeegin/v8std/blob/main/docs/std/521.md) |
| 5 | **Избыточные права** | Новый объект без ролей (№532); RLS «все всем»; роли шире, чем требует бизнес-сценарий | секция 6, [№532](https://github.com/zeegin/v8std/blob/main/docs/std/532.md) |
| 6 | **Фоновые задания** | Тяжёлый расчёт в интерактиве, а не в ФЗ; ФЗ без обработки ошибок; ФЗ, меняющее данные без блокировок | секция 7, [№642](https://github.com/zeegin/v8std/blob/main/docs/std/642.md) |
| 7 | **Внешние вызовы** | HTTP-запросы / файловые операции / OLE **внутри транзакции** или без таймаута | скил `1c-integration` |
| 8 | **Временные файлы** | `КаталогВременныхФайлов()` без очистки; генерация путей без уникальности; файлы в транзакции | скил `1c-integration` |
| 9 | **Молчаливый перехват исключений** | `Попытка...Исключение КонецПопытки;` без `ВызватьИсключение` и без логирования | скил `1c-logging`, [№540](https://github.com/zeegin/v8std/blob/main/docs/std/540.md) |

**Как использовать:** даже если MR маленький (одна правка) — прогоните этот список целиком. Категории 1, 2, 4, 9 — 🔴 блокирующие, ловят самые дорогие инциденты.

## Шаблон комментария к MR

### Принципы вывода

- **Findings first.** Замечания — впереди, отсортированные по серьёзности. Резюме — в конце, и только если полезно.
- **Не переписывайте код во время ревью**, если автор явно не попросил fixes после ревью. Ревью — это диагностика, а не авторство.
- **Каждое замечание заземлено** в конкретное место (путь + строка) или в вывод диагностики, не «где-то тут».

### Структура одного finding

Каждое замечание содержит 5 полей:

```
[Severity] [Стандарт] Path:file:line
  Issue:    что не так (одной фразой)
  Impact:   к чему ведёт (последствия на проде)
  Fix:      suggested fix — что изменить (без переписывания всего блока)
```

### Пример сгруппированного вывода

```
🔴 Блокирующие (обязательно исправить):

  [🔴 №733] module.bsl:142
    Issue:  СрезПоследних вызван без параметра даты и отбора
    Impact: СУБД читает весь регистр; список «тормозит» у каждого пользователя
    Fix:    Передать &ДатаКонца и отбор по измерению

  [🔴 №436] module.bsl:88
    Issue:  Запрос.Выполнить() внутри цикла Для Каждого
    Impact: N запросов к БД вместо одного; рост линейно от размера массива
    Fix:    Собрать массив, один запрос с «В (&Массив)»

  [🔴 №532] Catalogs/<Имя>/
    Issue:  Новый справочник не включён ни в одну роль
    Impact: Стандартные пользователи его не видят
    Fix:    Добавить права в Rights.rights (минимум Read в БазовыеПрава)

🟡 Важно (обсудить с автором):

  [🟡 №636] module.bsl:55
    Issue:  Серверная процедура объявлена как &НаСервере (контекстная)
    Impact: Форма тащится на сервер при каждом вызове — лишний трафик
    Fix:    Если форме не нужны её данные — &НаСервереБезКонтекста

🟢 Рекомендации (на усмотрение автора):

  [🟢 №400] module.bsl:120
    Issue:  Сообщить("Ошибка") без привязки к полю
    Impact: Пользователь не видит, какое поле виновато
    Fix:    СообщитьПользователю(...) с параметром Поле

  MR добавляет справочник + форму. 3 блокирующих (все — high-risk §8: №733, №436, №532),
```

## Исключения

Любое отступление от стандарта допустимо, если:
1. Есть техническое обоснование в комментарии у кода;
2. Согласовано на ревью;
3. Зафиксировано (например, в отдельном документе-обосновании / ADR, если причина — производительность).
