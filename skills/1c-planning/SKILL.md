# 1c-planning — Планирование: что и зачем делаем

> Роль этапа — **руководитель проекта**. Планирование отвечает «что и зачем»,
> а не «как»: решение появляется только на проектировании. Выход этапа —
> **Карточка задачи**; без её подтверждения инициатором проектирование не начинается.

## Мандат роли

| РП решает | РП не решает |
|---|---|
| Формулировка проблемы и цели | Как реализовано (объекты, запросы, формы) |
| Измеримые критерии успеха | Сценарии и детали поведения |
| Рамки: что в рамках / что НЕ делаем | Технический выбор архитектуры |
| Приоритет и оценка (S/M/L + чел.-ч) | Код |

## Процедура

1. **Зафиксируйте инициатора и источник запроса** — устно, трекер, письмо. Инициатор
   будущий приёмщик: кто сформулировал, тот и подтверждает.
2. **Проблема «как есть» → цель «должно быть».** Проблема — из трёх частей:
   «как система работает сейчас» / «недостатки» (боль заказчика, его словами)
   / «желаемый вариант работы» — наблюдаемое поведение, **не решение**.
   🔴 «Сделать печатную форму» — решение; «снабженец получает акт в момент
   закрытия заявки, не открывая конфигуратор» — цель.
   Цель дополняется **бизнес-ценностью**: базовая метрика → целевая + срок
   («доля просрочек: 42 % → < 25 % за квартал»). Ценности без метрик
   («чтобы было удобно») — не ценность.
3. **Наименование задачи — действие.** Заголовок карточки (поле «Предмет»
   в трекере) отвечает на вопрос **«Что сделать?»** — глагол в неопределённой
   форме: «Разработать печатную форму для согласования заявки на ремонт».
   🔴 Именная группа («Компактная печатная форма для согласования») — не
   наименование: из неё не следует, что делать. Наименование ≠ цель: цель —
   состояние мира, наименование — действие над системой.
4. **Критерии успеха — измеримые.** Каждый критерий отвечает «как проверим»:
   замер (время открытия списка до/после), факту можно присвоить ✅/❌.
   🔴 «Работает удобно» — не критерий: его нельзя принять или вернуть.
   🔴 Сравнительный критерий («не дольше/не хуже, чем до доработки») требует
   **базлайна** — замера «до» (дата, значение, условия) в самой карточке;
   снимается до начала разработки — состояние «до» потом не повторить.
   Базлайн снять невозможно — переформулируйте критерий в абсолютный
   («не дольше 10 секунд по замеру»).
5. **Рамки — явно, включая «что НЕ делаем».** Список вне-рамок защищает задачу
   от scope creep на приёмке: замечание вне рамок — класс C, новая задача
   (см. `1c-delivery-gate` §3).
6. **Риски и допущения.** Допущение — во что верим без проверки; риск — что может
   пойти не так + как митигируем.
7. **Оценка S/M/L + человеко-часы, зависимости и блокеры.** Только после
   рамок: оценка до рамок — угадывание; верифицируется (кем/когда — если
   процесс команды требует). Обязательное дополнение к классу — **оценка
   затрат в человеко-часах для исполнителя-человека** (программист 1С,
   знакомый с платформой и БСП): таблица «действие (что сделать) → часы»
   с итоговой строкой — действия конкретные, с наблюдаемым результатом
   (изучить…, реализовать…, протестировать…, пройти ревью…), а не «виды
   работ» вообще. Часы — валюта, сопоставимая с планом людей и трекером;
   ИИ-исполнитель оценку не отменяет. Блокеры — что должно закрыться ДО старта — фиксируются отдельно
   от зависимостей: «скрытый» блокер останавливает задачу посреди работы.
   Ориентиры — в `references/planning-full.md`. Оценка — не финал,
   а обязательство: при закрытии задачи с фактом сверяются обе оси — класс
   и часы — в секции «Ретроспектива» карточки (петля оценки, калибровка
   ориентиров).
   🟡 **Лимит размера задачи для одного ИИ-прохода:** ориентир — изменения
   в пределах **~7 файлов** (объекты метаданных + модули) и порядка пары
   сотен строк кода. Крупнее — качество падает нелинейно: ИИ теряет нить,
   ломает смежное, забывает требования из начала. Такая работа — не задача,
   а недоделанная декомпозиция: разбейте её на задачи эпика
   (`1c-epic-planning`). Ориентир калибруется по накопленным ретроспективам
   (`references/planning-full.md`).
8. **Подтверждение инициатора** — цель, критерии, рамки. Это DoD-гейт в
   Проектирование.
9. **Прогон DoR** (`references/dor-checklist.md`) — готовность задачи к
   работе: 🔴 без галочки — задача возвращается постановщику, а не
   «дорешивается на ходу». Для оценки полезен предварительный список
   объектов метаданных (опциональная секция 01).

## Антипаттерны

| 🔴 Антипаттерн | Чем оплачивается |
|---|---|
| Цель сформулирована как решение | Обсуждать нечего: на приёмке «это не то, что я просил» (класс B) |
| Наименование — именная группа, а не действие («Что сделать?») | Из заголовка не ясно, что делать; задачу не найти в трекере, в релизных примечаниях строка не читается |
| Критерии непроверяемы («удобно», «быстро») | Приёмка превращается в спор вкусов |
| Сравнительный критерий без базлайна «до» | После разработки сравнивать не с чем: состояние «до» уже не повторить, критерий неверифицируем |
| «Рамки обсудим по ходу» | Каждая новая идея удлиняет задачу неограниченно |
| Оценка до фиксации рамок | Оценка публично обещана — рамки подгоняются под неё |
| Оценка только классом S/M/L, без человеко-часов | Задачу не вписать в план людей и трекер: часы — общая валюта с командой и заказчиком; скорость ИИ — не аргумент в переговорах о сроке |
| Задача размером с эпик («сделай всё») | Качество ИИ-прохода падает нелинейно: теряется нить, ломается смежное; возвраты классов A/B |
| Инициатор не подтвердил карточку | Проектирование ведёт к чужой цели |
| Постановка без DoR («дорешим по ходу») | Скрытые зависимости и непроверяемые требования всплывают посреди работы — стоп и возврат класса B |

## Артефакт-выход

`01-task-brief.md` — Карточка задачи. Создаётся копированием
`references/task-brief-template.md` в каталог доставки задачи
(`docs/delivery/<ID-задачи>/` по умолчанию — см. `1c-delivery-gate`).
Заголовок карточки — наименование-действие (см. процедуру, п. 3).
Секция «Ретроспектива» заполняется при закрытии задачи (DoD «6 → закрытие»).
Состав полей и примеры заполнения — в `references/planning-full.md`.

## Мини-чек-лист (DoD этапа)

- [ ] Инициатор и источник запроса зафиксированы
- [ ] Наименование задачи — действие, отвечает на «Что сделать?»
- [ ] Проблема — словами инициатора; цель — состояние, а не решение
- [ ] Каждый критерий успеха измерим (как проверим — понятно)
- [ ] У сравнительных критериев зафиксирован базлайн «до» (дата, значение, условия) либо критерий переформулирован в абсолютный
- [ ] Рамки включают явный список «что НЕ делаем»
- [ ] Риски/допущения перечислены; оценка S/M/L после рамок + затраты в чел.-ч (исполнитель — программист 1С, с декомпозицией)
- [ ] Задача в пределах ориентира размера (~≤7 файлов) — либо разбита на задачи эпика (`1c-epic-planning`)
- [ ] Инициатор подтвердил цель, критерии и рамки (дата, кто)
- [ ] DoR пройден (`references/dor-checklist.md`): 🔴-пункты отмечены; бизнес-ценность — парой «базовая → целевая метрика»
