# Definition of Ready — готовность задачи к работе

> Чек-лист качества постановки (карточка 01). Проходится **до** передачи
> задачи исполнителю — вместе с подтверждением инициатора (гейт 1→2
> конвейера). 🔴 блокирует: задача возвращается постановщику; 🟡 важно;
> 🟢 желательно. DoR отвечает «задачу можно начинать?», DoD-гейты
> конвейера (`1c-delivery-gate` §2) — «этап закончен?».

## 🔴 Процессный гейт

- [ ] Заказчик и приёмщик указаны (приёмщик по умолчанию — заказчик)
- [ ] Оценка проставлена и верифицирована: класс S/M/L + затраты в чел.-ч (исполнитель — программист 1С, таблицей «действие → часы» с итогом)
- [ ] Оценка/объём в пределах лимита задачи (~≤7 файлов); крупнее — эпик (`1c-epic-planning`)
- [ ] Зависимости и блокеры выявлены и зафиксированы в 01

## 🔴 Содержание

- [ ] Предмет — действие, отвечающее на «Что сделать?» (не именная группа)
- [ ] Бизнес-ценность измерима: базовая метрика → целевая (+ срок), не «чтобы было удобно»
- [ ] Описание из трёх частей: «как сейчас» / «недостатки» / «желаемый вариант»
- [ ] Критерии успеха проверяемы: независимый проверяющий присвоит ✅/❌ без вопроса автору
- [ ] Рамки включают явное «что НЕ делаем»
- [ ] Инициатор подтвердил цель, критерии и рамки (гейт 1→2); открытые вопросы закрыты его решениями (секция «Решения инициатора» в 01)

## 🟡 Качество требований

- [ ] Граничные условия продуманы: кто/когда/как часто; источник данных
- [ ] Краевые случаи перечислены: пустые данные, отказы, незаполненный ответственный
- [ ] Для затрагивающих задач озвучены НФТ: совместимость версий, объёмы, регрессия, отказоустойчивость

## 🟢 Желательно

- [ ] Предварительный список объектов метаданных в 01 (для оценки)
- [ ] Макет интерфейса для новых форм (эскиз — в 03 на проектировании)

## Стоп-лист (когда задача возвращается постановщику)

- нет измеримой бизнес-ценности в «Цели»;
- оценка без человеко-часов (только класс S/M/L) — задачу не вписать в план людей;
- «Проблема» не объясняет текущее поведение и недостатки;
- требования непроверяемы («сделать удобно», «чтобы работало быстро»);
- не указан заказчик/приёмщик;
- объём превышает лимит задачи и не декомпозирован;
- скрытая зависимость/блокер, выявленный только в работе.

> 🔴, найденный после старта задачи, — повод вернуть её постановщику,
> а не «дорешивать на ходу»: каждый тихо дорешанный пункт — несогласованные
> рамки и возврат класса B на приёмке.

## Связь с конвейером

DoR — качество входа этапа 1 и часть гейта 1→2 (`1c-delivery-gate` §2).
Дальше качеством владеют DoD-гейты: проектирование — 2→3, согласование
пакета — 3→4, готовность кода — 4→5.
