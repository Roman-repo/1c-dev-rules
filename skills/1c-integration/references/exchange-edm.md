# Обмен данными: EnterpriseData, конвертация данных, планы обмена

> №771 и №701 в `integration-full.md` — только заголовками. Эта карточка отвечает на вопросы:
> **«какой механизм обмена выбрать»** и **«где типовые грабли при настройке обмена между конфигурациями»**.

---

## 1. Выбор механизма — решающая таблица

| Ситуация | Механизм | Почему |
|---|---|---|
| Обмен между **типовыми** конфигурациями 1С (ERP ↔ УТ ↔ БП) | **EnterpriseData** через штатную подсистему БСП | Поддерживаемый формат, сопоставление из коробки, не писать свою сериализацию (№771) |
| Обмен с 1С, но модели **сильно различаются** (нестандартные объекты, другая структура) | EnterpriseData + **правила конвертации (КД 3.1)** | Формат стандартный, маппинг — декларативными правилами, а не кодом |
| Интеграция с **не-1С** системой (внешний API) | REST/JSON (см. `integration-auth.md`) | EnterpriseData наружу отдавать тяжело: XDTO-формат, XML-обёртки — внешняя сторона не оценит |
| Распределённая база / узлы по отбору | **План обмена** с правилами регистрации (№701) | Регистрация изменений платформой, транспорт любой |
| Разовая миграция данных | Конвертация данных (КД 2.1/3.1) или обработка | Не строить постоянный обмен ради одноразовой задачи |

🔴 Главный анти-паттерн: **своя сериализация** (самописный XML/JSON между двумя 1С) — когда
задача решается EnterpriseData. Своя схема = свой формат версионировать, своё сопоставление
поддерживать, свои дубли разбирать.

---

## 2. EnterpriseData — что нужно знать

- Формат — XML-пакеты на базе XDTO, версионируется (`EnterpriseData_1.x` — версия важна:
  отправитель и получатель должны понимать общую версию; при обновлении конфигурации
  версия формата может подняться).
- Обмен строится на **плане обмена** (регистрация изменений) + подсистеме БСП обмена
  данными: настройка через «Синхронизацию данных», а не кодом.
- **Сопоставление объектов** — ключевой этап: как система понимает, что «Номенклатура А»
  из источника = «Номенклатура Б» в приёмнике. По умолчанию — по GUID ссылок, далее —
  по полям поиска (наименование, ИНН/КПП, артикул).
- Расширение формата под свои объекты — через **правила конвертации (КД 3.1)**:
  ПКО (правила конвертации объектов), ПКС (свойств), обработчики — декларативно,
  в типовых механизмах, а не произвольным кодом выгрузки.

⚠️ Версии формата и состав подсистем зависят от версии БСП — перед проектированием
сверьтесь с БСП проекта (`grep -rn "EnterpriseData" CommonModules/ --include=*.bsl`).

## 3. 🔴 Типовые грабли обмена (из практики сопровождения)

| ❌ Грабля | Симптом | ✅ Лекарство |
|---|---|---|
| **Дубли при сопоставлении** | После обмена — два контрагента «Ромашка» | Поля поиска настроены (ИНН+КПП), первичное сопоставление — до запуска регламентного обмена |
| **GUID-рассинхрон** | Объект есть в обеих базах, но с разными GUID — обмен не видит связи | Не пересоздавать объекты вручную в приёмнике; связь — через регистр соответствия |
| **Отборы узла не учтены** (№701) | Данные «не доезжают» до узла или едут лишние | Правила регистрации проверены на тестовом наборе: что регистрируется к выгрузке, что нет |
| **Правила регистрации — макетом плана обмена** (№799) | Правила вне проверок платформы, не отладить без внешних обработок, исправления не отслеживаются | Правила регистрации — в общем модуле-менеджере регистрации (синтакс-контроль, версионирование, отладка) |
| **Обмен падает на одном объекте** и вся очередь встаёт | Сообщение не подтверждено, отправка повторяется вечно | Ошибка обработки — в ЖР с контекстом объекта; «больное» сообщение — разобрать и пропустить осознанно |
| **Нет контроля объёма** | Тысячи объектов за сеанс, обмен идёт часами, блокировки | Регламентное задание обмена — в непиковое время (см. `1c-scheduled`), порционная выгрузка |
| **Правила конвертации правят «вживую»** на продуктиве | Рассинхрон версий правил между узлами | Правила — артефакт поставки: версия, тест на копии, потом продуктив |
| **Обмен в интерактиве пользователя** | «Сохранил документ — жду 40 секунд» | Выгрузка/загрузка — фоновыми/регламентными заданиями (№642), не в транзакции записи (№783) |

## 4. Минимальный порядок внедрения обмена

1. **Матрица объектов**: какие объекты в какую сторону, кто мастер-система для каждого (двусторонняя синхронизация одного объекта — источник бесконечных конфликтов; избегать).
2. **Сопоставление НСИ первично** (номенклатура, контрагенты, организации) — до включения документов.
3. Тест на копии: выгрузка → загрузка → сверка (количества, итоги, дубли).
4. Регламентное задание обмена: идемпотентное, с логированием (см. `1c-scheduled`), в непиковое время.
5. Мониторинг: контроль «очередь не растёт» и «ошибок загрузки нет» — иначе обмен молча встаёт.

## Мини-чек-лист обмена данными

- [ ] Механизм выбран по таблице §1, не «своя сериализация» при доступном EnterpriseData (№771)
- [ ] Для каждого объекта назначена мастер-система (нет двустороннего конфликта)
- [ ] Поля поиска/сопоставления настроены, первичное сопоставление НСИ сделано
- [ ] Отборы узлов проверены на тестовом наборе (№701)
- [ ] Обмен — регламентным заданием, вне транзакций пользователя, в непиковое время
- [ ] Ошибки обмена логируются с контекстом; «больные» сообщения не блокируют очередь навсегда
- [ ] Правила конвертации версионируются и применяются через тест на копии
