# Аутентификация и секреты во внешних интеграциях 1С

> Карточка `integration-full.md` покрывает таймауты/ретраи (№748/№794), но не вопрос
> **«как безопасно аутентифицироваться во внешнем API и где хранить секреты»** — а это
> самая частая дыра в интеграциях: секрет в коде, токен без обработки истечения, пароль в ЖР.

---

## 1. Схемы аутентификации — что когда

| Схема | Когда | Ключевое |
|---|---|---|
| **Basic Auth** (логин/пароль в заголовке) | Внутренние сервисы, простые API | Только по HTTPS; логин/пароль — из безопасного хранилища, не из кода |
| **API-ключ** (заголовок `X-API-Key` и т.п.) | Server-to-server с фиксированным доступом | Ключ — секрет; не встраивать в URL (попадает в логи прокси/ЖР) |
| **OAuth 2.0 Client Credentials** | Стандарт для server-to-server внешних API | Отдельный token-эндпоинт; кэшировать токен до `expires_in`; обрабатывать 401 → обновить |
| **OAuth 2.0 / JWT** (Bearer с токеном от IdP) | Интеграции через корпоративный провайдер идентификации | 1С обычно **использует** токен, а не подписывает; проверять срок жизни |
| **Взаимный TLS / сертификаты** | Банковские/гос. интеграции | Сертификат в хранилище ОС/МенеджерКриптографии, не файлом рядом с кодом |

## 2. 🔴 Секреты — НЕ в коде и НЕ открытым текстом

**Анти-паттерны (все — блокирующие на ревью):**

```bsl
// ❌ Секрет прямо в коде — уезжает в git, виден всем с доступом к конфигурации
Токен = "eyJhbGciOiJIUzI1NiIs...";

// ❌ Секрет в открытой константе — читается любым пользователем с правами на константу
КлючAPI = Константы.КлючВнешнегоAPI.Получить();

// ❌ Секрет в параметре URL — попадает в логи прокси, ТЖ, историю браузера
Запрос = Новый HTTPЗапрос("/data?api_key=" + КлючAPI);
```

**Как правильно:**

1. Секрет хранится в **безопасном хранилище БСП** (`ОбщегоНазначения.ЗаписатьДанныеВБезопасноеХранилище(Владелец, Данные)` / `ПрочитатьДанныеИзБезопасногоХранилища(Владелец)`) либо в защищённом регистре настроек интеграции с ограниченными ролями (№532).
2. Чтение секрета — **только на сервере**, только в момент вызова; на клиента секрет не передаётся никогда.
3. В ЖР/логах секрет **маскируется**: логировать факт «токен получен/просрочен», а не значение. Перед записью тела запроса в лог — вырезать заголовки `Authorization`, `X-API-Key`.
4. Ротация секрета = смена значения в хранилище, **без** обновления конфигурации.

⚠️ Точные имена методов безопасного хранилища зависят от версии БСП — проверьте
`grep -rn "Безопасно*Хранилищ" CommonModules/ --include=*.bsl` в проекте перед использованием.

## 3. OAuth 2.0 Client Credentials — рабочий шаблон

Самая частая схема для server-to-server: получить токен → использовать → обновить по истечении.

```bsl
// Токен кэшируем (параметр сеанса/регистр): запрашивать на КАЖДЫЙ вызов —
// лишняя нагрузка на IdP и риск блокировки за частые запросы.
Функция ПолучитьТокен(ПараметрыИнтеграции)
    Кэш = ПрочитатьКэшТокена();  // свой регистр сведений: токен + срок жизни
    Если Кэш <> Неопределено И Кэш.Истекает > ТекущаяДатаСеанса() + 60 Тогда
        Возврат Кэш.Токен;  // запас 60 сек до истечения
    КонецЕсли;

    Соединение = Новый HTTPСоединение("auth.example.com", 443, , , , 30,
        Новый ЗащищенноеСоединениеOpenSSL);
    Тело = "grant_type=client_credentials"
        + "&client_id=" + ПараметрыИнтеграции.ИдКлиента
        + "&client_secret=" + ПараметрыИнтеграции.Секрет;  // из безопасного хранилища
    Запрос = Новый HTTPЗапрос("/oauth/token");
    Запрос.Заголовки.Вставить("Content-Type", "application/x-www-form-urlencoded");
    Ответ = Соединение.ОтправитьДляОбработки(Запрос);

    Если Ответ.КодСостояния <> 200 Тогда
        // В лог — код и служебное описание, БЕЗ тела с client_secret
        ВызватьИсключение НСтр("ru = 'Не удалось получить токен доступа.'");
    КонецЕсли;

    Чтение = Новый ЧтениеJSON;
    Чтение.УстановитьСтроку(Ответ.ПолучитьТелоКакСтроку());
    ОтветJSON = ПрочитатьJSON(Чтение, Истина);  // Соответствие
    Чтение.Закрыть();
    ЗаписатьКэшТокена(ОтветJSON["access_token"], ОтветJSON["expires_in"]);
    Возврат ОтветJSON["access_token"];
КонецФункции
```

Обязательные правила:

- **Кэшировать токен** до истечения `expires_in` (с запасом ~60 сек) — не запрашивать на каждый вызов.
- **401 от API** = токен просрочен/отозван → инвалидировать кэш, получить новый, повторить запрос **один раз** (не в цикле — см. №794).
- Таймаут и на token-запрос тоже (№748): зависший IdP не должен вешать сеанс.
- Поток с «человеческим» логином/паролем (password grant) — избегать; для сервера-серверу — только client credentials.

## 4. Типовые ошибки аутентификации в интеграциях

| ❌ Ошибка | Последствие | ✅ Лекарство |
|---|---|---|
| Секрет в коде/константе открыто | Утечка через git/права | Безопасное хранилище + роли (§2) |
| Токен без кэша, запрос на каждый вызов | Rate-limit IdP, лишние 200–500 мс на вызов | Кэш до `expires_in` (§3) |
| Нет обработки 401 | Интеграция «внезапно» падает после смены токена | 401 → обновить токен → 1 повтор |
| Секрет в URL | Секрет в логах прокси/ТЖ | Секрет только в заголовке/теле по HTTPS |
| Тело запроса с секретом в ЖР | Утечка через журнал регистрации | Маскирование заголовков в логах (§2) |
| HTTP без TLS ради «внутренней сети» | Перехват токена в трафике | `ЗащищенноеСоединениеOpenSSL` везде |

## Мини-чек-лист аутентификации интеграции

- [ ] Ни одного секрета в коде, константах открыто, URL
- [ ] Секреты — из безопасного хранилища, чтение только на сервере
- [ ] Токен кэшируется до истечения (с запасом)
- [ ] 401 обрабатывается: инвалидация кэша → новый токен → один повтор
- [ ] Таймауты на все вызовы, включая token-эндпоинт (№748)
- [ ] В логах нет значений секретов/токенов (маскирование заголовков)
- [ ] HTTPS с `ЗащищенноеСоединениеOpenSSL` для всех внешних вызовов
