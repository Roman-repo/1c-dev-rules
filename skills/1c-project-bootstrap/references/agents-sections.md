2. **Как платформа определяет «можно ли править»** (ParentConfigurations.bin) — полностью универсально.
3. **Порядок работы над задачей** — 3 этапа (Планирование/Реализация/Самопроверка).
4. **Принципы эксперта** (7 принципов сеньора).
5. **Соглашения об именовании** — CamelCase, запрет `ё`, глаголы, `Вр`-префикс.
6. **Поисковые шаблоны** (grep-рецепты) — универсальны после замены префикса/пути.

## Полный текст: Как платформа определяет «можно ли править»

Эвристика по префиксу — упрощение. Платформа определяет редактируемость через
**состояние поддержки** (`Ext/ParentConfigurations.bin`). Алгоритм:

```
1. Файла поддержки нет → поддержки нет          → редактирование РАЗРЕШЕНО
2. G = 1 (глобальный запрет)                     → read-only ВСЁ
3. G = 0 → проверяем f1 по uuid объекта:
     f1 = 0 (на замке) хотя бы у одного поставщика → ЗАПРЕЩЕНО
     f1 = 1/2 (редактируется/снято)              → РАЗРЕШЕНО
     uuid не найден                               → не на поддержке → РАЗРЕШЕНО
```

То есть «наш» код (с префиксом проекта) — это объекты с `f1 = 1/2` или вовсе не на поддержке;
БСП — объекты с `f1 = 0` (на замке у поставщика 1С). Префикс — быстрый способ прикинуть,
но если сомневаешься — объект не на поддержке можно редактировать смело.

📖 [Полный алгоритм и формат ParentConfigurations.bin](https://github.com/Nikolay-Shirokov/cc-1c-skills/blob/main/docs/1c-support-state-spec.md)

## Полный текст: Порядок работы над задачей

### Этап 1. Планирование (до написания кода)

1. **Не читай всё подряд.** Следуй алгоритму погружения (см. карту проекта, если есть).
2. **Локализуй** объекты по имени и префиксу через `find`/`grep`.
3. **Пойми связи** через карту движений и поиск ссылок `grep -rn`.
4. **Прогони архитектурный чек-лист** — скил `1c-arch-checklist`: 7 вопросов эксперта (где жить логике, есть ли готовое, зависимости, сеть, отказ, перф, читаемость).
5. **Пройди гейт-чек-лист в `1c-dispatch-gate`** — обязательный фильтр «сигнал → карточки» **перед** таблицей A.
6. **Прочитай отобранные скилы** — открой SKILL.md и прочитай актуальный текст; не полагайся на память.

### Этап 2. Реализация

7. **Пиши код** по прочитанным правилам. Сверяйся с мини-чек-листом в конце каждого скила.
8. **Перед написанием новой функции — проверь переиспользование.** `grep` по БСП (`ОбщегоНазначения.*`) и прикладным модулям (с префиксом проекта). Не дублируй существующее.
9. **Комментируй «почему», а не «что».** «Что делает» видно из кода; комментарий объясняет **зачем** так, какой нюанс обходится. При обходе стандарта — комментарий с обоснованием обязателен.
10. **🔴 Не выдумывай функции.** Любая функция/метод, которая **не является 100% стандартной** платформенной (`НайтиПоКоду`, `СтрСоединить`, `Записать` и т.п.) — должна быть либо определена в проекте, либо раскрыта через стандартные средства. **Перед использованием — `grep -rn "Функция <Имя>" <путь к src> --include=*.bsl`.** Если определения нет и это не платформенная — **запрещено** использовать как готовую.
    - Типичные галлюцинации: `НайтиИлиСоздать`, `ОбщегоНазначения.СоздатьЭлемент`, `ЗагрузитьТабличныйДокумент`.
11. **🔴 Сверяйся с версией платформы.** Перед использованием метода, появившегося в новой версии (`ДокументМикс`, нативный парсер `.xlsx`, `Асинх`/`Ждать`) — проверь `compatibilityMode` в `Configuration.mdo`.
    - `Асинх Процедура`/`Ждать` в формах появились в 8.3.15+
    - нативный парсер `.xlsx` без OLE — 8.3.21+
12. **🔴 UUID при создании метаданных — только случайные.** При создании нового объекта метаданных (`.mdo`/`.form`) генерируй **каждый** UUID заново (`uuidgen | tr 'A-Z' 'a-z'`), а **не** плейсхолдерами вида `a1b2c3d4-…`. **Это касается ВСЕХ UUID в файле**, включая:
    - `uuid` корневого объекта
    - **`typeId`/`valueTypeId` внутри `<producedTypes>`** — частая ошибка: их воспринимают как «технические» и вставляют плейсхолдеры
    - UUID подобъектов: `attributes`, `forms`, `templates`, `tabularSections`, `commands`, `dimensions`, `resources`

    После подстановки — проверь отсутствие дубликата: `grep -oE '(uuid|typeId|valueTypeId)="[0-9a-f-]+"' Объект.mdo | sort | uniq -d` (должно быть 0 внутри файла), `grep -rn "<новый uuid>" <путь к src>` — 0 по всему проекту.
13. **🔴 Если правишь метаданные XML вслепую (без EDT) — предупреди явно.** Структуру `.mdo`/`.form` нельзя проверить синтаксически в этой среде. Скажи пользователю: «эта часть не проверена валидатором EDT, возможны ошибки структуры».
14. **🔴 Роли для новых объектов (№532).** Каждый новый объект метаданных (включая константу) включай минимум в одну роль. Без ролей объект невидим стандартным пользователям. Проверка: `grep -rl "Constant.<Префикс>Имя\|InformationRegister.<Префикс>Имя" Roles/` должен вернуть ≥1.

### Этап 3. Самопроверка (после написания, до коммита)

15. **Прогони скил `1c-thin-triggers`** — построчный проход по коду, 5 слоёв (механические, архитектура, перф, отказоустойчивость, галлюцинации API).
16. **Сверь со скилом `1c-code-review`** — по секции типа изменённого объекта.
17. **Перед коммитом** — убедись, что новый код с префиксом проекта, без `ё` в метаданных, экспортные процедуры — с описанием. Если правились метаданные — повтори правило 13.
18. **🟡 Повторный независимый прогон** (рекомендуется для нетривиальных MR). После самопроверки — прогони чек-листы ещё раз **с установкой «критик»», желательно после паузы. Опыт показывает: первый прогон пропускает 1–2 блокера, которые ловит второй — у автора есть слепое пятно к собственным ошибкам.
    - Особое внимание: **роли новых объектов (№532)**, **чтение внутри транзакции (№783)**, **UUID в `producedTypes`** — это «провальные» категории.

## Полный текст: Принципы эксперта

| Принцип | Что значит | Как проверять |
|---|---|---|
| **Логика в правильном слое** | Форма — UI, сервер — данные/бизнес-логика | скил `1c-arch-checklist` §1 |
| **Не дублируй** | Сначала `grep` по БСП и прикладным модулям, потом пиши | скил `1c-arch-checklist` §2 |
| **Думай об отказе** | Что если сервис упал, пользователь прервал, двое одновременно? | скил `1c-arch-checklist` §5 |
| **Каждое `ГДЕ` в индекс** | Производительность — сразу, не «потом» | скил `1c-arch-checklist` §6 |
| **Комментарий = «почему»** | «Что» видно из кода; комментарий объясняет намерение | правило 9 этапа 2 |
| **Код для читателя** | Пишется 1 раз, читается 100; < 50 строк, осмысленные имена | скил `1c-arch-checklist` §7 |
| **Обход стандарта — обоснован** | Если отступил от правила — комментарий с причиной | правило 9 этапа 2 |

## Полный текст: Соглашения об именовании

- Новые объекты — **только с префиксом проекта** (узнать у пользователя).
- **Буква `ё` в именах метаданных ЗАПРЕЩЕНА** (только в пользовательских текстах можно).
- Переменные — `ВерблюжийРегистр` с заглавной: `НомерДокумента`, `ТекущийПользователь`.
- Булевы — с вопроса: `ЭтоНовый`, `МожноРедактировать`.
- Венгерская нотация и префиксы `п`, `тз`, `вт`, `стр` — **ЗАПРЕЩЕНЫ**.
- Функции начинаются с глагола: `Получить…`, `Установить…`, `Проверить…`.
- Временные таблицы в запросах — с префикса `Вр`.

## Полный текст: Поисковые шаблоны (grep-рецепты)

```bash
# кто ссылается на объект
grep -rn "<Префикс>ИмяОбъекта" <путь к src> --include=*.bsl

# все движения документа (в коде)
grep -n "Движения\." Documents/<Префикс>Имя/ObjectModule.bsl

# подписки на события (неявная логика)
ls EventSubsystems | grep <Префикс>

# оглавление большого модуля
grep -n "^Процедура\|^Функция\|^#Область" Module.bsl

# все общие модули с данным глаголом в имени
grep -rn "Функция.*Получить" CommonModules --include=*.bsl | grep <Префикс>

# дубликаты UUID в .mdo (UUID глобальны — здесь простой uniq корректен)
grep -oE 'uuid="[0-9a-f-]+"' Объект.mdo | sort | uniq -d

# проверки диагностик BSL LS в коде (если есть)
grep -rn "bslls:\|acc:" --include=*.bsl
```
