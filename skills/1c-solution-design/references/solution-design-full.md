# Проектирование: полный регламент этапа

> Развёрнутые правила этапа «Проектирование» (SKILL.md `1c-solution-design`).
> Роли: функциональный архитектор + аналитик. Вход — Карточка задачи;
> выход — 02/03/04.

---

## 1. Сценарий исполнения — правила построения

### Структура

1. **Участники (роли)** — все участники процесса, включая «Систему»
   (регламентные задания, обмены, фоновые процессы).
2. **Предусловия** — что верно до начала (данные, состояния, права).
3. **Постусловия** — что верно после успешного прохождения (в т.ч. в данных:
   движения, статусы).
4. **Счастливый путь** — таблица шагов `№ | Роль | Шаг | Триггер | Описание | Результат`.
5. **Отклонения** (синоним: альтернативные потоки) — нумерация «№а» от точки
   ветвления (1а, 1б…): ошибки, отмены, пустые данные, отказы прав, конкурентный доступ.
6. **Покрытие критериев успеха** — какие шаги закрывают какой критерий из 01.

### Качество шага

| Проверка | Плохо | Хорошо |
|---|---|---|
| Наименование — один глагол? | «Нажимает "Печать" и выбирает команду "Согласование"» | Шаг «Печатает форму "Согласование"» + Описание «Нажимает "Печать"<br>Выбирает команду "…"» |
| Результат наблюдаем? | «Обрабатывает заявку» | «Заявка переведена в статус "В работе", видна у бригады» |
| Триггер — событие? | «Пользователь решает» | «Наступила дата планового ремонта» |
| Описание нужно? | 1 действие = сам шаг | прочерк; несколько действий — каждое с новой строки |
| Поведение, не реализация? | «Заполняется реквизит Статус» | «Заявка видна со статусом "В работе"» |

Правило для отклонений: для каждого шага счастливого пути спросите
«что если данные пустые / операцию отменили / то же делает другой пользователь /
внешний сервис недоступен». Хорошие критерии успеха из 01 часто уже подсказывают
ветки (критерий «пустая категория — не ошибка» = отклонение).

### Связь с BDD

Шаг сценария с поведенческой проверкой разворачивается в Gherkin (Vanessa
Automation, `1c-testing`):

```
Сценарий: <результат шага N>
  Дано <предусловие>
  Когда <действие шага N>
  Тогда <результат шага N>
```

Не каждый шаг требует BDD: юнит-проверяемая логика (расчёт, заполнение)
проверяется YaXUnit дешевле. Выбор фиксируется в матрице трассировки (04),
колонка «Проверка».

## 2. Спецификация изменений — правила

- **Источник объектов** — не выдумываются: перед добавлением в спецификацию
  нового объекта/функции выполняется чек переиспользования (`1c-arch-checklist`
  вопрос 2: grep по БСП и прикладным модулям).
- **Миграции** — отдельная строка на каждую: что переносится, чем
  (обработка/скрипт), когда запускается (до релиза / при первом старте),
  как проверяется. Миграция без проверки — не миграция.
- **Права** — на каждый новый объект: какая роль, или обоснование «доступ
  через существующую роль X» (№532, скил `1c-security`).
- **Кросс-влияние** — изменяемый объект → кто использует (impact-анализ) →
  что проверяем сверх сценария.
- **Откат** — последовательность возврата к предыдущему состоянию: данные,
  конфигурация, права. Если отката нет — писать «отката нет, причина»;
  это осознанное решение, а не умолчание.
- **Arch-checklist в шапке**: таблица «вопрос № → ответ/ссылка на раздел».
  Вопросы 1–7 — см. скил `1c-arch-checklist`.

### Взаимодействие ролей внутри этапа

1. Аналитик строит сценарий (02) по карточке.
2. Архитектор накладывает сценарий на конфигурацию: объекты, данные, права (03),
   прогоняет arch-checklist; несводимости («этот шаг некуда положить») возвращает
   аналитику на переработку сценария, а не «проталкивает».
3. Вместе строят критерии приёмки и матрицу (04).

## 3. Критерии приёмки и матрица трассировки — правила

- Один критерий успеха карточки ≥ один критерий приёмки. Часть критерия
  приёмки может быть строже критерия успеха — но не наоборот.
- Критерий приёмки формулируется как проверяемое утверждение о наблюдаемом
  поведении: «при пустой категории колонка пуста, ошибок нет».
- Колонка «Объект/код» — из 03: где критерий реализуется (форма X, модуль Y,
  запрос Z). Колонка «Проверка» — способ: ручная (шаг сценария №), unit
  (имя теста), BDD (имя сценария Vanessa).
- Матрица без пустых ячеек — DoD. Заполнение статусов:
  - внутренняя приёмка (05) проставляет статусы по всем строкам;
  - внешняя приёмка (06) подтверждает или оспаривает статусы и добавляет
    замечания в лист возврата (классификация — `1c-external-acceptance`).

---

## 4. Версионирование артефактов при возвратах

Возврат класса B изменяет проектирование: в 02/03/04 дописывается секция
«История изменений» (дата, что изменилось, почему — со ссылкой на пункт листа
возврата). Старые строки матрицы не удаляются: критерий, снятый с задачи,
помечается «перенесён в задачу \<ID\>» — так сохраняется трассировка и
аудит возвратов.

## 5. Сквозной мини-пример (продолжение задачи про категории риска)

- 02: счастливый путь из 3 шагов (открыл монитор → видит и сортирует колонки →
  открывает заявку из строки) + отклонение 2а «категория не заполнена —
  колонка пуста, не ошибка».
- 03: изменение одной формы списка; запрос ДС: колонка-ссылка без соединения +
  реквизит через явное ЛЕВОЕ СОЕДИНЕНИЕ с обычной таблицей (№732, лестница
  паттернов `1c-queries`); права не меняются; arch-checklist отвечен
  (логика не в форме); откат — вернуть форму.
- 04: три критерия приёмки ← три критерия успеха; проверки ручные + замер
  времени открытия; статус — заполняется на приёмках.
