# Критерии приёмки — <ID задачи>

> Шаблон артефакта `04-acceptance-criteria.md` (этап «Проектирование»,
> скил `1c-solution-design`). Скопируйте в `docs/delivery/<ID-задачи>/`.
> Каждый критерий — проверяемое утверждение о наблюдаемом поведении.
> Статусы: «Статус 05» заполняет внутренняя приёмка, «Статус 06» — внешняя.
> 🔴 DoD этапа: матрица без пустых ячеек (кроме статусов).

**Источники:** критерии успеха из `01-task-brief.md`; шаги из
`02-execution-scenario.md`; реализация из `03-change-spec.md`.

## Матрица трассировки и критерии приёмки

| AC-ID | Требование (FR-ID) | Критерий (проверяемо) | Шаг сценария | Объект/код (03; файл) | Проверка (ручная/unit/BDD) | Статус 05 | Статус 06 |
|---|---|---|---|---|---|---|---|
| AC-01 | FR-01 | | | | | ☐ | ☐ |
| AC-02 | FR-02 | | | | | ☐ | ☐ |

Цепочка: **FR → шаг 02 → объект/файл 03 → AC → тест/живой прогон → evidence 05
→ решение 06**. Исходную формулировку хранит 01/02; здесь не переписывайте её
без необходимости — указывайте FR-ID и только проверяемое уточнение.

### Алфавит статусов (обеих колонок)

| Пометка | Значение | Кто ставит |
|---|---|---|
| ☐ | не проверялся; блокирует передачу на внешнюю приёмку | — (начальное) |
| ✅ | проверен живым прогоном или исполняемым автотестом, соответствует | 05, 06 |
| ✅с | проверен статически; только для структуры метаданных, ролей, XML, оформления | 05 |
| ⏳ | среда/проверка недоступна: задача заблокирована (05); приёмка отложена (06) | 05, 06 |
| ❌ | не соответствует: красная строка, самовозврат класс A (05); замечание приёмщика (06) | 05, 06 |
| n/a | неприменим (строка исключена возвратом класса B) — с пояснением в истории изменений | 05/06 |

Правила заполнения:

- «Шаг сценария» — номер шага из 02 (счастливый путь или отклонение).
- «Проверка» — конкретный способ: «ручная, шаг 2», «unit: ТестИмя», «BDD:
  Сценарий <имя>» (Vanessa Automation — скил `1c-testing`). До внешней приёмки
  поведенческий AC должен быть ✅; ☐/⏳/✅с для ручной проверки блокируют гейт.
- Для CLI/библиотеки живой прогон на репозитории — полноценное evidence;
  база 1С обязательна только когда предмет задачи её использует.
- Сравнительный критерий («не хуже/не дольше, чем до изменений») — в «Проверке»
  обязательна ссылка на базлайн «до» из карточки 01 (дата, значение, условия);
  базлайна нет — критерий переформулируется в абсолютный (`1c-planning`).
- Критерий, упавший ❌ в двух раундах протокола 06, на следующей итерации
  проверяется unit/BDD-тестом: «Проверка» меняется с «ручная» на
  «unit: ИмяТеста»/«BDD: Сценарий» (правило `rework-rules`; заготовка —
  в Gherkin-секции ниже).
- Каждый FR из 01/02 должен иметь хотя бы один AC; неизвестный FR и AC без
  источника — 🔴 ошибка проектирования. Согласованное уточнение получает новый
  FR-ID и фиксируется в истории изменений.

## Gherkin (для BDD-проверок)

> Заполняется для критериев с поведенческой проверкой через UI
> (Vanessa Automation). Юнит-проверяемая логика — YaXUnit, достаточно
> имени теста в матрице.

```
Функционал: <имя области>

Сценарий: <критерий №N>
  Дано <предусловие из 02>
  Когда <действие шага из 02>
  Тогда <результат шага из 02>
```

## Порядок заполнения статусов

- **Внутренняя приёмка** (`05-internal-acceptance.md`) — заполняет «Статус 05»
  по всем строкам с evidence; ❌ — самовозврат в разработку (класс A).
- **Внешняя приёмка** (`06-acceptance-protocol.md`) — заполняет «Статус 06»,
  подтверждая (✅) или оспаривая (❌) статус 05; спорные строки → лист возврата
  с классом A/B/D (`1c-external-acceptance`); новое за пределами матрицы →
  класс C, новая задача. При решении «Отложено» — ⏳ по непроверенным строкам.
- Итоговый статус критерия — колонка «Статус 06»; пока пуста — «Статус 05».

> Формат до 0.13.0 — одна колонка «Статус» с составными записями
> («✅ статич. (05) / ⏳ интерактивно»). Новые артефакты ведутся в двух
> колонках; существующие не переписываются — `delivery_tools.py` читает оба формата.
