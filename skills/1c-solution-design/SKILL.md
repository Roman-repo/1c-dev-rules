# 1c-solution-design — Проектирование: как должно работать

> Роли этапа — **функциональный архитектор** и **аналитик**. Здесь рисуется
> чертёж: мастер на разработке строит по нему, приёмщик принимает по нему.
> Выход — три артефакта: **Сценарий исполнения**, **Спецификация изменений**,
> **Критерии приёмки** (с матрицей трассировки). Сценарий описывает
> **поведение**, а не реализацию. Этап завершается **передачей пакета на
> согласование Оркестратору** (этап 3 конвейера) — решение фиксируется в
> листе замечаний 04a (см. раздел ниже).

## Мандаты ролей

| Роль | Решает | Не решает |
|---|---|---|
| Функциональный архитектор | Как процесс ляжет на 1С: объекты, данные, права, границы подсистем; обязательно отвечает на 7 вопросов `1c-arch-checklist` | Пошаговые сценарии пользователя |
| Аналитик | Сценарии до последнего шага, отклонения, детали требований, формулировки критериев приёмки | Выбор объектов метаданных |

## Вход этапа

Карточка задачи (`01-task-brief.md`) с выполненным DoD планирования:
критерии успеха измеримы, рамки подтверждены инициатором. 🔴 Нет подтверждённой
карточки — вернитесь на `1c-planning`: проектировать под неподтверждённую цель
значит заложить возврат класса B заранее.

## Артефакт 1. Сценарий исполнения (`02-execution-scenario.md`)

Формат — таблица шагов: **Роль → Шаг → Триггер → Описание → Результат**.

```markdown
## Счастливый путь
| № | Роль | Шаг (что делает) | Триггер (когда) | Описание | Результат шага |
|---|---|---|---|---|---|
| 1 | Механик | Создаёт заявку на ремонт | Обнаружен дефект при осмотре | Выбирает оборудование<br>Описывает дефект | Черновик заявки создан |
```

Правила:

- **Шаг = один глагол-действие** (предмет шага): «Печатает форму "Заявка на
  ремонт"», «Создаёт заявку на ремонт». 🔴 Всё остальное — подробности
  механизма (кнопки, команды, поля) — переносится в Описание: не «Нажимает
  "Печать" и выбирает команду "…"», а Шаг «Печатает форму "…"» + Описание
  «Нажимает "Печать"<br>выбирает команду "…"».
- **Описание** раскрывает шаг, если он длиннее одного действия; 🔴 несколько
  действий — **каждое с новой строки** (в ячейке markdown-таблицы — `<br>`).
  Для коротких шагов — прочерк.
- **Результат шага** проверяем: по нему позже ставится ✅/❌ на приёмке.
- **Триггер** — событие, запускающее шаг (не «пользователь захотел», а что
  произошло в процессе).
- **Роль** — участник процесса; шаг может выполнять «Система» (РЗ, обмен,
  фоновое заполнение).
- 🔴 **Отклонения обязательны** (синоним: альтернативные потоки): ошибки,
  отмены, пустые данные, конкурентный доступ. «Счастливый путь — половина
  кода» — не покрытые проектированием ветки возвращаются классом B с приёмки.
- Сценарий описывает поведение «снаружи»; объекты и запросы — в спецификации.

Шаблон: `references/execution-scenario-template.md`.

## Артефакт 2. Спецификация изменений (`03-change-spec.md`)

Чертёж для разработчика: что именно меняется в конфигурации.

Обязательные секции (полный состав — в шаблоне):

- **Объекты метаданных** — новые/изменяемые, с назначением.
- **Изменения структуры данных и миграции** — реквизиты, регистры, заполнение
  существующих данных (кто и когда запускает миграцию).
- **Права и RLS** — роли на новые объекты (№532).
- **Кросс-влияние** — кто ещё использует изменяемые объекты (impact-анализ
  из `1c-arch-checklist`, вопрос 3).
- **Откат** — как вернуть состояние до изменения.

🔴 Спецификация без отвеченного `1c-arch-checklist` (7 вопросов) не проходит
DoD-гейт: ответы фиксируются в шапке спецификации.

Шаблон: `references/change-spec-template.md`.

### Архитектурные развилки — ADR

Arch-checklist (вопросы 1–3: где живёт логика, есть ли готовое, кто зависит)
вскрывает **развилки** — решения с 2+ реальными вариантами и долгими
последствиями: «документ или регистр сведений», «расширение или конфигурация»,
«общий модуль или модуль менеджера», «заимствовать с контролем или снять
с поддержки». Такая развилка фиксируется **ADR** (Architecture Decision
Record): один файл на решение — контекст, варианты, решение, причины,
последствия.

- 🔴 **ADR обязателен**, когда: выбирается «хозяин» логики или объект-носитель
  данных; выбирается механизм платформы с миграционными последствиями
  (структура данных, обмен); **меняется ранее принятое решение** (в старом
  ADR ставится статус «Заменено», в новом — ссылка на него).
- 🟡 ADR живёт **дольше задачи**: каталог `docs/architecture/adr/` проекта —
  единое место решений (SSOT). В 03 — ссылка, а не пересказ.
- Развилка без долгих последствий (один очевидный вариант) ADR не требует —
  решение фиксируется прямо в 03; пустая секция ADR в шаблоне 03
  заполняется явно: «не требуются».
- Шаблон: `references/adr-template.md`.

## Артефакт 3. Критерии приёмки + матрица трассировки (`04-acceptance-criteria.md`)

Каждый критерий успеха из карточки превращается в **проверяемый критерий
приёмки** и связывается со сценарием и реализацией:

```markdown
| № | Критерий (проверяемо) | Шаг сценария | Объект/код (03) | Проверка (ручная/unit/BDD) | Статус 05 | Статус 06 |
```

- Статусы ведутся в двух колонках: **«Статус 05»** заполняет внутренняя
  приёмка (из отчёта 05), **«Статус 06»** — внешняя (из протокола 06).
  Итоговый статус критерия — колонка 06; пока она пуста — 05. Приёмщик
  подтверждает (✅) или оспаривает (❌) статус 05, при «отложено» ставит ⏳.
- **Алфавит статусов** (легальные пометки, обеих колонок):

| Пометка | Значение | Кто ставит |
|---|---|---|
| ☐ | не проверялся | — (начальное) |
| ✅ | проверен живым прогоном, соответствует | 05, 06 |
| ✅с | проверен статически, без живой базы (evidence в 05); интерактивная проверка — на внешней приёмке | 05 |
| ⏳ | статически не проверяем — передан на внешнюю приёмку (05); не проверен, приёмка отложена (06) | 05, 06 |
| ❌ | не соответствует: красная строка, самовозврат класс A (05); замечание приёмщика (06) | 05, 06 |
| n/a | неприменим (строка исключена возвратом класса B) — с пояснением в истории изменений | 05/06 |

- 🟡 Допустимые источники критерия приёмки: критерий успеха из 01 **или**
  отклонение из 02 (пустые данные, отказы). Критерий из отклонения
  помечается «[Откл]» — трассировка на шаг 02
  обязательна, запись в историю изменений не требуется.
- 🟡 Для критериев с поведенческой проверкой удобно сразу писать Gherkin
  (`Дано/Когда/Тогда`) — готовые сценарии для Vanessa Automation (`1c-testing`).
- 🟡 Колонка «Проверка» — не навсегда: критерий, упавший ❌ в двух раундах
  протокола 06, переводится с ручной проверки на unit/BDD (правило
  `1c-delivery-gate` → `rework-rules`; Gherkin-заготовка ниже — готовый
  сценарий для Vanessa).
- 🔴 Пустая ячейка в матрице = критерий, который никто не проверяет, или
  сценарий, который никто не реализует. DoD требует матрицу без пустых ячеек.
- 🔴 Сравнительный критерий («не хуже/не дольше, чем до изменений») проверяем
  только при зафиксированном **базлайне «до»** из карточки 01 (дата, значение,
  условия) — ссылка на базлайн обязательна в колонке «Проверка». Базлайна нет —
  вернуть критерий на переформулировку в абсолютный (`1c-planning`).

Шаблон: `references/acceptance-criteria-template.md`.

## Выход этапа: передача пакета на согласование (этап 3 конвейера)

Три артефакта готовы и прошли самопроверку по мини-чек-листу — этап **не
закончен**: пакет документации утверждает Оркестратор на следующем этапе
конвейера — **«Согласование»** (участники, режимы и процедура —
`1c-delivery-gate` §0).

1. Определите режим каталога доставки: файл `_conveyor-mode.md`
   (`mode: manual` / `mode: auto`; нет файла — manual).
2. **manual** — остановитесь и предъявите Оркестратору сводку пакета:
   - суть сценария (основной путь + перечень отклонений);
   - границы спецификации (объекты метаданных из 03, что тронуто / что нет);
   - ключевые критерии приёмки и развилки, зафиксированные ADR;
   - 🔴 не начинайте код до решения. Решение и замечания Оркестратор
     фиксирует в **листе замечаний `04a-design-review.md`** (шаблон:
     `references/design-review-template.md`): «Согласовано» → этап
     «Разработка» (`1c-dispatch-gate`); «Доработать» → замечания с адресом
     возврата — **этап 2** (правка 02/03/04) или **этап 1** (до-сбор
     требований, правка 01 с повторным подтверждением инициатора), затем
     повторное согласование.
3. **auto** — 04a создаётся автоматически с решением «Согласовано», пометкой
   режима `auto` и датой; конвейер идёт дальше без остановки.

## Антипаттерны

| Антипаттерн | Чем оплачивается |
|---|---|
| Исполнитель перешёл к коду сразу после подготовки 02/03/04, без согласования | Разработка по несмотренному чертежу: переделка при первом взгляде Оркестратора; нарушение гейта 3→4 (режим manual) |
| Сценарий только «счастливый путь» | Ошибочные ветки всплывают классом B на приёмке |
| Сценарий описывает реализацию («заполняется реквизит X») | Приёмщик не может проверить: он видит поведение, не код |
| Критерии приёмки ≠ критерии успеха карточки | Принято не то, что заказывали |
| Спецификация без arch-checklist | Логика оседает в форме, нарушение №629 находится в ревью, а не в проектировании |
| Развилка «документ vs регистр» решена в разговоре и не записана | Через полгода «почему» не восстановить; следующая задача переигрывает решение заново |
| Матрица трассировки с дырами | Шаги без проверки; проверки без реализации |

## Мини-чек-лист (DoD этапа)

- [ ] Сценарий покрывает все критерии успеха; есть раздел «Отклонения»
- [ ] Каждый шаг имеет наблюдаемый результат; роли участников перечислены
- [ ] Спецификация отвечает на 7 вопросов `1c-arch-checklist`; есть откат
- [ ] Развилки с 2+ вариантами и долгими последствиями зафиксированы ADR (или в 03 явно «не требуются»)
- [ ] Критерии приёмки происходят из критериев успеха и проверяемы
- [ ] У сравнительных критериев есть базлайн «до» из 01 (ссылка в «Проверке»)
- [ ] Матрица трассировки без пустых ячеек
- [ ] Все три артефакта в каталоге доставки задачи
- [ ] Пакет 02/03/04 передан на согласование (этап 3): в manual — остановка и решение Оркестратора в листе замечаний 04a, в auto — 04a создаётся автоматически
