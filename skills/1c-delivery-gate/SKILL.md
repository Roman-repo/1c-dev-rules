# 1c-delivery-gate — маршрутизатор конвейера разработки

> **Конвейер разработки** (синоним: жизненный цикл задачи) — последовательность
> этапов доставки задачи: Планирование → Проектирование → **Согласование** →
> Разработка → Внутренняя приёмка → Внешняя приёмка → Релиз. Согласование и
> Разработка — два из семи этапов.
> Рабочий строит дом по чертежу архитектора: этот гейт следит, чтобы у задачи
> были чертежи **до** кода, чертежи были **смотрены Оркестратором** до передачи
> строителю, приёмка — **после** кода и место в релизе — **после**
> приёмки. **Открывается первым при старте любой задачи**, далее — маршрутизация по §1.

## Как пользоваться

1. Сверьте масштаб: запрос крупнее одной задачи (большая доработка, программа
   работ) — это **эпик**: сначала `1c-epic-planning` (декомпозиция на задачи),
   затем каждая задача — конвейером ниже.
2. Определите **этап** задачи (§1) — по входному сигналу и по уже имеющимся артефактам.
3. Войдите в **роль** этапа и откройте его скил — прочитав текст, не по памяти.
4. Завершите этап **артефактами**: этап без артефактов не завершён.
5. Переход дальше — только через **DoD-гейт** (§2).
6. Возврат с приёмки — по классификации §3; детали в `references/rework-rules.md`.
7. Состояние задачи и гейты сверяются скриптом плагина:
   `python3 scripts/delivery_tools.py status <каталог задачи>` (этап, статусы
   матрицы 04, согласование Оркестратора, решение протокола, следующий шаг)
   и `check <каталог>` (механическая часть DoD; ERR — блокирующее нарушение).
   Сводка всех задач и эпиков каталога доставки — `roadmap <каталог доставки>`.

## §0. Участники и этап согласования конвейера

| Участник | Кто это | За что отвечает |
|---|---|---|
| **Постановщик** (инициатор) | Человек, сформулировавший задачу | Подтверждает карточку 01 (гейт 1→2); он же приёмщик на внешней приёмке |
| **Оркестратор** | Координирует Исполнителя; сегодня — человек, с ростом возможностей ИИ — может быть агентом | Проводит этап 3 «Согласование»: решение по пакету 02/03/04 (лист замечаний 04a); управляет режимом `/auto` // `/manual` |
| **Исполнитель** | ИИ-агент (или несколько); проходит этапы конвейера по этим правилам | Артефакты этапов, код, самопроверка; 🔴 **не начинает код до «Согласовано» в 04a в режиме manual** |

**Этап 3 «Согласование»** — живая точка контроля между чертежами и кодом:

- Вход: пакет 02/03/04 с выполненным DoD проектирования. Исполнитель
  предъявляет Оркестратору сводку пакета (сценарий, границы спецификации,
  критерии приёмки, развилки ADR).
- Оркестратор принимает решение и фиксирует его в **листе замечаний
  `04a-design-review.md`**: «Согласовано» → этап «Разработка»; «Доработать» →
  таблица замечаний с адресом возврата: **этап 2** (правка 02/03/04) или
  **этап 1** (до-сбор требований — правка 01, повторное подтверждение
  инициатора). После правки — повторное согласование тем же файлом.
- **Режимы согласования** — как проходит этап 3:
  - **manual** (по умолчанию): Исполнитель **останавливается** и ждёт решения
    Оркестратора; код не начинается до «Согласовано» в 04a.
  - **auto**: 04a создаётся автоматически с решением «Согласовано», пометкой
    режима и датой, конвейер идёт без остановки. Ответственность за пропуск
    живого согласования — на Оркестраторе, включившем режим.
  - Режим хранится в файле `<каталог доставки>/_conveyor-mode.md`
    (`mode: manual` / `mode: auto`), персистентен между сессиями. В ZCode
    управляется командами плагина `/auto` и `/manual`; нет файла — действует
    manual. Режим каталога выводится в `delivery_tools.py status/check`.

🔴 **Непрерывный прогон «документация → код» без согласования в manual —
нарушение гейта 3→4**, а не ускорение: разработка по несмотренному чертежу
оплачивается возвратом класса B (дороже сразу остановиться).

## §1. Карта этапов: роль → скил → артефакты

| № | Этап | Роль участника | Скил | Артефакты-выходы (обязательные) |
|---|---|---|---|---|
| 1 | **Планирование** | Руководитель проекта | `1c-planning` | `01-task-brief.md` — Карточка задачи |
| 2 | **Проектирование** | Функциональный архитектор + аналитик | `1c-solution-design` | `02-execution-scenario.md`, `03-change-spec.md`, `04-acceptance-criteria.md` |
| 3 | **Согласование** | Оркестратор (решение) + Исполнитель (сводка пакета) | `1c-delivery-gate` §0 | `04a-design-review.md` — Лист замечаний (решение + замечания с адресом возврата) |
| 4 | **Разработка** | Разработчик | `1c-dispatch-gate` + тематические | Код + прогон `1c-thin-triggers`, `1c-code-review`, `validate-new-object.sh` |
| 5 | **Внутренняя приёмка** | Разработчик в роли тестировщика | `1c-internal-acceptance` | `05-internal-acceptance.md` — отчёт по прогону сценария |
| 6 | **Внешняя приёмка** | Приёмщик (инициатор задачи) | `1c-external-acceptance` | `06-acceptance-protocol.md` (+ `06a-rework-list.md` при возврате) |
| 7 | **Релиз** | РП / релиз-инженер | `1c-release` | `release-manifest.md` + `release-notes.md` (на релиз, не на задачу) |

**Уровень выше — эпики.** Запрос дороже одной задачи (оценка L/XL, несколько
ролей/подсистем/релизов) — это **эпик**: `1c-epic-planning` создаёт карточку
эпика (`00-epic-brief.md`) и декомпозирует инициативу на задачи — каждая
проходит этот конвейер отдельно и связывается с эпиком полем «Эпик» в
карточке 01. Сводка состояния всех задач каталога доставки —
`delivery_tools.py roadmap`.

**Терминология.** «Планирование до кода» в `1c-dispatch-gate` (локализация объектов, arch-checklist) — это **вход этапа 4 «Разработка»**, а не этап 1. Этап 1 отвечает «что и зачем», этап 2 — «как должно работать», этап 3 — «согласовано ли Оркестратором», этап 4 — «как написано».

**Роль участника ≠ роль доступа.** Роль в этой карте — участник процесса (кто принимает решения этапа). Роли доступа 1С (права, RLS) — скил `1c-security`. Если в задаче обе — пишите «роль участника»; права описываются в спецификации изменений.

**Шляпы.** В малой команде один человек носит несколько ролей. Это допустимо, но артефакты раздельные: надев шляпу приёмщика, разработчик проверяет против сценария, а не «по памяти о том, что писал».

## §2. DoD-гейты (условия перехода)

| Переход | Условие — Definition of Done предыдущего этапа |
|---|---|
| 1 → 2 | Карточка задачи заполнена целиком; критерии успеха измеримы; инициатор подтвердил цель, рамки и критерии |
| 2 → 3 | Сценарий покрывает **все** критерии успеха (счастливый путь + отклонения); спецификация прошла `1c-arch-checklist`; критерии приёмки проверяемы; в матрице трассировки нет пустых ячеек; Исполнитель подготовил сводку пакета для Оркестратора |
| 3 → 4 | 🔴 В листе замечаний 04a решение Оркестратора **«Согласовано»** (режим/дата заполнены); при «Доработать» — замечания отработаны, адреса возврата (этап 2 / этап 1) закрыты, согласование повторено. В режиме auto 04a создаётся автоматически (§0) |
| 4 → 5 | Код прошёл `1c-thin-triggers` и `1c-code-review`; изменения не вышли за «Объекты метаданных» спецификации 03 (расширение состава — согласовано и внесено в 03); `validate-new-object.sh` без FAIL (каждое необъяснённое FAIL — возврат в разработку) |
| 5 → 6 | Все шаги сценария пройдены ✅ или отклонения согласованы; заявленные тесты зелёные; evidence приложен к отчёту |
| 6 → 7 | Протокол «принято»; блокирующих замечаний нет |
| 7 → закрытие | Состав релиза сверен с протоколами приёмки; примечания готовы; миграции описаны; ретроспектива карточки задачи заполнена (оценка/факт, возвраты, вывод) |

**Правило:** переход с невыполненным DoD — это долг. Долг на переходе оплачивается возвратом класса B на внешней приёмке: дороже сразу остановиться.

## §3. Возвраты с приёмки — классификация

| Класс | Суть замечания | Куда возвращаем |
|---|---|---|
| **A** | Работает не по сценарию/спецификации — дефект разработки | Этап 4 «Разработка» |
| **B** | Сценарий/спецификация неверны или неполны; задачу поняли не так | Этап 2 «Проектирование»: обновить 02/03/04, доработать только затронутую часть |
| **C** | Новое требование, которого нет в рамках карточки | 🔴 **Не возврат** — новая задача. «Возврат ≠ расширение рамок» |
| **D** | Косметика (текст, подписи, опечатки) | Этап 4 «Разработка», быстрый цикл без полного перепрогона |

Жизненный цикл возврата, формат листа возврата, повторная приёмка — `references/rework-rules.md`.

## Хранение артефактов

По умолчанию — `docs/delivery/<ID-задачи>/` в репозитории проекта: артефакты 01–06 (+04a согласование, +06a). Карточка эпика — `docs/delivery/EP-NNN-<slug>/00-epic-brief.md` (уровень над конвейером, `1c-epic-planning`); задачи эпика — обычные каталоги задач, связанные полем «Эпик» в 01. Релизовые артефакты — `docs/delivery/_releases/<версия>/` (релиз группирует несколько задач). Режим согласования конвейера (§0) — файл `docs/delivery/_conveyor-mode.md` на весь каталог доставки. Проект может переопределить путь в `AGENTS.md` — тогда используется проектный путь. Артефакт создаётся копированием шаблона из `references/` этапного скила.

## Мини-чек-лист

- [ ] Этап определён по §1; роль этапа принята; скил этапа прочитан текстом
- [ ] Входные артефакты предыдущего этапа существуют и его DoD выполнен
- [ ] Артефакты этапа созданы по шаблону в проектном каталоге доставки
- [ ] DoD-гейт (§2) пройден до перехода на следующий этап
- [ ] Переход 3→4: этап «Согласование» пройден — в 04a решение «Согласовано» (в manual — живое решение Оркестратора, в auto — автоматическое)
- [ ] `delivery_tools.py check` по каталогу задачи — без ERR (машиночитаемая часть DoD)
- [ ] При возврате: класс замечаний определён (A/B/C/D), лист возврата создан
