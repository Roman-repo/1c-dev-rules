# 1c-delivery-gate — маршрутизатор конвейера разработки

> **Конвейер разработки** (синоним: жизненный цикл задачи) — последовательность
> этапов доставки задачи: Планирование → Проектирование → Разработка →
> Внутренняя приёмка → Внешняя приёмка → Релиз. Разработка — один этап из шести.
> Рабочий строит дом по чертежу архитектора: этот гейт следит, чтобы у задачи
> были чертежи **до** кода, приёмка **после** кода и место в релизе **после**
> приёмки. **Открывается первым при старте любой задачи**, далее — маршрутизация по §1.

## Как пользоваться

1. Определите **этап** задачи (§1) — по входному сигналу и по уже имеющимся артефактам.
2. Войдите в **роль** этапа и откройте его скил — прочитав текст, не по памяти.
3. Завершите этап **артефактами**: этап без артефактов не завершён.
4. Переход дальше — только через **DoD-гейт** (§2).
5. Возврат с приёмки — по классификации §3; детали в `references/rework-rules.md`.

## §1. Карта этапов: роль → скил → артефакты

| № | Этап | Роль участника | Скил | Артефакты-выходы (обязательные) |
|---|---|---|---|---|
| 1 | **Планирование** | Руководитель проекта | `1c-planning` | `01-task-brief.md` — Карточка задачи |
| 2 | **Проектирование** | Функциональный архитектор + аналитик | `1c-solution-design` | `02-execution-scenario.md`, `03-change-spec.md`, `04-acceptance-criteria.md` |
| 3 | **Разработка** | Разработчик | `1c-dispatch-gate` + тематические | Код + прогон `1c-thin-triggers`, `1c-code-review`, `validate-new-object.sh` |
| 4 | **Внутренняя приёмка** | Разработчик в роли тестировщика | `1c-internal-acceptance` | `05-internal-acceptance.md` — отчёт по прогону сценария |
| 5 | **Внешняя приёмка** | Приёмщик (инициатор задачи) | `1c-external-acceptance` | `06-acceptance-protocol.md` (+ `06a-rework-list.md` при возврате) |
| 6 | **Релиз** | РП / релиз-инженер | `1c-release` | `release-manifest.md` + `release-notes.md` (на релиз, не на задачу) |

**Терминология.** «Планирование до кода» в `1c-dispatch-gate` (локализация объектов, arch-checklist) — это **вход этапа 3 «Разработка»**, а не этап 1. Этап 1 отвечает «что и зачем», этап 2 — «как должно работать», этап 3 — «как написано».

**Роль участника ≠ роль доступа.** Роль в этой карте — участник процесса (кто принимает решения этапа). Роли доступа 1С (права, RLS) — скил `1c-security`. Если в задаче обе — пишите «роль участника»; права описываются в спецификации изменений.

**Шляпы.** В малой команде один человек носит несколько ролей. Это допустимо, но артефакты раздельные: надев шляпу приёмщика, разработчик проверяет против сценария, а не «по памяти о том, что писал».

## §2. DoD-гейты (условия перехода)

| Переход | Условие — Definition of Done предыдущего этапа |
|---|---|
| 1 → 2 | Карточка задачи заполнена целиком; критерии успеха измеримы; инициатор подтвердил цель, рамки и критерии |
| 2 → 3 | Сценарий покрывает **все** критерии успеха (основной + альтернативные потоки); спецификация прошла `1c-arch-checklist`; критерии приёмки проверяемы; в матрице трассировки нет пустых ячеек |
| 3 → 4 | Код прошёл `1c-thin-triggers` и `1c-code-review`; `validate-new-object.sh` без FAIL (каждое необъяснённое FAIL — возврат в разработку) |
| 4 → 5 | Все шаги сценария пройдены ✅ или отклонения согласованы; заявленные тесты зелёные; evidence приложен к отчёту |
| 5 → 6 | Протокол «принято»; блокирующих замечаний нет |
| 6 → закрытие | Состав релиза сверен с протоколами приёмки; примечания готовы; миграции описаны |

**Правило:** переход с невыполненным DoD — это долг. Долг на переходе оплачивается возвратом класса B на внешней приёмке: дороже сразу остановиться.

## §3. Возвраты с приёмки — классификация

| Класс | Суть замечания | Куда возвращаем |
|---|---|---|
| **A** | Работает не по сценарию/спецификации — дефект разработки | Этап 3 «Разработка» |
| **B** | Сценарий/спецификация неверны или неполны; задачу поняли не так | Этап 2 «Проектирование»: обновить 02/03/04, доработать только затронутую часть |
| **C** | Новое требование, которого нет в рамках карточки | 🔴 **Не возврат** — новая задача. «Возврат ≠ расширение рамок» |
| **D** | Косметика (текст, подписи, опечатки) | Этап 3 «Разработка», быстрый цикл без полного перепрогона |

Жизненный цикл возврата, формат листа возврата, повторная приёмка — `references/rework-rules.md`.

## Хранение артефактов

По умолчанию — `docs/delivery/<ID-задачи>/` в репозитории проекта: артефакты 01–06 (+06a). Релизовые артефакты — `docs/delivery/_releases/<версия>/` (релиз группирует несколько задач). Проект может переопределить путь в `AGENTS.md` — тогда используется проектный путь. Артефакт создаётся копированием шаблона из `references/` этапного скила.

## Мини-чек-лист

- [ ] Этап определён по §1; роль этапа принята; скил этапа прочитан текстом
- [ ] Входные артефакты предыдущего этапа существуют и его DoD выполнен
- [ ] Артефакты этапа созданы по шаблону в проектном каталоге доставки
- [ ] DoD-гейт (§2) пройден до перехода на следующий этап
- [ ] При возврате: класс замечаний определён (A/B/C/D), лист возврата создан
