# Правила возвратов с приёмки

> Возврат — нормальная часть цикла, а не провал. Провал — возврат без
> классификации: он бьёт по неверному этапу и размывает рамки задачи.
> Классификация (A/B/C/D) — в §3 SKILL.md; здесь — детали и порядок работы с возвратами.

---

## Примеры классов (для калибровки)

| Класс | Пример замечания | Куда и почему |
|---|---|---|
| **A** | «По сценарию шаг 3 — заявка должна закрываться автоматически, а закрывается руками» | Разработка: сценарий правильный, код ему не соответствует |
| **A** | «Колонка есть, но пустая для существующих данных» | Разработка: миграция/заполнение из спецификации не выполнено |
| **B** | «В сценарии нет ветки, когда согласующий отклоняет заявку — а это половина случаев» | Проектирование: сценарий неполон; обновить 02/03/04, доработать затронутое |
| **B** | «Мы имели в виду не это: критичность должна считаться по другому правилу» | Проектирование: цель понята неверно — карточка и сценарий перепроверяются с инициатором |
| **C** | «А удобно было бы ещё выгрузлять это в Excel» | Новая задача: в рамках карточки выгрузки нет. 🔴 Не подвешивать в этот возврат |
| **D** | «Подпись в печатной форме — ООО „Ромашка“, без кавычек-ёлочек» | Разработка, быстрый цикл: точечная правка + перепроверка затронутого шага |

Калибровочное правило: **класс — это этап, где ошиблись**, а не этап, где
сделали работу. Если правильный сценарий реализован неправильно — A. Если
сценарий сам неправильный — B. Если сценария этого вообще не должно было быть — C.

## Жизненный цикл возврата

1. **Фиксация.** Каждое замечание — строкой в лист возврата (`06a-rework-list.md`):
   номер, формулировка (цитата приёмщика), класс A/B/C/D, целевой этап, что сделать.
2. **Класс C — сразу в сторону.** Новая карточка задачи (`1c-planning`); в протоколе
   приёмки — пометка «вынесено в задачу \<ID\>». Возврат не расширяет рамки.
3. **Класс B — сначала проектирование.** Обновляются 02/03/04 (с записью в «Историю
   изменений» артефакта), при необходимости — уточнение карточки с инициатором.
   Затем разработка **только затронутой части**. Полный перепрогон сценария —
   по решению проектировщика, но отклонения вокруг изменений — обязательно.
4. **Класс A — разработка.** Правка + перепрогон затронутых шагов + ревью-прогоны
   (`1c-thin-triggers`, `1c-code-review`) на изменённом коде.
   🔴 **Один и тот же критерий упал ❌ дважды** (два раунда протокола 06) —
   следующая итерация закрывает его **unit/BDD-тестом**, а не третьей ручной
   проверкой: колонка «Проверка» матрицы 04 меняется с «ручная» на
   «unit: ИмяТеста»/«BDD: Сценарий» (Gherkin-заготовка — в 04; `1c-testing`);
   падение теста на внутренней приёмке = красная строка 05. Ручная проверка
   дважды пропустила одно и то же — третья попытка не изменит исход.
5. **Класс D — быстрый цикл.** Точечная правка без полного ревью; внутренний
   перепрогон затронутого шага.
6. **Повторная приёмка — по листу возврата.** Проверяются пункты возврата и
   изменённые критерии (если B менял 04), а не вся задача с нуля. Исходный
   протокол не перезатирается: решение «возврат» → после исправления новый
   протокол со ссылкой на лист возврата.

## Счётчики и сигналы здоровья

| Сигнал | Интерпретация |
|---|---|
| Возвраты класса B по одной задаче ≥ 2 | Проектирование формально: сценарий пишется «под решение». Остановиться и перепроектировать |
| Один критерий ❌ в двух раундах протокола | Ручная проверка не держит поведение: регресс вернётся в третий раз — перевод на unit/BDD обязателен (жизненный цикл возврата, п. 4) |
| Класс C давится в возврат вместо новой задачи | Рамки карточки не работают — инициатор не подтверждал их всерьёз |
| Внутренняя приёмка красная, но задача сдаётся | Этап 5 превращается в фикцию: сдавать только с зелёным отчётом или согласованными отклонениями |
| Повторная приёмка проверяет «всё с нуля» | Лист возврата не ведётся — этап не закрыт формально, время приёмщика тратится впустую |

Счётчики возвратов фиксируются в секции «Ретроспектива» карточки задачи (01)
при закрытии — поле «Возвраты» (A/B/C/D; C — вынесено в задачи): это честный
индикатор качества проектирования и оценки на этапе планирования, и данные
для сигналов здоровья выше.

---

## Антипаттерны

- 🔴 **«Доработаем по ходу»** — замечания класса C, принятые в возврат без новой
  карточки. Задача теряет конечность: DoD-гейты больше не работают.
- 🔴 **Возврат класса B сразу в разработку** («ну это же мелочь, пусть разработчик
  допишет»). Без обновления 02/03/04 сценарий и код расходятся — следующий
  возврат предопределён.
- 🟡 **Замечание без класса** — его невозможно проверить на повторной приёмке:
  «стало ли лучше» не бинарно.
- 🟡 **Перезатирание протокола** — теряется история приёмок; каждый протокол
  самостоятельный документ со ссылкой на предыдущий.
