# Полная карта конвейера разработки (жизненного цикла задачи)

> Развёрнутая версия §1 SKILL.md: для каждого этапа — вход, роль с мандатом,
> процедура, выход, DoD. Сквозной пример — в конце. Термин «роль» здесь —
> **роль участника процесса** (не роль доступа 1С).

---

## Сводная матрица ролей

| Этап | Роль участника | Мандат (что решает) | Что роль НЕ решает |
|---|---|---|---|
| Планирование | Руководитель проекта (РП) | Что и зачем делаем; рамки; приоритет; критерии успеха | Как реализовано |
| Проектирование | Функциональный архитектор | Как бизнес-процесс ляжет на 1С: объекты, данные, права, границы систем | Код и синтаксис |
| Проектирование | Аналитик | Сценарии исполнения до последнего шага; детали требований; критерии приёмки | Технический выбор объектов |
| Разработка | Разработчик | Как написано: код по стандартам | Что и зачем; изменение рамок |
| Внутренняя приёмка | Разработчик в роли тестировщика | Соответствие сценарию до сдачи | Пересмотр требований |
| Внешняя приёмка | Приёмщик (инициатор) | Соответствие критериям приёмки; решение «принято/возврат» | Как внутри реализовано |
| Релиз | РП / релиз-инженер | Состав релиза; готовность к поставке | Приёмка отдельных задач |

Один человек может носить несколько ролей (шляпы), но смена шляпы = смена
точки зрения: тестировщик не оправдывает код, приёмщик не смотрит код.

## Этапы

### 1. Планирование — скил `1c-planning`

- **Вход:** запрос инициатора (устно, в трекере, в письме).
- **Выход:** `01-task-brief.md` — Карточка задачи.
- **DoD:** карточка заполнена; критерии успеха измеримы; инициатор подтвердил цель, рамки, критерии.

### 2. Проектирование — скил `1c-solution-design`

- **Вход:** карточка задачи с выполненным DoD этапа 1.
- **Выход:** `02-execution-scenario.md` (Сценарий исполнения), `03-change-spec.md` (Спецификация изменений), `04-acceptance-criteria.md` (Критерии приёмки + матрица трассировки).
- **DoD:** сценарий покрывает все критерии успеха включая отклонения; спецификация прошла `1c-arch-checklist` (7 вопросов); критерии приёмки проверяемы; матрица трассировки без пустых ячеек.

### 3. Разработка — гейт `1c-dispatch-gate`

- **Вход:** артефакты этапа 2 с выполненным DoD.
- **Выход:** код в исходниках проекта + прогон самопроверки.
- **Процедура:** `1c-dispatch-gate` → тематические скилы → реализация → `1c-thin-triggers` + `1c-code-review` + `validate-new-object.sh` (для метаданных).
- **DoD:** ревью-прогоны чистые; FAIL скрипта — либо исправлен, либо объяснён в отчёте внутренней приёмки.

### 4. Внутренняя приёмка — скил `1c-internal-acceptance`

- **Вход:** код с DoD этапа 3 + сценарий (02) + критерии приёмки (04).
- **Выход:** `05-internal-acceptance.md` — Отчёт внутренней приёмки.
- **DoD:** каждый шаг сценария (счастливый путь + отклонения) пройден с фиксацией «ожидание/факт/статус/evidence»; отклонения от спецификации перечислены и обоснованы; известные ограничения зафиксированы.

### 5. Внешняя приёмка — скил `1c-external-acceptance`

- **Вход:** отчёт внутренней приёмки без красного.
- **Выход:** `06-acceptance-protocol.md`; при возврате — `06a-rework-list.md`.
- **DoD:** по каждому критерию приёмки статус ✅/❌; решение зафиксировано (принято / возврат с классом A/B/D; класс C — новая задача).

### 6. Релиз — скил `1c-release`

- **Вход:** задачи с протоколом «принято».
- **Выход:** `release-manifest.md` + `release-notes.md` в каталоге релиза.
- **DoD:** состав сверен с протоколами (в релиз — только принятое); миграции суммированы из спецификаций; примечания для пользователей и админов готовы; техническая сборка — по чек-листу `1c-collab`; ретроспектива карточки задачи (01) заполнена — оценка/факт, возвраты A/B/C/D, вывод.

## Артефакты и нумерация

```
docs/delivery/
├── <ID-задачи>/
│   ├── 01-task-brief.md            ← Планирование
│   ├── 02-execution-scenario.md    ← Проектирование
│   ├── 03-change-spec.md           ← Проектирование
│   ├── 04-acceptance-criteria.md   ← Проектирование
│   ├── 05-internal-acceptance.md   ← Внутренняя приёмка
│   ├── 06-acceptance-protocol.md   ← Внешняя приёмка
│   └── 06a-rework-list.md          ← только при возврате
└── _releases/
    └── <версия>/
        ├── release-manifest.md     ← Состав релиза
        └── release-notes.md        ← Примечания к релизу
```

Правила:

- Номер = порядок ЖЦ; создаётся копированием шаблона из `references/` этапного скила.
- Артефакт живёт в проекте, шаблон — в плагине (принцип слоёв).
- Артефакт обновляется **на месте** с секцией «История изменений» внизу: при возврате класса B в 02/03/04 дописывается, что и почему изменилось (аудит возвратов).
- Матрица трассировки в 04 — мост между этапами: «Статус 05» заполняет внутренняя приёмка, «Статус 06» — внешняя; итоговый статус — колонка 06 (алфавит статусов — `1c-solution-design`).

### Механическая сверка конвейера

Скрипт плагина `scripts/delivery_tools.py` выводит состояние задачи из самих
артефактов (отдельный файл состояния не заводится — он может разойтись с
артефактами):

- `python3 scripts/delivery_tools.py status <каталог задачи>` — этап, статусы
  матрицы 04 (✅/статич./⏳/❌), красные строки 05, решение протокола 06,
  черновик/состав релиза, следующий шаг; для «Отложено» — текст возобновления
  из протокола;
- `python3 scripts/delivery_tools.py check <каталог задачи>` — машиночитаемая
  часть DoD-гейтов: наличие артефактов, подтверждение инициатора в 01, пустые
  ячейки матрицы 04, красные строки и вердикт 05, решение 06 (при «Возврат» —
  наличие 06a), «принято» в составе боевого релиза. Exit 1 — есть ERR.

Код и ревью-прогоны (гейт 3→4) скрипту недоступны — их статусы фиксируются
в шапке 05 и проверяются по ней.

## Сквозной пример (мини)

Задача: «в списке заявок нужно видеть категорию риска и критичность дефекта».

1. **Планирование.** Карточка: инициатор — руководитель службы; проблема — «критичность не видна в мониторе, решения принимаются вслепую»; критерий успеха — «в форме списка видны обе колонки, список открывается не дольше, чем до доработки (по замеру)»; вне рамок — «изменение логики расчёта критичности». Оценка S.
2. **Проектирование.** Сценарий: пользователь открывает монитор → в списке колонки «Категория риска» (ссылка) и «Критичность дефекта» (реквизит через ЛЕВОЕ СОЕДИНЕНИЕ с обычной таблицей — не точка, №732); отклонение — категория не заполнена → пусто, не ошибка. Спецификация: изменения одной формы; arch-checklist отвечен (логика не в форме — данные читает запрос списка). Критерии приёмки: 2 колонки + замер времени открытия.
3. **Разработка.** dispatch-gate: форма + ДС → `1c-forms`, `1c-queries` (лестница паттернов №732), `validate-new-object.sh` (X15 — текст запроса ДС).
4. **Внутренняя приёмка.** Прогон сценария: обе колонки, пустая категория, замер до/после. Отчёт 05.
5. **Внешняя приёмка.** Демонстрация инициатору по критериям. Принято → протокол 06.
6. **Релиз.** Задача в состав релиза; в примечаниях — строка для пользователей («в мониторе добавлены колонки…»).

## Типовые ошибки применения цикла

| Антипаттерн | Чем оплачивается |
|---|---|
| Начать разработку без карточки задачи | Scope creep: «а сделайте ещё вот это» — рамок нет |
| Сценарий только «счастливый путь» | Отклонения всплывают на приёмке (класс B) |
| Внутренняя приёмка «по памяти» | Дефекты того же класса, что и разработчик слепые зоны |
| Приёмка без критериев (04) | Спор «нравится/не нравится» вместо фактов |
| Возврат класса C как «доработка» | Задача никогда не закрывается, оценка взорвана |
| В релиз — недопринятая задача «чтобы успеть» | Возврат всего релиза |
