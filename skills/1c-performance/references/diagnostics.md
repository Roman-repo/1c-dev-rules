# Диагностика инцидентов производительности на проде

> Скил `1c-performance` отвечает на вопрос «как писать быстро». Эта карточка — на вопрос
> **«на проде уже тормозит / взаимоблокировка — как найти причину по фактам, а не по ощущениям»**.

Главный принцип: **сначала замер, потом гипотеза**. Оптимизация без замера — гадание:
«узкое место» почти всегда не там, где кажется.

---

## 1. Инструменты — что для чего

| Инструмент | Когда применять | Цена |
|---|---|---|
| **Технологический журнал (ТЖ)** | Расследование на сервере: медленные запросы, блокировки, взаимоблокировки, таймауты, исключения | Замедляет сервер и ест диск — включают **точечно и выключают** после расследования |
| **Замер в коде** (`ТекущаяУниверсальнаяДатаВМиллисекундах()` до/после) | Точечный замер подозрительного участка кода | Ничтожна |
| **БСП «Оценка производительности»** (ключевые операции) | Постоянный мониторинг длительности операций в продуктиве | Мала, замеры агрегируются |
| **Замер производительности в конфигураторе / EDT** | Профилировка на стенде: какие строки/вызовы сколько заняли | Не для прода |
| **ЦУП (Центр управления производительностью)** | Постоянный APM-мониторинг крупных внедрений | Отдельная подсистема |
| **Средства СУБД** (план запроса, pg_locks, Extended Events) | Когда ТЖ показал медленный запрос — смотреть план и блокировки на стороне СУБД | Зависит от СУБД |

## 2. Технологический журнал — минимальный рабочий рецепт

ТЖ включается конфигурационным файлом `logcfg.xml` в каталоге `conf` сервера 1С
(для файловой базы — в профильном `conf` пользователя). Рестарт не нужен: настройки
подхватываются в течение минуты.

### Шаблон `logcfg.xml` под расследование «тормозит/блокировки»

```xml
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="D:\1clogs\incident" history="4">
    <!-- медленные запросы к СУБД (для PostgreSQL — DBPOSTGRS, для файловой — DBV8DBENG) -->
    <event><eq property="name" value="DBMSSQL"/></event>
    <!-- ожидания управляемых блокировок 1С -->
    <event><eq property="name" value="TLOCK"/></event>
    <!-- взаимоблокировки на уровне менеджера БД 1С -->
    <event><eq property="name" value="TDEADLOCK"/></event>
    <!-- таймауты ожидания блокировок -->
    <event><eq property="name" value="TTIMEOUT"/></event>
    <!-- исключения (куда смотреть при «ошибках под нагрузкой») -->
    <event><eq property="name" value="EXCP"/></event>
    <property name="all"/>
  </log>
</config>
```

Ключевое в шаблоне:

- **`history="4"`** — глубина хранения в часах. Без ограничения ТЖ за день съест диск.
- Включаются **только нужные события**. «Включить всё» на продуктивном сервере — само по себе инцидент.
- У событий есть свойство **`Duration` (микросекунды)** — по нему ищут «тяжёлые» экземпляры.

### Как читать выгрузку

Файлы `rphost_*.log` (по одному на рабочий процесс, ротация каждую минуту). Формат строки:
`мин:сек.мкс-длительность_мкс,ИМЯ_СОБЫТИЯ,уровень,свойства...`.

1. **Топ медленных запросов:** отобрать строки `DBMSSQL` с большой длительностью — например
   `grep ",DBMSSQL," rphost_*.log | awk -F'[-,]' '$2+0 > 10000000'` (всё дольше 10 с;
   поле 2 — длительность в мкс после дефиса) или отсортировать по длительности любым скриптом.
2. **Сопоставить запрос с кодом:** в свойствах события есть текст `Sql` и контекст
   (`t:applicationName`, `Usr`, `SessionID`, `t:connectID`). По фрагменту SQL — `grep` по проекту.
3. **Блокировки:** `TLOCK` показывает, кто кого ждёт (свойства `Regions`/`Locks` и пара
   «ожидающий ↔ держатель»); `TDEADLOCK` — участников взаимоблокировки и жертву.
4. **Не забыть выключить** ТЖ после расследования (удалить/закомментировать `logcfg.xml`).

⚠️ Точный набор имён свойств зависит от версии платформы и СУБД — при расхождении
сверяйтесь с документацией на технологический журнал своей версии.

## 3. Сценарии расследования

### 3.1. «Всё тормозит периодически»

1. Включить ТЖ (шаблон выше) на период воспроизведения.
2. Взять топ-10 `DBMSSQL` по суммарной длительности — обычно 2–3 запроса дают 90% времени.
3. Каждый запрос → проверить по карточке `performance-full.md`:
   без параметров ВТ (№733), соединение с подзапросом (№655), условие мимо индекса (№791/№658),
   точки к ссылкам (№725/№732).
4. План запроса на СУБД подтверждает догадку **до** правки кода.

### 3.2. «Конфликт блокировок / превышено время ожидания»

1. `TLOCK` + `TTIMEOUT` в ТЖ: определить пару «ожидающий ↔ держатель» и ресурс (регистр, диапазон).
2. Типовые корни (свериться с `1c-events-transactions`):
   - чтение данных внутри транзакции (№783) — транзакция длинная, держит блокировки;
   - блокирующее чтение остатков в начале транзакции (№661);
   - запись регистров по одной записи (№792) — много коротких блокировок;
   - избыточная блокировка шире нужного диапазона (№659).
3. Если пара «ожидающий ↔ держатель» — два проведения одного документа/регистра:
   проверить порядок наложения блокировок (везде одинаковый порядок ресурсов!).

### 3.3. «Взаимоблокировка (deadlock)»

1. `TDEADLOCK` в ТЖ: участники, жертва, ресурсы.
2. На стороне СУБД детальнее: MS SQL — system_health / Extended Events (`xml_deadlock_report`),
   PostgreSQL — `log_lock_waits` + `pg_locks`.
3. Классическое лекарство: **единый порядок обращения к ресурсам** во всех путях кода
   (сначала документ, потом регистр А, потом регистр Б — везде одинаково) + короткие транзакции (№783).

### 3.4. «Ошибки только под нагрузкой»

`EXCP` в ТЖ за период + журнал регистрации. Частый корень — обращение к данным,
изменённым параллельным сеансом (отсутствие `БлокировкаДанных` при read-modify-write,
см. `1c-events-transactions`).

## 4. Точечные замеры в коде

Для подозрительного участка — не «кажется, что медленно», а цифра:

```bsl
Начало = ТекущаяУниверсальнаяДатаВМиллисекундах();
// ... подозрительный код ...
Длительность = ТекущаяУниверсальнаяДатаВМиллисекундах() - Начало;
ЗаписьЖурналаРегистрации("Замер.РасчетОстатков", УровеньЖурналаРегистрации.Информация, , ,
    "Длительность: " + Длительность + " мс");
```

На постоянной основе (продуктив) — вместо самописных замеров использовать подсистему
БСП **«Оценка производительности»**: замеры по ключевым операциям агрегируются и видны
в APDEX-отчётах, без ручного разбора ЖР.

## 5. Анти-паттерны расследования

| ❌ Анти-паттерн | ✅ Как надо |
|---|---|
| Оптимизировать «на глаз» самый сложный запрос | Топ по фактической суммарной длительности из ТЖ |
| Держать ТЖ включённым «на всякий случай» без `history` | Включить на период воспроизведения, выключить |
| Менять код до получения плана запроса | План на СУБД подтверждает причину до правки |
| Лечить deadlock «разнесением по времени» | Единый порядок блокировок + короткие транзакции |
| Замер `ТекущаяДата()` (секунды) | `ТекущаяУниверсальнаяДатаВМиллисекундах()` |

## Мини-чек-лист расследования

- [ ] Инцидент воспроизводится (или есть логи за период инцидента)
- [ ] ТЖ включён точечно (нужные события + `history`), после — выключен
- [ ] Найден топ по фактической длительности, не «самый подозрительный»
- [ ] Запрос сопоставлен с кодом (grep по фрагменту SQL)
- [ ] Причина подтверждена планом запроса / TLOCK-парой до правки
- [ ] Правка проверена повторным замером (до/после)
