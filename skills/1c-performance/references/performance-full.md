## №487 — Минимизация серверных вызовов и трафика

**Критичность:** 🔴 Блокирующее

**Суть:** Каждый серверный вызов — это round-trip + сериализация. Группируйте операции: одна серверная процедура должна делать максимум работы, а не вызываться по разу на каждое поле формы.

❌ **Неправильно:**
```bsl
&НаКлиенте
Процедура ОрганизацияПриИзменении(Элемент)
    Подразделения = ПолучитьПодразделенияНаСервере();     // вызов 1
    Исполнители   = ПолучитьИсполнителейНаСервере();      // вызов 2
    Договоры      = ПолучитьДоговорыНаСервере();          // вызов 3
КонецПроцедуры;
```

✅ **Правильно:**
```bsl
&НаКлиенте
Процедура ОрганизацияПриИзменении(Элемент)
    Данные = ПолучитьВсеЗависимыеДанные();   // 1 вызов, возвращает Структуру
    // ... заполнение формы из Данные.Подразделения и т.д.
КонецПроцедуры;
```

🔍 Авто-проверка: `#bslls:MissingSpace` (косвенно, по структуре)
📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/487.md)
См. также: №636 (контекстный vs внеконтекстный сервер)

## №636 — Контекстная и внеконтекстная передача на сервер

**Критичность:** 🔴 Блокирующее

**Суть:** Если серверной функции не нужны реквизиты формы — используйте `&НаСервереБезКонтекста`. Контекстный вызов (`&НаСервере`) гонит через сеть **все** данные формы туда и обратно.

❌ **Неправильно:**
```bsl
&НаСервере
Функция ПолучитьМассивПодчиненных(Родитель)        // гонит всю форму
    Запрос = Новый Запрос("... ГДЕ Ссылка В ИЕРАРХИИ(&Родитель)");
    ...
КонецФункции;
```

✅ **Правильно:**
```bsl
&НаСервереБезКонтекста
Функция ПолучитьМассивПодчиненных(Родитель)        // только параметр
    ...
КонецФункции;
```

> ⚠️ **Граница правила (7-й полевой тест, кейс E'):** дорого только **клиент→сервер** обращение — именно тогда контекст гонится по сети. Серверная процедура формы, вызываемая **из серверного кода** (например, `ПодготовитьОтборСписка()` из `ПриСозданииНаСервере`), — обычный вызов в рамках одного серверного контекста, передачи формы по сети нет. Помечать такие процедуры нарушением №636 в ревью ошибочно; директиву проверяйте у процедур, вызываемых с клиента.

> 💡 **Признак правильного применения:** серверная процедура, которой форма не передаёт свой контекст, объявлена как `НаСервереБезКонтекста` — форма остаётся «лёгкой», серверный вызов не тащит данные формы.

🔍 Авто-проверка: `#bslls:UseLessServerCall`
📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/636.md)

## №642 / №755 — Длительные операции (сервер / клиент)

**Критичность:** 🔴 Блокирующее

**Суть:** Если операция рискует занять > 2–3 секунды — её **нельзя** выполнять синхронно в обработчике формы. На сервере — фоновые задания / `НачатьВыполнениеФоновогоЗадания`; на клиенте — `ВыполнитьОбработкуЗадания` с индикатором прогресса.

❌ **Неправильно:**
```bsl
&НаКлиенте
Процедура Применить(Команда)
    ПересчитатьВсеНаСервере();   // пользователь ждёт, форма замёрзла
КонецПроцедуры;
```

✅ **Правильно:**
```bsl
&НаКлиенте
Процедура Применить(Команда)
    Параметры = ...;
    Оповещение = Новый ОписаниеОповещения("ПослеПересчета", ЭтаФорма);
    НачатьВыполнениеНаСервере(Оповещение, , "ПересчитатьВсеНаСервере", Параметры);
    // форма остаётся живой, показываем прогресс
КонецПроцедуры;
```

📖 №642 [сервер](https://github.com/zeegin/v8std/blob/main/docs/std/642.md) · №755 [клиент](https://github.com/zeegin/v8std/blob/main/docs/std/755.md)
См. также: №489 (динамические списки)

## №489 — Ограничения при использовании динамических списков

**Критичность:** 🔴 Блокирующее

**Суть:** Тяжёлый динамический список тормозит всю форму. Ограничения:
- запрос должен быть «плоским» (см. №732);
- автообновление — только для списков, которые реально должны обновляться; период автообновления не короткий;
- не обновлять невидимые списки;
- условное оформление минимально.

> 💡 **Типовой сценарий:** включают автообновление сразу для **всех** динамических списков формы «по умолчанию», с коротким периодом. Это частая причина «торможения» рабочего места — автообновление включают **только** для списков, где оно реально нужно, и с не коротким периодом.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/489.md)
См. также: №732, №733

## №664 — Режим разделения итогов для регистров накопления

**Критичность:** 🟡 Важно

**Суть:** Для регистров накопления с большим оборотом включайте разделение итогов — ускоряет параллельную запись и устраняет блокировки.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/664.md)

## №708 — Разрешение итогов для периодических регистров сведений

**Критичность:** 🟡 Важно

**Суть:** Для периодических регистров сведений, по которым часто берётся `СрезПоследних`, включайте итоги среза последних — иначе СУБД каждый раз пересчитывает. Если итоги не нужны — отключайте, чтобы не тратить ресурс на их поддержку.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/708.md)

## №496 — Чтение отдельных реквизитов объекта

**Критичность:** 🔴 Блокирующее

**Суть:** Если нужно прочитать 1–3 реквизита объекта — используйте `ОбщегоНазначения.ЗначенияРеквизитовОбъекта(...)` или точечный запрос. Не `.ПолучитьОбъект()` (тянет все реквизиты и табличные части) и не разыменование через точку в цикле.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/496.md)
См. также: №648

## №491 — Влияние параметров сеанса и ФО на RLS

**Критичность:** 🔴 Блокирующее

**Суть:** Изменение параметра сеанса или ФО, влияющих на RLS (например текущая организация), вызывает **пересчёт RLS** — дорогая операция. Не менять их без необходимости; особенно не в цикле. Чтение — дёшево, запись — дорого.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/491.md)
См. также: №413, №459

## №490 — Блокировка данных объекта для редактирования из кода

**Критичность:** 🔴 Блокирующее

**Суть:** Чтобы заблокировать объект от параллельного редактирования, используйте `Документы.Имя.Заблокировать()` / метод объекта `Заблокировать()` перед изменением. Не оставлять чтение-модификация-запись без блокировки — получите потерю данных при параллельной работе.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/490.md)
См. также: №460, №659

## №659 — Избыточные блокировки

**Критичность:** 🟡 Важно

**Суть:** Не блокировать «с запасом» — каждая лишняя блокировка снижает параллельность. Блокируйте только то, что реально меняется. Используйте минимальные по охвату блокировки (по ключу, а не по таблице).

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/659.md)
См. также: №460, №661

## №661 — Блокирующее чтение остатков в начале транзакции

**Критичность:** 🔴 Блокирующее

**Суть:** В начале транзакции не делайте блокирующее чтение (`Для Изменения`) остатков, если это не строго необходимо — это создаёт «узкое место» (congestion), все транзакции выстраиваются в очередь. Сдвигайте блокирующее чтение ближе к концу транзакции или избегайте через более поздний пересчёт.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/661.md)
См. также: №460, №659

## №662 — Сдвиг границы последовательности документов

**Критичность:** 🟡 Важно

**Суть:** Если используется механизм последовательностей — проведение документа «не по порядку» сдвигает границу, что требует перепроведения. Использовать последовательности осознанно; при параллельном проведении учитывать влияние на границу.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/662.md)

## №725 — Оптимизация использования оперативной памяти

**Критичность:** 🟡 Важно

**Суть:** Не выгружать в память больше, чем нужно. `Запрос.Выполнить().Выгрузить()` всей таблицы — зло, если можно обрабатывать построчно через `.Выбрать()`. Массивы и ТЗ — очищать после использования. В больших операциях — порционная обработка.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/725.md)

## №791 — Дополнительные индексы

**Критичность:** 🟡 Важно

**Суть:** Дополнительные индексы (поля с признаком «Индексировать») — ускоряют чтение, но замедляют запись и требуют места. Добавлять осознанно, под реальные запросы. Не «индексировать всё» — это хуже, чем не индексировать.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/791.md)
См. также: №652

## №792 — Многократная запись регистров

**Критичность:** 🟡 Важно

**Суть:** Несколько записей в один регистр в одной транзакции — объединяйте в один набор записей. Не записывать **один и тот же набор** по одной строке в цикле — это умножает round-trip к СУБД.

❌ **Неправильно** (антипаттерн):
```bsl
Для Каждого Стр Из ТЗ Цикл
    Набор.Очистить();
    Набор.Добавить().Заполнить(Стр);
    Набор.Записать();   // N записей N round-trip'ов к СУБД
КонецЦикла;
```

✅ **Правильно:**
```bsl
Для Каждого Стр Из ТЗ Цикл
    Набор.Добавить().Заполнить(Стр);
КонецЦикла;
Набор.Записать();   // 1 round-trip
```

> ⚠️ **Не путать с `СоздатьМенеджерЗаписи` в цикле — это НЕ антипаттерн.**
> Запись **разных записей** через `Регистр…СоздатьМенеджерЗаписи()` + `.Записать(Истина)` в цикле — **каноничный паттерн** для регистров с параллельной записью (очереди уведомлений, логи, истории). Причина: набор записей блокирует весь регистр на время записи и затирает чужие записи при перезаписи; менеджер записи этого не делает.
>
> **Признак канона:** цикл с `СоздатьМенеджерЗаписи` + `.Записать(Истина)` сопровождается комментарием-обоснованием вида *«Записываем по одной записи, чтобы не считывать весь регистр в набор и не терять данные при параллельной записи»*.
>
> **Перед обвинением этого паттерна — `grep` по каноничным модулям проекта** (модули очередей, логов, интеграций). Если паттерн там с обосновывающим комментарием — это обоснованное отступление, не нарушение.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/792.md)

## Мини-чек-лист по производительности

- [ ] Серверные вызовы сгруппированы, нет «по одному на поле» (№487)
- [ ] Внеконтекстные серверные функции где возможно (№636)
- [ ] Тяжёлые операции вынесены в фон (№642/№755)
- [ ] Динамические списки «плоские», без ВТ/подзапросов (№489/№732)
- [ ] Параметры в `Остатки`/`СрезПоследних` (№733)
- [ ] Нет запросов в цикле (№436)
- [ ] Итоги включены там, где нужен `СрезПоследних` (№708)
