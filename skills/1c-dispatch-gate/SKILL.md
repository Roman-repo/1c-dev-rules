# 1c-dispatch-gate — маршрутизатор этапа «Разработка»

> Этот гейт отвечает за этап **«Разработка»** конвейера разработки (полный цикл задачи — `1c-delivery-gate`: Планирование → Проектирование → Разработка → приёмки → Релиз). Если задача только ставится или сдаётся/принимается — сначала `1c-delivery-gate`.
> Это точка входа в **правила разработки**: перед любой работой над кодом пройдите гейт-чек-лист и таблицу A. Другие скилы (`1c-queries`, `1c-forms`, `1c-metadata`…) открываются **после** этого шага — по результату маршрутизации.

## Как пользоваться

1. **Перед кодом/ревью** — пройдите **гейт-чек-лист** (§1). Для каждого подходящего утверждения — отметить и открыть указанные скилы.
2. **По типу работы** — сверьтесь с **таблицей A** (§2), откройте тематические скилы.
3. **В ревью** — по сигналу в коде — таблица B (§3).
4. **После написания кода** — `1c-thin-triggers` (5 слоёв построчно) и `1c-code-review`.

---

## §1. Гейт-чек-лист (обязателен до написания кода)

Для **каждого** утверждения, подходящего под задачу, — отметить и открыть указанные скилы.

| Условие задачи | Открыть скилы | Что проверить |
|---|---|---|
| ☐ Создаётся **новый объект** метаданных (справочник, документ, обработка, регистр, **константа**) | `1c-metadata` · `1c-security` | Случайные UUID (включая `typeId`/`valueTypeId`!), синоним ru/en, **роли** (№532), структура модуля |
| ☐ Создаётся/правится **форма** | `1c-forms` | 5 обязательных областей, бизнес-логика вне формы, `modifiesStoredData` |
| ☐ **Правка XML** формы/объекта (`.form`/`.mdo`) вручную | `1c-metadata` | `LineNumber`, `PagesGroupExtInfo`, `<enabled>` у Page, уникальность UUID, роли |
| ☐ Есть **запись/проведение** документа или массовая запись | `1c-events-transactions` | Шаблон транзакции, блокировки, `ПроверитьЗаполнение()` |
| ☐ **Контроль остатков** / `Остатки()` / «проведение по остаткам» / отрицательные остатки | `1c-events-transactions` · `1c-metadata` (registers-design §1) | Целевой регистр — **Balance/BalanceAndTurnovers** (на Turnovers `.Остатки()` не компилируется); паттерн «запись → `Остатки(&МоментВремени)` → Отказ» |
| ☐ Есть **запросы** | `1c-queries` | Нет запроса в цикле, перечислены поля, `СрезПоследних` с параметрами |
| ☐ **Чтение/запись данных** справочников/документов | `1c-events-transactions` · `1c-code-review` | Точечное чтение, `ЗначенияРеквизитовОбъекта` вместо `.ПолучитьОбъект()` |
| ☐ Работа с **файлами/сетью** | `1c-integration` | Только спецкаталог, таймауты, вне транзакции |
| ☐ Есть **команды формы**, модифицирующие данные | `1c-forms` | Флаг `modifiesStoredData` (Изменяет сохраняемые данные) |
| ☐ Есть **исключения/перехват** (`Попытка/Исключение`) | `1c-logging` | Логирование, не молчаливый перехват |
| ☐ Это **регламентное задание** | `1c-scheduled` | Идемпотентность, устойчивость, расписание реалистичное |
| ☐ Пишутся/ревьюятся **тесты** (YaXUnit, Vanessa Automation) | `1c-testing` | Arrange/Act/Assert, 4 типа кейсов, цели покрытия |

**Правило:** ни одно подходящее утверждение не должно остаться неотмеченным. Если отмечено — скил открыт и прочитан, а не просто «посмотрели по названию».

## §4. По симптому проблемы

| Симптом | Открыть |
|---|---|
| «Тормозит», «зависает», «долго открывается» (профилактика в коде) | `1c-performance` · `1c-queries` |
| 🔴 «Уже тормозит на проде» / «конфликт блокировок» / «взаимоблокировка» — **расследование инцидента** | `1c-performance` (+ `references/diagnostics.md`: ТЖ, замеры, TDEADLOCK) |
| «Конфликт блокировок», «deadlock» | `1c-events-transactions` |
| «Данные рассинхронизированы» | `1c-events-transactions` |
| «Форма не открывается после правки» | `1c-metadata` |
| «Оригинальный метод не выполняется в расширении» | `1c-extensions` (`ПродолжитьВызов`) |
| «Не обновляется список» | `1c-forms` · `1c-performance` |
| «Права не работают» | `1c-security` |

## Порядок работы на этапе «Разработка» (краткая выжимка)

Полная процедура — в `AGENTS.md` проекта (генерируется скилом `1c-project-bootstrap`).

### Этап 1. Подготовка к коду (вход этапа «Разработка» конвейера)
1. Локализуйте объекты по имени и префиксу через `find`/`grep`.
2. Поймите связи через карту движений проекта и поиск ссылок `grep -rn`.
3. **Прогоните этот гейт-чек-лист + arch-checklist (`1c-arch-checklist`).**
4. Откройте отобранные тематические скилы и **прочитайте их текст**, не полагайтесь на память.

> Постановка задачи («что и зачем») и проектирование («как должно работать»:
> сценарий, спецификация, критерии приёмки) — предыдущие этапы конвейера
> разработки, скилы `1c-planning` и `1c-solution-design`. Самопроверка готового
> кода перед сдачей заказчику — `1c-internal-acceptance`.

### Этап 2. Реализация
5. Пишите код по прочитанным правилам.
6. **Перед новой функцией — проверьте переиспользование** (`grep` по БСП и прикладным модулям).
7. Комментируйте «почему», а не «что».
8. 🔴 **Не выдумывайте функции.** Любая не-100%-стандартная функция должна быть определена в проекте или раскрыта через стандартные средства.
9. 🔴 **Сверяйтесь с версией платформы** (`compatibilityMode` в `Configuration.mdo`).

### Этап 3. Самопроверка
10. **Прогоните `1c-thin-triggers`** — построчно по 5 слоям.
11. **Сверьтесь с `1c-code-review`** — по секции типа изменённого объекта.
12. **🟡 Повторный прогон** — после паузы или с установкой «критик».
