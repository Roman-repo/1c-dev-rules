# 1c-testing — тестирование кода 1С

> Два инструмента покрывают два слоя проверки: **YaXUnit** — unit-тесты серверной бизнес-логики (как `JUnit` для Java), **Vanessa Automation** — BDD-сценарии на Gherkin для приёмочных тестов через UI. Стандарты v8std по тестированию не выделены отдельно — это практика инструментов, а не стандарт фирмы 1С.

## Когда какой инструмент

| Слой | Инструмент | Что проверяет |
|---|---|---|
| Серверная бизнес-логика (расчёты, заполнение, проверки) | **YaXUnit** | Функции общих модулей: вход → результат |
| Приёмочные сценарии через UI (пользователь нажал → документ провёлся) | **Vanessa Automation** | Полный цикл формы: открытие → ввод → проведение → результат |

> Источник приёмочных BDD-сценариев — Сценарий исполнения и критерии приёмки
> задачи (скил `1c-solution-design`): каждый шаг сценария разворачивается в
> `Дано/Когда/Тогда`; прогон по ним же входит во внутреннюю приёмку
> (`1c-internal-acceptance`).

## 🔴 Главное правило — Arrange / Act / Assert

Любой тест (unit или BDD-шаг) строится по одной структуре:

1. **Arrange** — подготовка данных (создать объект, заполнить параметры).
2. **Act** — вызов тестируемой функции / действие пользователя.
3. **Assert** — проверка результата.

Без одного из трёх — тест бесполезен. особенно часто забывают **Arrange** (тест зависит от состояния базы) или **Assert** (тест что-то делает, но не проверяет).

## 🟡 Naming — `Тест<Функция>_<Сценарий>`

Имя теста = тестируемая функция + сценарий. Сценарии из фиксированного набора:

- `СуществующийОбъект`, `НесуществующийОбъект`
- `НеверныйПараметр`, `ПустоеЗначение`
- `ГраничноеУсловие`

Пример: `ТестПолучениеДанныхКлиента_НесуществующийОбъект`.

## 🟡 Четыре типа кейсов на каждую функцию

Для каждой тестируемой функции — минимум по одному кейсу каждого типа:

| Тип | Что проверяет | Пример входа |
|---|---|---|
| **Happy path** | Нормальный сценарий, корректные данные | Существующий клиент с заполненными полями |
| **Edge cases** | Граничные условия | Пустая строка, 0, максимальное значение |
| **Error cases** | Невалидные данные | Несуществующая ссылка, неверный тип |
| **Boundary** | Граничные значения типов | `NULL`, `Неопределено`, пустые коллекции |

## Цели покрытия (ориентир)

| Слой кода | Цель |
|---|---|
| Экспортные функции (публичный API) | 100% |
| Бизнес-логика (расчёты, проверки) | 90% |
| Утилиты (вспомогательные функции) | 80% |
| UI-обработчики | 70% |
| **Общее покрытие** | **80%** |

## Мини-чек-лист по тесту

- [ ] Тест строится по Arrange / Act / Assert (все три блока есть)
- [ ] Имя теста — `Тест<Функция>_<Сценарий>` (для YaXUnit) или `Сценарий:` + шаги (для Vanessa)
- [ ] Покрыты 4 типа кейсов: happy / edge / error / boundary
- [ ] Assert конкретный (`ЮТест.ОжидаетЧто(...).Равно(...)`), не «выполнилось без ошибки»
- [ ] Тест не зависит от состояния базы (Arrange создаёт свои данные) или явно помечен как интеграционный
