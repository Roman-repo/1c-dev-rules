# Карточка: Тестирование кода 1С

> Практические шаблоны тестирования: unit-тесты на **YaXUnit** и BDD-сценарии на **Vanessa Automation**.
> Адаптировано из [`testing-patterns.md`](https://github.com/Desko77/claude-code-skills-1c/blob/main/rules/testing-patterns.md)
> репозитория `claude-code-skills-1c` (MIT). Стандарты v8std по тестированию не выделены отдельно —
> это ниша инструментов, а не стандартов фирмы 1С.

## Когда применять

При написании/ревью тестов для кода 1С (`**/*.bsl` в тестовых обработках/расширениях, `**/*.feature` для Vanessa Automation). Особенно — при разработке серверной бизнес-логики в общих модулях (кандидат на YaXUnit) и при проработке пользовательских сценриев через UI (кандидат на Vanessa).

## YaXUnit — Unit-тесты

### Шаблон теста

```bsl
Процедура Тест<ИмяФункции>_<Сценарий>() Экспорт

    // Arrange — подготовка данных
    // ... создать объект / заполнить параметры ...

    // Act — вызов тестируемой функции
    Результат = <ТестируемыйМодуль>.<ИмяФункции>(...);

    // Assert — проверка результата
    ЮТест.ОжидаетЧто(Результат)
        .<МетодПроверки>;

КонецПроцедуры
```

### Пример: happy path

```bsl
Процедура ТестПолучениеДанныхКлиента_СуществующийКлиент() Экспорт

    // Arrange
    Клиент = Справочники.Контрагенты.СоздатьЭлемент();
    Клиент.Наименование = "Тест";
    Клиент.Записать();

    // Act
    Данные = <МодульКлиентов>.ПолучитьДанныеКлиента(Клиент.Ссылка);

    // Assert
    ЮТест.ОжидаетЧто(Данные)
        .Свойство("Наименование").Равно("Тест");

КонецПроцедуры
```

### Пример: error case

```bsl
Процедура ТестПолучениеДанныхКлиента_НесуществующийОбъект() Экспорт

    // Arrange
    ПустаяСсылка = Справочники.Контрагенты.ПустаяСсылка();

    // Act + Assert — ожидаем исключение
    ЮТест.ОжидаетЧто(<МодульКлиентов>.ПолучитьДанныеКлиента)
        .ВыбрасываетИсключение(ПустаяСсылка);

КонецПроцедуры
```

### Assertion API — `ЮТест.ОжидаетЧто(...)`

| Метод | Что проверяет |
|---|---|
| `.Равно(Ожидаемое)` | Строгое равенство |
| `.НеРавно(Значение)` | Неравенство |
| `.Больше(Значение)` / `.Меньше(Значение)` | Сравнение чисел/дат |
| `.Между(От, До)` | Вхождение в диапазон |
| .Свойство("Имя") | Переход к проверке свойства объекта |
| `.Содержит(Значение)` | Вхождение в строку/коллекцию |
| `.Заполнено()` | Значение заполнено (не `Неопределено`, не пустая ссылка, не пустая строка) |
| .ВыбрасываетИсключение(...) | Ожидаемое исключение при вызове |

Методы можно чейн-ить: `ЮТест.ОжидаетЧто(Данные).Свойство("Сумма").Больше(0)`.

### Соглашение об именах

Формат: `Тест<ИмяФункции>_<Сценарий>`

Сценарии — из фиксированного набора:

- `СуществующийОбъект`, `НесуществующийОбъект`
- `НеверныйПараметр`, `ПустоеЗначение`
- `ГраничноеУсловие`

## Vanessa Automation — BDD-тесты

### Шаблон сценария (Gherkin)

```gherkin
Функционал: <Название функциональности>

Сценарий: <Описание сценария>

    Дано <начальное состояние>
    Когда <действие пользователя>
    Тогда <ожидаемый результат>
```

### Пример: создание заказа клиента

```gherkin
Функционал: Создание заказа клиента

Сценарий: Менеджер создаёт заказ на существующего клиента

    Дано я авторизуюсь под ролью "Менеджер"
    И открыта форма "Документ.ЗаказКлиента"

    Когда в поле "Контрагент" я выбираю "Тестовый клиент"
    И в таблице "Товары" я нажимаю кнопку "Добавить"
    И в поле "Номенклатура" я выбираю "Товар1"
    И в поле "Количество" я ввожу "10"
    И я нажимаю кнопку "Провести и закрыть"

    Тогда документ "Заказ клиента" проведён
    И в регистре "ТоварыКОтгрузке" появились записи по заказу
```

### Когда BDD, а не unit

BDD (Vanessa Automation) оправдан, когда:
- Сценарий **проходит через UI** (форма, кнопки, проведение документа) — это приёмочный тест.
- Проверяется **взаимодействие нескольких объектов** (документ + регистр + подписка).
- Требование сформулировано **на языке заказчика** («менеджер оформляет возврат» — это BDD, а не unit).

Если тестируется одна функция общего модуля (без UI) — это **unit**, пишите на YaXUnit. UI-обёртка для одного вызова функции — лишний хрупкий слой.

## Типология кейсов — четыре типа на функцию

Для каждой тестируемой функции — минимум по одному кейсу каждого типа:

| Тип | Что проверяет | Пример входа |
|---|---|---|
| **Happy path** | Нормальный сценарий, корректные данные | Существующий клиент с заполненными полями |
| **Edge cases** | Граничные условия | Пустая строка, 0, максимальное значение |
| **Error cases** | Невалидные данные | Несуществующая ссылка, неверный тип |
| **Boundary** | Граничные значения типов | `NULL`, `Неопределено`, пустые коллекции |

**Пробелы в кейсах — главная причина «тесты зелёные, баг в проде».** Happy path покрывают всегда, edge/error/boundary — часто забывают. Именно они ловят баги: что будет, если в функцию пришла пустая ссылка? `NULL` вместо даты? Пустой массив?

## Цели покрытия (ориентир)

| Слой кода | Цель покрытия | Обоснование |
|---|---|---|
| Экспортные функции (публичный API) | 100% | Это контракт модуля — должен быть покрыт полностью |
| Бизнес-логика (расчёты, проверки) | 90% | Главная ценность, максимальный охват |
| Утилиты (вспомогательные функции) | 80% | Важны, но риск ниже |
| UI-обработчики | 70% | Хрупки, часть проверяется BDD |
| **Общее покрытие** | **80%** | Реалистичный ориентир для зрелого проекта |

> Покрытие 100% везде — недостижимо и не нужно. Цель — попасть в зоны риска (бизнес-логика), а не погнаться за метрикой.

## Процесс генерации тестов из функции

При появлении новой экспортной функции:

1. **Анализ** — выпишите параметры, типы, возвращаемое значение, побочные эффекты (запись регистров, вызовы других модулей).
2. **Граничные условия** — определите, какие входные значения граничны (пустые, максимальные, NULL, неверный тип).
3. **Генерация кейсов** — по одному кейсу каждого типа (happy / edge / error / boundary).
4. **Arrange / Act / Assert** — каждый кейс оформляется по структуре.
5. **Запуск + покрытие** — прогоните тесты, сверьте покрытие с целями, исправьте упавшие.

## Чек-лист ревью теста

- [ ] Тест строится по Arrange / Act / Assert (все три блока есть)
- [ ] Имя теста — `Тест<Функция>_<Сценарий>` (YaXUnit) или `Функционал:` + `Сценарий:` (Vanessa)
- [ ] Покрыты 4 типа кейсов: happy / edge / error / boundary
- [ ] Assert конкретный (`ЮТест.ОжидаетЧто(...).Равно(...)`), не «выполнилось без ошибки»
- [ ] Тест создаёт свои данные (Arrange) или явно помечен как интеграционный
- [ ] UI-сценарий (Vanessa) — оправдан, не дублирует unit-тест
- [ ] Покрытие тестируемой функции соответствует целям из таблицы
