## №532 — Установка прав для новых объектов и полей

**Критичность:** 🔴 Блокирующее

**Суть:** Каждый новый объект метаданных (справочник, документ, регистр, **константа**) и каждое новое поле должны быть включены **минимум в одну роль** с осмысленными правами. Не оставлять «все права всем» и не оставлять без ролей совсем — иначе объект будет недоступен или, наоборот, открыт всем.

> ⚠️ **Типовая грабля:** новый объект (константа, регистр рассылки/адресатов) зарегистрирован в `Configuration.mdo`, но **не включён ни в одну роль** — стандартные пользователи его не видят (рассылка молча не уходит и т.п.). Первый прогон ревью это часто пропускает; нужна целенаправленная проверка ролей (см. M11 в скиле 1c-metadata → metadata-xml).

**Проверка после создания объекта:**

```bash
# объект присутствует хотя бы в одном Rights.rights
grep -rl "Constant.Имя\|InformationRegister.Имя\|Catalog.Имя" <путь к src>/Roles/
```

Должен вернуть хотя бы 1 файл (обычно `БазовыеПрава/Rights.rights` и/или `АдминистраторСистемы/Rights.rights`).

**Что включать для типовых случаев:**
- **Константа-настройка** → `Read` в `БазовыеПрава`; `Read+Update` в роль администратора.
- **Регистр адресатов/настроек** → `Read+Update` в `БазовыеПрава` (чтобы администратор мог заполнять); права на измерения — `View+Edit`.
- **Справочник/документ прикладной** → отдельные роли `Чтение…`/`ДобавлениеИзменение…` (как принято в проекте).

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/532.md)
См. также: №488, №689, скил 1c-metadata → metadata-xml §6 M11

## №474 — Имя, синоним, комментарий

**Критичность:** 🟡 Важно

**Суть:** У каждого объекта метаданных заполнены все три:
- **Имя** — для кода, без `ё`, CamelCase, с префиксом `<ПрефиксПроекта>`;
- **Синоним** — для пользователя, на русском (и при необходимости en/es);
- **Комментарий** — краткое назначение, особенно для нетривиальных объектов.

❌ **Неправильно:** синоним пустой (пользователь видит техническое имя).
✅ **Правильно:** `Имя = ПричиныСписанияТоваров`, `Синоним = "Причины списания товаров"`.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/474.md)

## №469 — Правила создания общих модулей

**Критичность:** 🔴 Блокирующее

**Суть:** Общий модуль создаётся под конкретную задачу, с осмысленным именем. Настроены флаги контекста (Сервер/Клиент/Внешнее соединение), глобальность, повторное использование. Не «универсальный модуль всего».

✅ **Универсальная конвенция именования общих модулей:**
- `<Домен>Сервер` — серверные функции домена (например `ТоварыСервер`);
- `<Домен>Клиент` — клиентские обёртки (`ТоварыКлиент`);
- `<Домен>ВызовСервера` — серверные для вызова с клиента (`ТоварыВызовСервера`).

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/469.md)
См. также: №486, №544

## №470 — Использование функциональных опций

**Критичность:** 🔴 Блокирующее

**Суть:** Включайте/выключайте целые блоки функциональности через функциональные опции (ФО), а не через константы-флаги в коде. ФО автоматически скрывают элементы интерфейса и поля.

✅ **Хороший пример:** `ИспользоватьЗаказы`, `ИспользоватьСкладскойУчет`, `ИспользоватьСтатусы` — все через ФО, читаются один раз в `ПриСозданииНаСервере`. Подставьте примеры ФО своего проекта.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/470.md)
См. также: №459

## №703 — Ограничение на модальные окна и синхронные вызовы

**Критичность:** 🔴 Блокирующее

**Суть:** В управляемых формах — **никаких** модальных окон и синхронных вызовов. Только асинхронные: `ПоказатьПредупреждение`, `НачатьВыполнениеНаСервере`, `ОписаниеОповещения`. Это требование веб-клиента и совместимости.

## №486 — Модуль объекта, модуль менеджера, общие модули

**Критичность:** 🔴 Блокирующее

**Суть:** Чёткое разделение:
- **Модуль объекта** — обработчики записи/проведения, логика конкретного экземпляра;
- **Модуль менеджера** — общие операции над классом объектов (печать, заполнение по умолчанию, обработчики подписок);
- **Общие модули** — переиспользуемая логика, не привязанная к объекту.
Не дублировать логику между ними; экспортные процедуры — в модуле менеджера и общих модулях.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/486.md)
См. также: №544

## №544 — Ограничения на экспортные процедуры и функции

**Критичность:** 🟡 Важно

**Суть:** Экспортные (`Экспорт`) процедуры/функции — это интерфейс модуля. Не плодите их: чем меньше экспорта, тем проще поддержка. Внутренние процедуры — без `Экспорт`. Экспортные — с описанием (№453) и стабильной сигнатурой.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/544.md)

## №550 — Имена объектов метаданных

**Критичность:** 🔴 Блокирующее

**Суть:** Имена метаданных — по смыслу, в едином стиле:
- справочники и регистры — во **множественном** числе (`Товары`, `Контрагенты`);
- документы — в **единственном** (`ПоступлениеТоваровУслуг`);
- с префиксом проекта/подсистемы (`<ПрефиксПроекта>`).
Без буквы `ё`, без пробелов, CamelCase.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/550.md)
См. также: №454, №550

## №468 — Пользовательские представления объектов

**Критичность:** 🟡 Важно

## №473 — Использование кодов (номеров) объектов

**Критичность:** 🟡 Важно

## №477 — Самодостаточность регистров

**Критичность:** 🟡 Важно

**Суть:** Запись регистра должна быть самодостаточной для чтения: не требовать для интерпретации обращения к другим таблицам. Измерения и ресурсы — полные; не «экономить» на измерениях, разбрасывая смысл по регистратору.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/477.md)

## №445 — Получение метаданных объектов

**Критичность:** 🟡 Важно

**Суть:** Для получения метаданных используйте `Метаданные()` ссылки или `Метаданные.Имя`. Не вызывайте `Метаданные()` в цикле — кэшируйте. Для массовых операций с метаданными — общие модули БСП.

## №632 — Использование констант

**Критичность:** 🟡 Важно

**Суть:** Константы — для редко меняющихся глобальных значений (основная организация, режим работы). Не использовать как хранилище часто меняющихся данных или пользовательских настроек (для настроек — БСП-механизмы). Чтение константы дёшево, запись — с пересчётом зависимостей.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/632.md)

## №633 — Активность движений

**Критичность:** 🟡 Важно

**Суть:** Для регистров накопления выбирайте «Запись в режим доступа» и активность движений осознанно. Если движения всегда нужны — активные. Если возможны черновые/неактуальные — возможность отключать. Влияет на итоги и производительность.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/633.md)

## №677 — Использование общих реквизитов

**Критичность:** 🟡 Важно

**Суть:** Общий реквизит (например `Организация`) — включается только в те объекты, где он реально нужен, через свойство «Состав». Не «во все» — это раздувает таблицы. Влияет на RLS при разделении по организациям.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/677.md)

## №704 — Использование определяемых типов

**Критичность:** 🟡 Важно

**Суть:** Определяемый тип — для полей, тип которых задаётся составом типов в конфигурации-приёмнике (например `ДокументОСнование`). Использовать, когда состав типов различается в разных поставках. Не злоупотреблять — усложняет поддержку.

📖 [Полный текст](https://github.com/zeegin/v8std/blob/main/docs/std/704.md)

## №728 — Реквизиты составного типа

**Критичность:** 🟡 Важно

**Суть:** Реквизит составного типа (может содержать ссылки разных видов) — усложняет запросы (см. №654) и индексацию. Использовать осознанно, когда это действительно нужно (например `ДокументОснование`). Если типов мало и они стабильны — лучше несколько отдельных реквизитов.

## Мини-чек-лист по метаданным

- [ ] Новый объект включён минимум в одну роль (№532)
- [ ] Имя/синоним/комментарий заполнены, без `ё`, с префиксом `<ПрефиксПроекта>` (№474)
- [ ] Общие модули с осмысленным именем и правильными флагами контекста (№469)
- [ ] Блоки функциональности — через ФО, не через константы-флаги (№470)
- [ ] Предопределённые — через механизм предопределённых (№697)
- [ ] Нет модальных окон / синхронных вызовов (№703)

## Справочное приложение: режимы конфигурации (Configuration.mdo)

> Глобальные свойства, задающие поведение всей конфигурации. С привязкой к **реальным
> значениям проекта** (проверено по `Configuration.mdo`).
>
> Источник: `1c-configuration-spec.md` §2.3 из [cc-1c-skills](https://github.com/Nikolay-Shirokov/cc-1c-skills).

### Режимы работы и совместимости

| Свойство | Значение | На что влияет |
|---|---|---|
| `compatibilityMode` | _см. в своём `Configuration.mdo`_ (типично 8.3.12 … 8.3.27) | 🔴 Главное ограничение: методы **новее `compatibilityMode`** недоступны в основной конфигурации. Проверь своё значение: `grep compatibilityMode Configuration.mdo` и сверяй с версией появления метода (правило 11 в AGENTS.md). |
| `configurationExtensionCompatibilityMode` | _см. в своём `Configuration.mdo`_ (часто новее основной) | Расширения могут использовать более новые методы, чем основная конфигурация. Проверяй отдельно — может отличаться от цели миграции (напр. основная 8.3.12, расширения 8.3.27). |
| `defaultRunMode` | `ManagedApplication` | Управляемое приложение (УФ). Обычные формы не используются. |
| `scriptVariant` | `Russian` | Код на русском. Имена объектов/методов — кириллицей. |
| `dataLockControlMode` | **`Managed`** | 🔴 Управляемые блокировки. См. скил 1c-events-transactions → locks-transactions — все блокировки пишем явно через `БлокировкаДанных`. |
| `objectAutonumerationMode` | — | Автонумерация объектов (обычно `NotAutoFree`). |
| `modalityUseMode` | (должно быть `DontUse`) | 🔴 Модальные окна запрещены (№703). Используй `Показать*` / `ОписаниеОповещения`. Если значение не `DontUse` — проверь. |
| `synchronousPlatformExtensionAndAddInCallUseMode` | — | Синхронные вызовы платформы/внешних компонент (обычно `DontUse` в УФ). |

### Назначение и использование

| Свойство | Значение в проекте | На что влияет |
|---|---|---|
| `usePurposes` | `PersonalComputer` (обычно) | Назначение: ПК / мобильное. Определяет доступные формы/команды. |
| `defaultRoles` | (зависит от конфигурации) | Роли по умолчанию — назначаются новым пользователям. |
| `defaultLanguage` | `Language.Русский` | Язык по умолчанию для пользовательских текстов. |
| `includeHelpInContents` | — | Включать ли справку в оглавление. |

### Хранилища настроек

БСП использует хранилища настроек. Ключевые:

| Свойство | Что хранит |
|---|---|
| `commonSettingsStorage` | Общие настройки |
| `reportsUserSettingsStorage` | Пользовательские настройки отчётов |
| `reportsVariantsStorage` | Варианты отчётов (вместо самописного сохранения — см. №557) |
| `formDataSettingsStorage` | Данные форм |
| `dynamicListsUserSettingsStorage` | Настройки динамических списков |

> 💡 Если нужно сохранить пользовательскую настройку — используй соответствующее хранилище
> через БСП, а не самописное сохранение в регистр/файл (№557).
