# Релиз: полный регламент этапа

> Развёрнутые правила этапа «Включение в релиз» (SKILL.md `1c-release`).
> Роль — РП / релиз-инженер. Вход — принятые задачи; выход —
> `release-manifest.md` + `release-notes.md` в каталоге релиза.

---

## Отбор задач

| Критерий включения | Проверка |
|---|---|
| Протокол приёмки «принято» | `06-acceptance-protocol.md` со ссылкой |
| «Принято с замечаниями» класса D | Включается с пометкой «косметика в следующем релизе» — если D-правка не успевает |
| Задача класса C (новая, родилась на приёмке) | Только если успела пройти свой цикл до сбора релиза — ускорять приёмку нельзя |

Правило «дешевле подождать»: одна невошедшая задача отодвигает её ценность
на следующий релиз; одна недопринятая — ставит под удар весь текущий
(откат релиза возвращает и остальные задачи).

## Разрешение конфликтов спецификаций

По всем 03 задач релиза строится таблица пересечений:

| Объект | Задачи, меняющие | Конфликт | Решение (порядок/объединение/разведение релизов) |
|---|---|---|---|

- Один объект, разные задачи — сверить секции 03 друг с другом: правки
  совместимы, если не меняют одно и то же свойство/реквизит.
- Одна миграция двумя задачами — объединить в одну (миграции в релизе
  выполняются один раз по общему списку, а не по одному на задачу).
- Конфликт неразрешим (две задачи переписывают одно поведение) — развести
  по релизам; это решение РП, зафиксированное в составе релиза.

## Свод миграций

Суммируется из секций «Изменения структуры данных и миграции» всех 03:

| Миграция | Задача-источник | Порядок | Исполнитель | Проверка после |
|---|---|---|---|---|

- Порядок учитывает зависимости (сначала справочники, потом документы,
  ссылающиеся на них; сначала структура, потом заполнение).
- Для каждой миграции — проверка после выполнения (запрос-валидатор,
  обработка сверки). Миграция без проверки в релиз не включается.
- В примечания для админов идёт: длительность, окно обновления, точка
  необратимости (после какой миграции откат только из бэкапа).

## Примечания к релизу (release-notes)

**Пользователям** — из критериев приёмки задач, языком задач:

- «В мониторе заявок добавлены колонки "Категория риска" и "Критичность
  дефекта"; список можно сортировать по ним» (не «доработана форма списка»).
- Структура: «Что нового» / «Что изменилось» / «Что временно ограничено»
  (известные ограничения из 05).
- Один пункт = одна задача; формулировка проверяется вопросом «поймёт ли
  пользователь, что ему делать по-другому?».

**Админам** — операционная готовность:

- новые роли/права — кому назначить до старта (№532);
- новые регламентные задания — включить/расписание;
- настройки/сервисные параметры;
- длительность обновления и окно; порядок миграций;
- откат: последовательность и точка необратимости; бэкап обязателен.

## Связь с техническим слоем

| Тема | Скил |
|---|---|
| Чек-лист выпуска: версия, чистая ИБ, бэкап, .cf/.cfu/.cfe, откат | `1c-collab` |
| Обновление типовой/БСП, редактируемость объектов поставщика | `1c-collab` · `1c-platform-support` |
| Расширения (CFE) в поставке | `1c-extensions` |
| Регламентные задания релиза (расписания) | `1c-scheduled` |

Артефактный слой (состав, примечания) — этот скил; технический — выше.

## После поставки

- Сверка фактического состава с манифестом (что вошло на самом деле).
- Класс D «принято с замечаниями» — задачи-хвосты заводятся сразу
  (напоминание о долге следующего релиза).
- Обращения пользователей после релиза сверяются с примечаниями: вопрос,
  ответ на который был в notes, — сигнал о качестве notes, а не о пользователе.
