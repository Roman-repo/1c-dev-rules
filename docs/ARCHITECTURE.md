# Архитектура набора 1c-dev-rules

> Документ для контрибьюторов: как устроен набор, как добавлять и править скилы, как поддерживать синхронизацию с upstream-источниками.

## Принципы

1. **Универсальность.** Скилы не содержат упоминаний конкретных конфигураций (`торо_`, `Project/Toir`). Примеры — абстрактные (`Документ.ЗаявкаНаРемонт`, `РегистрНакопления.РемонтныеРаботы`) или обезличенные. Проектная специфика — в `AGENTS.md` проекта, не здесь.

2. **Progressive disclosure.** Каждый скил = короткий `SKILL.md` (≤500 строк) с мини-сводкой и мини-чек-листом. Полные карточки — в `references/*.md`, читаются моделью по требованию. Так в system-reminder попадает только суть (описание ≤1024 симв), а детали грузятся при срабатывании.

3. **Один плагин — много скилов.** Все 30 скилов в одном плагине. Включается/выключается целиком. Это упрощает установку и versioning (одно `plugin.json`, одна версия).

4. **Слои.** Универсальные правила → здесь. Проектные карты и каноны → в `AGENTS.md` проекта. Чёткое разделение: скил не должен «знать» о конкретном проекте.

5. **Слой конвейера разработки (жизненный цикл задачи).** Кроме правил разработки есть слой конвейера доставки задачи (постановка → проектирование → согласование → разработка → внутренняя приёмка → код ревью → внешняя приёмка → релиз): `1c-delivery-gate` + 6 этапных скилов. Над конвейером — уровень эпиков (`1c-epic-planning`): инициатива дороже одной задачи декомпозируется на задачи, каждая идёт конвейером отдельно. Каждый этап отрабатывается **ролью участника** и обязан завершаться **артефактами** (шаблоны артефактов живут в `references/` этапных скилов как `*-template.md`, сам артефакт создаётся в проекте — по умолчанию `docs/delivery/<ID-задачи>/`). Артефакт — тоже «правило»: его поля ведут исполнителя этапа. Участники: Постановщик (инициатор), Оркестратор (координирует Исполнителя, проводит этап согласования), Исполнитель (ИИ-агент), Ревьюер (второй программист / техлид; проводит этап код ревью). Две живые точки контроля: этап 3 «Согласование» (0.19.0) — решение Оркестратора по пакету 02/03/04 фиксируется в артефакте 04a «Лист замечаний» (возврат — на этап 2 или до-сбор требований на этап 1); этап 6 «Код ревью» (0.23.0) — решение Ревьюера по коду после чистой внутренней приёмки фиксируется в артефакте 05a «Лист код-ревью» (проверка по чек-листу `1c-code-review` и каталогу правил checkbsl в его `references/checkbsl/` — генерируется `scripts/harvest_checkbsl.py`; возврат — на этап 4). В режиме `manual` (по умолчанию, файл `_conveyor-mode.md` в каталоге доставки, действует на оба живых гейта) — остановка и живое решение, в режиме `auto` — автоматически (команды плагина `/auto` и `/manual` в `commands/`). Машиночитаемая часть DoD-гейтов и сводка состояния задачи проверяются скриптом `scripts/delivery_tools.py` (`status`/`check`; сводка всех задач и эпиков каталога — `roadmap`) — состояние выводится из артефактов и не дублируется отдельным файлом.

## Формат SKILL.md

**Frontmatter** (YAML между `---`):

```yaml
---
name: 1c-queries                  # совпадает с именем каталога, kebab-case
description: >                    # ОБЯЗАТЕЛЬНО, ≤1024 симв; главное в первых ~250
  Запросы 1С, СКД, динамические списки. Use when writing or reviewing query/DCS/
  dynamic-list code: №733 (СрезПоследних с параметрами), №655 (нет ВТ в соединении),
  №436 (нет запроса в цикле). Чек-лист в конце.
when_to_use: >                    # опц., дополнительные триггеры
  При написании или ревью запросов, схем СКД, динамических списков. Триггеры:
  "СрезПоследних", "Остатки(", "ЛЕВОЕ СОЕДИНЕНИЕ", "ВЫБРАТЬ *".
license: MIT
---
```

**Тело** (markdown, ≤500 строк):

```markdown
# <Тема>

## Краткая сводка правил
[3-5 ключевых стандартов с 1-строчной сутью каждого]

## Мини-чек-лист
- [ ] правило 1
- [ ] правило 2
...

## Детали (читать по необходимости)
- references/<file>.md — что в нём
- references/<file>.md — что в нём
```

## Триггеры скилов

ZCode показывает модели в system-reminder только `name` + первые ~250 симв `description`. Модель решает, вызывать скил или нет. Поэтому:

- **`description`** — главный триггер. Пишите «Use when…» и перечисляйте конкретные стандарты/сигналы. Без этого скил under-triggers.
- **`when_to_use`** — подстраховка с явными сигналами (ключевые слова, имена процедур). В индекс скилов ZCode НЕ попадает — рассчитывайте, что сработать может только то, что в `description`.
- **Первые 250 симв — критичны.** Не начинайте с воды («Этот скил предназначен для…»), сразу суть: «Запросы 1С, СКД. Use when…». Структура: тема → «Use when» → «Триггеры» (слова-триггеры — в конце НЕ размещать: хвост обрезается).
- **Целевое состояние — `description` ≤250 симв (0 WARN валидатора).** Предупреждение о длине — сигнал о regression, а не фон: все 30 скилов ужаты до ≤250 (2026-08-29).

Граница ~250 — эмпирическое наблюдение за system-reminder клиента (2026-08-29: самое короткое описание 279 симв обрезается посреди слова). Она не настраивается из плагина. Перепроверяйте при мажорных обновлениях ZCode: если окно расшират — поднять `DESC_SOFT_LIMIT` в `scripts/validate_skills.py` вместе с ним.

## Добавление нового скила

1. Создайте `skills/<1c-name>/SKILL.md` (имя с `1c-` префиксом, kebab-case).
2. Заполните frontmatter (`name` = имя каталога, `description` ≤1024).
3. Тело ≤500 строк + мини-чек-лист.
4. Если правила не помещаются — `references/<file>.md`, сошлитесь из тела.
5. Проверьте: `python3 scripts/validate_skills.py` — валидирует frontmatter, `name`=каталог, длину `description` (≤1024 — ошибка, >250 — предупреждение), `license`, тело ≤500 строк, отсутствие проектной специфики и наличие ссылок на `references/*.md` (с учётом cross-skill). Exit code: 0 (нет ошибок) / 1 (есть ошибки).
6. Обновите таблицу в `README.md`.
7. Закоммитьте с `feat(skill): добавлен 1c-<name>`.

## Синхронизация с upstream

Источники (см. [SOURCES.md](./SOURCES.md)):

- `zeegin/v8std` — стандарты. Наши карточки — **адаптация**, не копия. При изменении upstream:
  1. Прочитать diff стандарта в v8std.
  2. Внести правки в `references/<card>.md` (сохранив структуру мини-сводка).
  3. В `CHANGELOG.md` — запись со ссылкой на коммит upstream.

- `comol/ai_rules_1c` — practice. Аналогично.

- `Nikolay-Shirokov/cc-1c-skills` — спецификации (ParentConfigurations.bin, форматы `.mdo`/`.dcs`). Используем как есть, со ссылкой.

Рекомендуемая периодичность — раз в квартал сверять `std/index.md` с актуальным оглавлением v8std.

## Что НЕ делаем

- Не параметризуем скилы переменными в runtime (плейсхолдеры типа `{{prefix}}`). Вместо этого — чистые универсальные примеры + проектный overlay через `AGENTS.md`.
- Не тащим `package.json` (нет JS-кода).
- Не делаем CLI-команды установки (ZCode ставит плагины только через UI).
- Не вставляем «исторические прецеденты» (вида «инцидент Б6») — это проектные ссылки, в универсальном наборе им не место. Заменяем на нейтральные описания паттернов.
