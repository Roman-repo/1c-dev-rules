## [0.5.8] — 2026-08-13

### Добавлено

- **Совместимость с Kimi (Kimi Work): манифест `kimi.plugin.json` в корне репо.** Поля по схеме Kimi (`$schema`, `name`, `version`, `description`, `keywords`, `skills`, `skillInstructions`). Плагин регистрируется в личном маркете Kimi из рабочей папки сессии; все 22 скила `1c-*` появляются в индексе скилов. Совместимость с ZCode сохранена: `.zcode-plugin/plugin.json` и `marketplace.json` не изменены по формату.
- **Триггерные токены `when_to_use` продублированы в `description` всех 22 скилов** (суффикс «Триггеры: …»). Роутер Kimi отбирает скилы по `description` и не читает поле `when_to_use` (специфично для ZCode) — без дублирования скилы недо-срабатывали бы в Kimi. Поле `when_to_use` сохранено (обратная совместимость с ZCode); хард-лимит description (1024) не превышен, `validate_skills.py` — PASS (0 ошибок; предупреждения >250 симв — ожидаемая плата за триггеры).

### Изменено

- **`bump-version.sh` — атомарный бамп версии теперь охватывает и `kimi.plugin.json`** (три файла синхронно, с верификацией; отсутствие `kimi.plugin.json` не ошибка — скрипт по-прежнему работает в ZCode-only копиях). Иначе получился бы аналог инцидента F1 (рассинхрон версий между манифестами).
- **README — «Вариант 4 — Kimi (Kimi Work)»** в «Как подключить» (регистрация в личном маркете из workspace, процедура обновления версии), дерево репозитория дополнено `kimi.plugin.json`, снята пометка «протестировано только в ZCode».

### Происхождение

Перенос практик 6-й сессии на среду Kimi Work: анализ расхождений форматов ZCode↔Kimi (манифест, поля фронтматтера, механизм доставки — в Kimi нет git-клона маркетплейса, «урок доставки» ZCode неприменим). Изменения внесены так, чтобы один репозиторий обслуживал оба клиента.

## [0.5.7] — 2026-08-13

### Добавлено

Теперь: тип распознаётся (`Report`), автоматически работают X6 (регистрация в `Configuration.mdo`), X7 (№532 — роли `Use`/`View`) и X7b (подсистема, WARN — отчёт пользовательский, `HAS_UI=1`). Добавлена **X13** — аналог X8/X12 для СКД: `<mainDataCompositionSchema>…Template.Имя</…>` → шаблон объявлен в `<templates>` с `templateType=DataCompositionSchema` → файл `Templates/<Имя>/Template.dcs` существует. Опечатка в имени/отсутствие схемы → **FAIL** (отчёт падает при открытии). Верифицировано: позитив (новый и существующий отчёты — 7 PASS) + негатив (битая ссылка на шаблон — FAIL) + регрессия X5/X6/X7 на документе.

### Исправлено

- **🟡 X5 ложно срабатывал на отчётах СКД («рассогласование параметров запроса»).** `X5` сверяет `&X` в тексте запроса ↔ `Запрос.УстановитьПараметр("X", …)`. Но в `ObjectModule.bsl` отчёта живут инлайн-запросы СКД, чьи параметры `&X` связаны через схему компоновки / `КомпоновщикНастроек`, а **не** через `УстановитьПараметр` → ложный FAIL. Теперь для `Report` модули объекта/менеджера из X5 исключены (СКД-параметры проверяет X13); для остальных типов поведение X5 не изменилось (регрессия на документе — PASS).

### Изменено

- **`1c-thin-triggers` (§кросс-файловая согласованность) — строки для отчётов СКД.** Добавлены цепочки: `mainDataCompositionSchema` ↔ существующий `Templates/<Имя>/Template.dcs` (`templateType=DataCompositionSchema`); параметр `&X` в запросе СКД ↔ `<parameter><name>` в схеме. Ранее секция покрывала формы/реквизиты/команды/обработчики/параметры/РЗ/подписки, но не отчёты.
- **`metadata-xml.md` §7.1 — таблица цепочек дополнена до X1–X13.** Ранее таблица отставала от скрипта (перечислены X1–X7, хотя скрипт уже умел X8/X9/X11/X12): добавлены X8 (РЗ methodName), X9 (РЗ Schedule.schedule), X11 (CFE `&ИзменениеИКонтроль`↔`ПродолжитьВызов`), X12 (подписка handler) и X13 (отчёт СКД). Список поддерживаемых типов в §7.2 — `+Report`.

### Происхождение

Пятое полевое тестирование, кейс B «Отчёт на СКД» (последний непокрытый класс из A–D). Создан отчёт `торо_РасходЗапчастейПоОбъектамРемонта` на базе регистра `торо_ФактическиеЗатратыЗапчастей` (обороты) с получением объекта ремонта через срез `торо_Ремонты` (№655 — ВТ материализуются до соединения; №733 — `СрезПоследних(&ДатаСреза, ID В (…))` с обоими параметрами; №656 — без `ВЫБРАТЬ *`) и лёгким `ПриКомпоновкеРезультата` (периоды по умолчанию через пользовательские настройки). На dogfooding: валидатор не распознавал `Report` (аналог инцидента с `EventSubscription` в 0.5.5), а X5 при этом ложился на инлайн-запрос СКД существующего отчёта `торо_ФактическиеЗатратыПоОбъектамРемонта`.

## [0.5.4] — 2026-08-12

### Добавлено

Выявлено при создании перехватчика `&После ОбработкаПроведения` для `торо_АктОВыполненииЭтапаРабот`.

## [0.5.3] — 2026-08-12

### Добавлено

- **`validate-new-object.sh` — поддержка `HTTPServices` и `WebServices` (G4).** После G1 (v0.5.2) скрипт распознавал CommonModules/ScheduledJobs, но НЕ каталоги `HTTPServices`/`WebServices` → для сервисов не выполнялась §7. Теперь оба типа распознаются, попадают в `HAS_RIGHTS` (у них право `Use`, не `Read/Update`, но проверка «объект в роли» применима) → X6 (Configuration.mdo) и X7 (роль) работают. Регрессия: `WebServices/InterfaceVersion` — 6 PASS.

### Исправлено

- **🔴 G5: X5 не ловил латиничные имена параметров запроса.** Regex `&[А-Яа-яЁё_]+` пропускал параметры вида `&RepairID` → скрипт выдавал ложное «рассогласование: есть в УстановитьПараметр, нет в &X» (параметр ЕСТЬ в `&X`, просто regex его не видел). Расширено до `&[А-Яа-яA-Za-zЁё_]+` (латиничных директив не существует — безопасно). Выявлено на собственном промахе автора кейса (параметр `&RepairID` вместо кириллицы — нарушена конвенция `scriptVariant=Russian`).
- **🔴 G6: правило 12 (UUID уникальны по проекту) минутами висло на крупных объектах.** `N × grep -rln "$uuid"` (по одному обходу ~11500 файлов на каждый UUID) для `WebServices/Exchange` (81 UUID) → **5:54 минуты**. Переписано на **Python** (`os.walk` по `.mdo`/`.form`/`.rights` + regex, одним проходом): **5 секунд**, ~70× быстрее; применимо к объектам любого размера. BSD `grep -f` с многими паттернами фундаментально медленный — Python снимает зависимость от платформы grep.

### Происхождение

Третье полевое тестирование, кейс C «HTTP-сервис / интеграция». Создан входящий HTTP-сервис `торо_ОстаткиРезерваЗапчастей` (GET `/reserve?repair_id=` → JSON по баланс-регистру `торо_РезервЗапчастейНаРемонт`). ### Исправлено

- **🔴 Баг `validate-new-object.sh` X1: ложный PASS из-за `grep -c … || echo 0`.** При 0 совпадений `grep -c` печатает `0` и возвращает exit 1 → `|| echo 0` дописывает второй `0` → `fc="0\n0"` → `[[ "$fc" -eq 0 ]]` ронял syntax error, then-ветка пропускалась → X1 рапортовал «все реквизиты присутствуют» для формы, где их нет. - **🟡 `validate-new-object.sh` выбирал форму недетерминированно** (`find … | head -1`) — у документа с несколькими формами валидировалась случайная (часто не главная). Теперь проверяются **все** `Form.form` объекта (отсортированно, с префиксом имени формы в выводе).

Каноничный контроль после `Движения.Записать()` явно благословлён как исключение.
- **`metadata-xml.md` §1 (LineNumber) — разделены EDT и Конфигуратор.** Прежняя формулировка «явный `LineNumber` вызывает ошибку загрузки» была категорична для EDT: реальные EDT-`.mdo` содержат его и грузятся без ошибок. Теперь: для Конфигуратора — не добавлять; для EDT — допустим, зеркалировать образец. §6 M8 смягчён соответственно.

Второе полевое тестирование плагина на задаче класса «проведение документа + движения по регистрам» (создание баланс-регистра и документа с контролем остатков). Главные уроки:

3. **Контроль остатков оказался не описан** в `1c-events-transactions`, а требование «нужен баланс-регистр, не оборотный» не звучало ни в gate, ни в events — автор едва не реализовал «остатки» на `Turnovers`.
4. **Правило LineNumber противоречило реальным EDT-файлам** проекта-донора.

## [0.4.0] — 2026-08-12

### Добавлено

- **Кросс-файловая согласованность** — новый раздел в скиле `1c-thin-triggers` и `1c-metadata` → `references/metadata-xml.md` (§7): проверки связей имён между `.mdo`, `Form.form`, `Module.bsl`. Закрывает класс багов ручной правки XML, который **не ловили** чек-листы §6 (они проверяли каждый файл отдельно, а не связи между ними). Триггеры: реквизит объекта ↔ `dataPath` ↔ `Объект.X`; команда ↔ `handler` ↔ процедура; параметры запроса `&X` ↔ `УстановитьПараметр`; наличие в `Configuration.mdo`, ролях (№532), подсистеме.
- **`scripts/validate-new-object.sh`** — bash-скрипт автоматической проверки нового объекта метаданных: прогоняет §6 (дубликаты UUID/ID, companions, DataPath) + §7 (X1–X7: кросс-файловая согласованность, `Configuration.mdo`, №532, подсистема). Выводит отчёт PASS/FAIL. Не заменяет EDT-валидацию, ловит ~80% типовых багов ручной правки.

### Изменено

- **`1c-forms` + `1c-metadata` → `module-templates.md`** — уточнение: форма **без табличных частей** содержит **4 области** (область таблицы опускается; создавать «пустую» область таблицы без суффикса `<ИмяТаблицы>` нельзя — суффикс обязан соответствовать реальной ТЧ). Раньше формулировка «5 областей, даже пустые» создавала неоднозначность.
- **`1c-metadata`** — правило 12 (UUID) дополнено: сверять не только дубликаты (`uniq -d`), но и **ожидаемое количество** UUID в файле (ловит пропуски — UUID сгенерирован, но не попал в файл).
- **`1c-metadata`** — новое предупреждение **«Образец может быть с изъяном»**: при копировании структуры с существующего объекта не доверять образцу как эталону полноты (роли, подсистема, `Configuration.mdo` у образца могут отсутствовать). Проверять новый объект по чек-листу, не по образцу.

### Происхождение изменений

Предложение возникло из **полевого тестирования плагина** на реальной задаче 1С (создание обработки выгрузки справочника в JSON). В ходе работы два runtime-блокера:

1. несоответствие имени параметра запроса (`ВключатьПомеченные` ↔ `ВключаяПомеченные`);
2. расхождение имени реквизита `Включать`/`Включая` между `.mdo` и `Module.bsl` (`Объект.ВключаяПомеченныеНаУдаление` ↔ реквизит `ВключатьПомеченныеНаУдаление`);

— были пойманы **только** ad-hoc grep-сверками автора, а не встроенными чек-листами плагина. Этот PR добавляет класс кросс-файловых проверок в набор и автоматизирует скриптом. Сам скрипт в ходе разработки прошёл цикл dogfooding: первый прогон выявил 3 бага в нём самом (некорректный `|| echo 0`, ложное срабатывание на директивах `&НаКлиенте`/`&НаСервере`, неверный regex для типов полей EDT) — все исправлены до коммита.
