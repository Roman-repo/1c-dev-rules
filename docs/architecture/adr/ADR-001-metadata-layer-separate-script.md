# ADR-001: Metadata-проверки — отдельный слой `metadata_scan.py`, не правила в regex-сканере и не ветка обёртки BSL LS

- **Статус:** Предложено (утверждается на согласовании META-001, лист 04a)
- **Дата:** 2026-09-04
- **Автор:** функциональный архитектор (ИИ), утверждает: сопровождающий плагин (Оркестратор)
- **Задача-источник:** META-001 (эпик EP-001)

## Контекст

Этап 6 «Код ревью» имеет два детерминированных слоя: `checkbsl_scan.py`
(regex по тексту `.bsl`) и `bsl_ls_analyze.py` (AST модулей через BSL LS, Java).
Оба видят только модули — 32 ключа каталога checkbsl секции metadata
(`.mdo`/`.rights`) не достижимы в принципе (покрыто 4 из 32, потолок
regex+AST ≈58% зафиксирован в ARCHITECTURE.md). Единственная реализация
metadata-проверок — bash-скрипт `validate-new-object.sh` (X1–X15, M1–M12),
его находки без ключей каталога, № стандартов и подавлений.

Перенос проверок в конвейер имеет три кандидата-«хозяина». Источник —
вложенный XML с кросс-файловыми ссылками (`.mdo` ↔ `Configuration.mdo` ↔
`Roles/` ↔ модули), не строко-ориентированный текст и не AST модулей.

## Варианты

| № | Вариант | Плюсы | Минусы |
|---|---|---|---|
| 1 | Правила `kind="mdo"` в `checkbsl_scan.py` | один CLI, общий движок правил | движок сканера — построчный regex: `.mdo` — вложенный XML, нужны ET-парсинг и кросс-файловый контекст (`--src-root`); смешение трёх моделей (строка/AST/дерево+ссылки) усложняет RULES, дифф-фильтр и тесты; регрессионный риск для работающего слоя |
| 2 | Отдельный `scripts/metadata_scan.py` (CLI-конвенции сканера, общие подавления/fixes) | источник нового типа = отдельный слой; работает без Java; перенос bash 1:1; независимые тесты; вливание в обёртку — контролируемая задача META-002 | до META-002 петля запускает слой отдельной командой (третий CLI) |
| 3 | Metadata-ветка в обёртке `bsl_ls_analyze.py` | сразу один отчёт слоёв | обёртка завязана на Java/BSL LS и их конфиги; слой обязан работать на машинах без Java (наследие сканера, graceful degradation); рост сложности обёртки до чужой ей модели данных |
| 4 | Ничего не делать | бесплатно | слепая зона 28/32 metadata-ключей остаётся; потолок 58% неподвижен; bash-дрейф продолжается |

## Решение

Вариант 2: отдельный слой `scripts/metadata_scan.py` — декларативные CHECKS
+ stdlib `xml.etree`, CLI как у сканера (`--diff`, `--src-root`,
`--suppress`, `--format md|json`, `--coverage-report`, exit 0/1/2),
подавления через `review_suppress.py`, fixes — общая база `bsl_ls_fixes.json`.
Слияние в отчёт обёртки — задача META-002 по результатам MVP.

## Причины

Разделение слоёв по типу источника (текст `.bsl` / AST модулей / XML
метаданных) уже принято архитектурой этапа 6; metadata-источник не
претендует на чужие движки — свой каркас минимальен (ET + предикаты,
«свой анализатор» не пишем — регламент стиля работы). Независимость от Java
сохраняет слой для машин без BSL LS. Перенос bash-проверок 1:1 (включая
купированные ложняки полевых тестов) минимизирует регрессию. Вариант 3
отвергнут как преждевременное слияние до подтверждения MVP на живых диффах;
вариант 1 — как смешение несовместимых моделей разбора.

## Последствия

**Стало проще / лучше:**
- третья, независимая точка роста покрытия (потолок 58% сдвигается
  источниками, не алиасами — цель EP-001);
- слой тестируется изолированно; петля самоочистки получает metadata-руку
  без Java;
- судьба `validate-new-object.sh` решается консолидацией (вызов слоя +
  формовые проверки до эпика форм).

**Стало дороже / нельзя:**
- до META-002 у петли две команды вместо одной (слой + обёртка);
- подавления/счётчик живут в двух местах до слияния — синхронизируются
  META-002;
- формат EDT-выгрузки — внешнее допущение: при смене формата правится
  парсер (риск зафиксирован в 01 META-001).
