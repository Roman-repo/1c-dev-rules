МИССИЯ СЕССИИ — ПОЛЕВОЙ ПРОГОН КОНВЕЙЕРА (первое реальное применение):
Одна реальная задача в toir2 **от постановки до релиза** по скилам конвейера,
со всеми артефактами. Это dogfooding шаблонов/DoD-гейтов/классификации:
каждое неудобство — находка для плагина.

1) Получи постановку задачи у инициатора (пользователь — инициатор и
   приёмщик). Если постановки нет — AskUserQuestion: «какая задача?»,
   принимается даже размытая: этап Планирования для того и существует.
2) Веди задачу по конвейеру (роль → скил → артефакт → DoD-гейт):
   • Планирование (1c-planning, роль РП): интервью → `01-task-brief.md`
     (цель-не-решение, измеримые критерии успеха, рамки «что НЕ делаем»,
     S/M/L) → подтверждение инициатора.
   • Проектирование (1c-solution-design, архитектор+аналитик):
     `02-execution-scenario.md` (№|Роль|Шаг|Триггер|Подшаги|Результат +
     обязательные альтернативные потоки), `03-change-spec.md` (объекты,
     миграции, права, impact, откат + arch-checklist), `04-acceptance-
     criteria.md` (критерии + матрица трассировки без пустых ячеек).
   • Разработка (1c-dispatch-gate → тематические скилы → код →
     thin-triggers + code-review + validate-new-object.sh).
   • Внутренняя приёмка (1c-internal-acceptance): прогон КАЖДОГО шага
     сценария с evidence → `05-internal-acceptance.md`; красное = самовозврат.
   • Внешняя приёмка (1c-external-acceptance): демонстрация инициатору по
     матрице 04 → `06-acceptance-protocol.md` (+ 06a при возврате; класс C —
     новая задача).
   • Релиз (1c-release): `release-manifest.md` + `release-notes.md`
     (в docs/delivery/_releases/<версия>/).
   Артефакты — в toir2: `docs/delivery/<ID-задачи>/` (каталог создать; ID
   согласуй с пользователем, например TASK-001).
3) Отклонения плагина (неудобные поля шаблонов, дыры DoD-гейтов, ложные
   срабатывания) — отчёт (формат ниже) → фикс в ~/Projects/1c-dev-rules →
   PR → `bash scripts/bump-version.sh patch` (0.11.x).
