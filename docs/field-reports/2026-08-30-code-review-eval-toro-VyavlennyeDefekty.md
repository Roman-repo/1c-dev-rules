## Оценка работы этапа

- **Слои отработали по конструкции.** Сканер <1 с, exit-коды по контракту.
  BSL LS: 105 с с нуля на полной конфигурации (2627 модулей), повтор по
  кэшу ≈2,7 с (замер сессии фикса). Отчёт r1 самодостаточен для возврата
  Исполнителю: код с маркером строки + «что не так» + «как правильно» +
  вердикт петли — ручной подготовки не требует.
- **Трёхслойность не избыточна — подтверждено на живом коде.** ИИ-проход по
  чек-листу добавил поверх детерминированных слоёв 🔴 №783 (запрос и запись
  статусов оснований внутри транзакции проведения — ObjectModule.bsl:166,171)
  и 🟡 №648 (~18 точечных чтений реквизитов Основание через точку). Обе
  категории не выражены AST-диагностиками BSL LS в принципе: границы
  платформенных транзакций и неявные запросы через точку — семантика
  исполнения, а не синтаксис. Вывод: ручной слой конвейера незамыкаем
  слоями 1–2, деление труда корректно.
- **Рубрикация чек-листа пригодна для модуля документа**: секции
  0/1/2/4/5/8 релевантны, 3/6/7 честно n/a — лишней работы не наводит,
  §8 прогоняется целиком.
- **Петля самоочистки**: вердикт r1 = 🔴 есть → «возврат на Разработку» —
  механика воспроизводима без конвейера задачи (модуль вне диффа), т.е.
  этап применим и к ревью существующего кода, не только к задачам.
- Побочно ревью вскрыло особенность типового кода ТОИР: экспорт-переменные
  `БезусловнаяЗапись`/`СтруктураДанных` — единый паттерн всех документов
  (проверено по торо_ЗаявкаНаРемонт, торо_ЗакрытиеЗаявокИРемонтов),
  `Источник.БезусловнаяЗапись` читается в ОМ торо_Ремонты:1325 —
  типовой «канал состояния», для плагина это сигнал: замечание
  ExportVariable в типовых конфигурациях требует проверки контракта,
  прежде чем предлагать правку (в отчёте ревью оформлено обоснованием).

## Отклонения плагина

```
[Сканер checkbsl_scan.py] — CommentedOutCodeLine сработал на описательном
  комментарии
Пример: ObjectModule.bsl:269 «// Движения по регистру "Внешние основания
  для работ", простановка Обработано = Истина» — комментарий описывает
  поведение процедуры, кода не содержит; паттерн «= Истина» внутри текста
  дал 🟢-срабатывание (в выводе сканера — единственное замечание с
  текстом, второе StyleLowercaseПерем — корректное).
Предложение: в паттерне требовать начала строки с код-токена (ключевое
  слово/оператор), а не произвольного текста с «=».
Класс: 🟡 ложное срабатывание
```

```
[Этап 6, детерминированные слои] — чтение БД внутри транзакции проведения
  (№783) не ловится ни сканером, ни BSL LS
Пример: ObjectModule.bsl:166 — Запрос.Выполнить() в ОбработкаПроведения;
  диагностик BSL LS с такой семантикой нет, границы платформенных
  транзакций в AST не видны. Ловится только ручным чек-листом §4/§8.1
  (что и произошло).
Предложение: за чек-листом и оставить (семантика), но закрепить в скиле
  1c-events-transactions явный подпункт «запрос в обработчике проведения»
  с примером выноса чтения за транзакцию.
Класс: 🟢 пробел в покрытии (осознанный, закрывается ручным слоем)
```

```
[Каталог checkbsl] — нет ключа на множественные точечные чтения реквизитов
  одной ссылки вне цикла
Пример: ObjectModule.bsl:15–50 — Основание.Дата/.Ответственный/
  .Организация/.Подразделение (+.Комиссия) ×4 ветки ≈ 18 неявных запросов;
  перекликается с известным пробелом «чтение через точку в цикле»
  (next-session-prompt, миссия п.8(в)).
Предложение: карточка каталога + пункт чек-листа §5 «несколько полей одной
  ссылки — одним ЗначенияРеквизитовОбъекта(Ссылка, "Дата, Ответственный…")».
Класс: 🟢 пробел в покрытии
```

```
[bsl_ls_fixes.json] — пример «как правильно» для MethodCognitiveComplexity
  нерелевантен ветвлению по ТипЗнч
Пример: bsl-ls-r1.md §1 советует «ранний выход вместо вложенности», а
  реальный фикс ОбработкиЗаполнения — декомпозиция 4 дублирующихся веток
  в помощник заполнения (так и оформлено в отчёте ревью).
Предложение: дополнить запись fixes примером декомпозиции веток
  заполнения по основанию.
Класс: 🟢 пробел в покрытии
```
