# Регрессионный набор триггеров скилов

> Постоянная проверка того, что разговорные запросы активируют нужные скилы,
> а похожие запросы не активируют их ошибочно. Источник данных —
> `tests/fixtures/skill_triggers.json` (issue #109).

## Состав и контракт

Для каждого из 30 скилов записаны:

- **3–5 позитивных фраз** — скил должен быть открыт;
- **1–2 негативные фразы** — целевой скил не должен быть открыт;
- сценарий, ожидаемый маршрутизатор и обязательные тематические скилы.

Текущий объём: **30 кейсов, 90 позитивных и 30 негативных фраз**.

| Сценарий | Ключ в JSON | Маршрутизатор по умолчанию | Что проверяется |
|---|---|---|---|
| Полный конвейер | `full_conveyor` | `1c-delivery-gate` | Жизненный цикл задачи и этапные скилы |
| Точечная разработка | `point_development` | `1c-dispatch-gate` | Маршрутизация кода к тематическим скилам |

Для прямого входа без отдельного маршрутизатора `expected.router` равен имени
самого скила (например, `1c-project-bootstrap`). В `expected.skills` первым
обязательным результатом всегда является целевой скил кейса.

## Структурная проверка в CI

```bash
python3 -m unittest tests.test_skill_trigger_regression -v
```

Автотесты проверяют: покрытие всех реальных каталогов `skills/`, отсутствие
дублей, число фраз, оба сценария, существование маршрутизатора и ожидаемых
скилов. Это **не имитация решения модели**: фактическая активация проверяется
живым прогоном ниже.

## Живой прогон в ZCode или Kimi

1. Установить проверяемую версию плагина и перезапустить клиент.
2. Выбрать клиент и сценарий; прогонять ZCode и Kimi как отдельные проверки.
3. Для каждой фразы открыть чистую сессию, чтобы предыдущий контекст не влиял на выбор.
4. Отправить фразу из JSON дословно, без `/1c-<имя>` и без ручного открытия скила.
5. Зафиксировать фактически открытые маршрутизатор и скилы.
6. Позитив засчитан, если открыт ожидаемый маршрутизатор и все `expected.skills`.
7. Негатив засчитан, если целевой скил кейса не открыт; открытие другого уместного скила не является ошибкой.
8. Любое расхождение оформить как регрессию триггера: фраза, ожидание, факт, клиент, версия плагина.

После изменения `description` скила сначала прогоняются его позитивы и негативы,
затем — полный набор перед релизом. Изменение смысла скила требует осознанного
обновления ожидаемого маршрута в JSON, а не только подгонки описания под старый тест.

## Отчёт живого прогона

Сохранять в `docs/field-reports/YYYY-MM-DD-skill-triggers-<client>.md`:

| Skill | Scenario | Phrase | Type | Expected | Actual | Result |
|---|---|---|---|---|---|---|
| `1c-...` | `full_conveyor` | дословная фраза | positive/negative | router + skills | фактически открыто | PASS/FAIL |

В шапке отчёта указать клиент, версию плагина, дату и итог
`PASS/всего` отдельно для позитивов, негативов и двух сценариев.
